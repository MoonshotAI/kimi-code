# llm Module Guide

llm is a standalone LLM request library in `@moonshot-ai/core` (`packages/core/src/llm/`). It owns one complete request: a typed request contract, protocol encoding and decoding, streaming facts, thinking, media, error classification, and policy-driven attempts. Provider catalog state, media stores, OAuth, and turn orchestration live in agent-core-v2, which passes core request and response types directly without an adapter.

## Design Principles

1. **Minimal boundary: llm = "a single request"**. The core composes a request with `createRequester().with(...)` and returns an `LlmOutcome` from `generate`. Request content uses `Message` values carrying optional `MessageAttributes`, preserved through resolvers and legalization and converted once when lowering to `NativeModule` (including rendering tool error/empty status for the model); outcomes contain `AssistantMessage` values with actual model, usage, finish, and response `attributes`. The library does not own provider catalog refresh state, session usage ledgers, compaction, switch, the media file system, or turn orchestration. There is no second requester, outer `HistoryEntry` wrapper, or compatibility event vocabulary.
2. **Streaming-native; outcomes and events have separate roles**. Core request execution returns `done / failed / aborted` as an `LlmOutcome` and emits `LlmRunEvent` values as they arrive. Completed, failed, interrupted, and retrying partial output all use the same `AssistantMessage` construction. Retry events carry partial output for diagnostics and stream resets without appending it to history; Loop appends only the final outcome message without reconstructing model metadata. `streamLlmRequest` exposes that same union as an `AsyncIterable` for transports, ending with `llm.ended` and its outcome. Streaming and non-streaming share the decoder: `stream: false` uses `send` and replays the complete response through it. The event vocabulary is `llm.started / requested / queued / notice / delta.* / retry / ended`; generation failures are returned directly and tool-call boundaries use decoder callbacks rather than `attempt.*` events.
3. **The pipeline masks inter-protocol differences; protocol patches express provider customizations**. Every protocol is a `defineProtocol` object (`packages/core/src/llm/protocol/protocol.ts`): `runPipeline` composes the encode stages (cacheKey → thinking → responseFormat → maxOutputTokens → sampling → tool → message → mergeTurns → annotate → finalize → flatten), with legalize passes for media, tool-call ids, provider patterns, thinking history, and model rules. A protocol also provides its stream decoder, non-streaming replay, error decoder, and client/send/sendStream transport. Providers derive protocols with `protocol.with(patch)`; Kimi lives in `packages/core/src/llm/builtin/provider/kimi/protocol.ts`. Endpoint declarations and environment resolution use the shared implementation in `packages/core/src/llm/endpoint.ts`.
4. **Two-layer error model**. Local validation throws `SyntaxRequestFormatError` from `llm/protocol/errors.ts`, converted by `toLlmSyntaxErrorMessage`. Protocol and transport failures become `LlmErrorMessage` values inside a failed `LlmOutcome`, preserving status fields, raw errors, request ids, and protocol-provided diagnostics. A protocol can implement `diagnoseError` to extract provider-specific details from the current attempt instead of exposing a generic `traceId`. Callers consume these core error values directly without a second error union.
5. **Immutable requester configuration + scoped execution memory**. A core requester is an immutable composition of protocol, endpoint, model, profile, content, and policy dimensions. Derived requesters share an execution context containing reusable in-memory recovery entries, while each generate restores an independent ledger so concurrent calls remain isolated. Ordinary Turns and side operations reuse these entries; a successful Loop reset clears them so Undo and history replacement do not inherit stale rewrites. `ProviderCatalogService.createRequester` initializes configuration when `AgentLoopService.syncRequester` creates or refreshes the Loop base requester; `AgentLoopService` owns the Loop and its execution context. Its `requester` getter exposes the raw `loop.requester`, and other Agent services call `loopService.requester.with(...)` with request `attributes` and policy overrides for side requests rather than injecting another requester service or decorator. Structural projection and media resolution run per attempt through registered policies, while outer retry remains with the turn machine and Loop. Credential recovery uses the shared core policy. Reusable media entries capture which media to omit and mark those outbound media parts with a request-scoped `omitted` placeholder reason instead of replacing them (never persisted to history), so later resolvers still see the original reference. Protocol legalization renders the placeholder for any part that is still marked; the agent media resolver renders it together with the attachment's name and local session path. The settle stage owns the attempt-scoped message accumulator, emits normalized streamed parts, validates completed tool-call arguments against resolved tool descriptions (including deferred entries), judges empty responses, records timing, emits `llm.requested` with the legacy request summary at each attempt, and synthesizes the outcome. Invalid arguments produce an `invalid_tool_arguments` retry without executing the call; the next attempt carries only a temporary system validation reminder instead of the rejected call, and that reminder is not persisted to the conversation journal. Each retry/recovery attempt creates a fresh accumulator; Loop consumes the final `AssistantMessage` for completed and interrupted history instead of maintaining another accumulator.
6. **No silent fallback**. Configuration is used exactly as given. Unsupported beta features, thinking settings, media, and empty responses fail explicitly rather than silently switching behavior. Argument validation is limited to newly completed tool calls; existing session history keeps its previous encoding and replay behavior. Empty arguments are accepted only when the resolved schema accepts `{}`.
7. **Every variable capability is a contribution point**. Protocol patches, media upload/degradation, usage, protocol error diagnostics, and recovery plug in around the core. The core does not import v2 DI, models-dev, or provider-catalog state.
8. **Data is data**. `LlmModelSpec` and `LlmRequest` are serializable core contracts. Core messages use the existing `imageUrl/audioUrl/videoUrl` media parts; data URLs, `kimi-file://` session references, and uploaded `ms://` file ids stay in those parts. `ProviderCatalogService` owns model/provider configuration records, catalog metadata and default-model selection; it initializes requesters without caching them or exposing generate/ping, stamping `protocol.name` and `attributes.modelAlias/providerType` onto the immutable requester so every derived `LlmRequest` carries the model identity it was created with. Upload capability is declared by `LlmEndpoint.files`, and the Agent media resolver registered in `loop.policy` receives the current `LlmRequest` directly, reading capabilities from `request.model.spec`, provider/protocol identity via `requestModelOf(request)`, and upload/credential hooks from `request.endpoint`; `LoopLlmRunObserver.start(request)` reads the same request-carried identity so usage, model attribution, and cache-break telemetry stay aligned with the wire model across mid-turn config changes and side-request retries. `SessionMediaStore.put` stores bytes and metadata and returns a `kimi-file://` reference, while `get` reads them back. ReadMediaFile only produces references; the Media Resolver resolves them on the next request using the request model, protocol media support, endpoint files, and endpoint credential recovery. The v2 history/wire message shape remains in `src/human/message.ts`; its codec preserves roles and envelopes without introducing a second media representation.
9. **Message conversion uses a compiler paradigm**. Generic messages become protocol payloads through ordered, independent patterns followed by lowering. Tool-message conversion and media mapping are patterns too. Main-line tool-result placeholders, reasoning details, and provider-specific wire behavior remain covered by the existing tests.

## Architecture

```
packages/core/src/llm/
├── message.ts                 core Message, MessageAttributes, tool-result rendering, and media parts
├── origin.ts                  prompt-origin metadata and message-origin transforms
├── context-usage.ts           Message-based context-token estimation
├── request.ts                 model, endpoint, protocol, profile, content, and policy dimensions
├── response.ts                run/stream events, LlmOutcome, timing, and notices
├── usage.ts                   TokenUsage, stream-patch merge, and counter arithmetic
├── endpoint.ts                endpoint declarations, environment fallback, and credential resolution
├── requester.ts               createRequester + immutable .with() composition + generate
├── stream.ts                  LlmRunEvent as an AsyncIterable for transports
├── thinking.ts                shared thinking validation and effort resolution
├── generate.ts                attempt driver: encode → client → send/sendStream (+replay) → decode
├── policy/                    attempts, settlement, retries, recoveries, resolvers, and credentials
├── protocol/                  defineProtocol, pipeline, patterns, shared rules, and protocol kits
├── transport/                 headers-timeout and proxy-aware fetch
└── builtin/
    ├── protocol/              openai / openai-responses / anthropic / google-genai implementations
    ├── provider/              core requester presets, including builtin/provider/kimi
    └── policy/                built-in recoveries, including media degradation

packages/agent-core-v2/src/human/
├── message.ts                 v2 history/wire Message model and accumulator
├── provider-catalog/          refresh/upsert/remove state and dual-source model merge
└── media/                     media cache, refs, resolver, store, upload, and Kimi uploads

packages/agent-core-v2/src/provider-catalog/
├── providerCatalogService.ts  App-scoped configuration, catalog, protocol, and requester service
├── configuration-store.ts     shared model/provider record storage and change events
├── model/                     record types, runtime projection helpers, OAuth/model auth, and budgets
├── provider/                  provider record types and core requester presets
├── protocol/                  capability/identity metadata and provider error domain
├── requester.ts               requester routing helpers
├── errors.ts                  provider errors and core error conversions
└── capability.ts              legacy capability conversion

packages/agent-core-v2/src/agent/loop/
├── mediaPolicy.ts             Loop media-tool and media-resolution policies
├── toolSelectPolicy.ts        Loop ToolSelect resolver
├── requestMetadata.ts         request attribution tracker and metadata-header resolver
├── loopService.ts             Loop wiring, policy registration, and syncRequester
└── requestObservation.ts      per-run observer for request trace, usage, events, and telemetry
```

Host composition lives in `agent/loop/` and `provider-catalog/`: `loopService.ts`, `projector.ts`, and `projection.ts` are ordinary objects constructed with the Loop, not scoped services. The single App-scoped `ProviderCatalogService` owns model/provider configuration CRUD and change events, catalog queries and runtime projection, protocol capability/identity/base-id/supported-protocol metadata, and core-requester initialization through `createRequester`. `AgentLoopService.syncRequester` combines that service with Profile, model, completion-budget, and execution context, and calls `loop.setRequester` whenever config, catalog, or Profile changes (taking effect on the next Turn). Agent policies (ToolSelect, media tools, structure, media resolution, request-metadata headers, credential/structure/media recoveries) are registered directly on `loop.policy`. Profile, Loop, and klient pass `LlmRequestPart`, full `LlmRequest`, `LlmRunEvent`, and `LlmOutcome` directly without a translation layer.

Request lifecycle: `AgentLoopService.syncRequester` calls `ProviderCatalogService.createRequester` with protocol, model, endpoint, credential-aware headers, timeout fetch, optional `LlmEndpoint.files`, and the Agent-scoped execution context → a normal Turn uses the base requester captured at Turn start, while a side operation calls `loop.requester.with(...)` with its own content, model budget, `attributes` (`kind`, `turnId`, `logFields`, `promptCacheProbe`), and retry policy → each Step or side call issues one `generate` call, and core `LoopLlmRunObserver.start(request)` creates a per-run observation; `runLlmRequest` computes usedTokens from the final profile and restores a generate-local recovery ledger from requester memory → each attempt applies inherited and newly proposed rewrites, runs ToolSelect, media-tool, structure, media, and request-metadata resolvers from `loop.policy` in order over `Message` values (preserving `attributes`), emits `llm.started` once at run entry, then emits `llm.requested` and records the resolved request for each attempt → the protocol legalize/pipeline stages rewrite `Message` values, strip `deferred` metadata for models without dynamic loading, render tool status at `NativeModule` conversion, and lower all declared tools and messages → the client uses `sendStream`, or `send` plus replay for non-streaming → settle produces an `AssistantMessage` with actual request `attributes` and emits stream facts → Loop or klient consumes the same `LlmRunEvent` vocabulary, with klient using `streamLlmRequest` directly. There is no request preview, `step.model`, outer `HistoryEntry` wrapper, or Loop-side `AssistantMessage` reconstruction. ReadMediaFile stays registered and only produces `kimi-file` references; the media-tool resolver hides its schema, calls, and results when the model accepts neither image nor video, and the media resolver turns references into a capability hint, an uploaded file id, or inline base64. Full compaction and prompt prediction use the same `loop.requester`, `loop.policy`, and run observer, with request trace, usage, and telemetry owned by Loop observation.

Tool disclosure is a request-view concern rather than an execution permission. At the final `legalize-tools` boundary, top-level declarations win (the last duplicate wins), then system messages are scanned newest to oldest; removed duplicates emit one `llm.notice` and one warning log per tool name. A `tool_lifecycle` text-part meta clears the removed names from this duplicate scan, so declarations on opposite sides of that unload boundary survive; legacy duplicates without the meta keep the last-declaration-wins behavior. This pass never deletes system messages, even when their tool arrays become empty; empty-message cleanup belongs to other passes. The Agent persists its pre-resolver Loop baseline (`tools.settled`) and ordered runtime changes after MCP initialization; session restore reuses a persisted `tools.settled` baseline verbatim without re-filtering it against newer policy changes, while older journals without `tools.settled` derive the baseline once via `initialTools()` from their replayed `tool_select.initialized` snapshot and session policy. Tool policy disables gate execution without mutating a frozen baseline, and later requests reconcile runtime catalog changes without rewriting an unchanged baseline. For capable models, the ToolSelect resolver removes deferred entries from the resolved top-level tools and converts the Loop-baseline deferred names into an initial tool-change snapshot at the start of the projected messages. The step reminder provider emits only subsequent added/removed deltas, folding them against the last projected announcements until the history revision changes. SelectTools delivers selected schemas through system messages appended by `loop.remind`. Loaded state requires the exact active schema version. A same-name modification of a deferred or runtime-disclosed tool records removed old and added new definitions in one delta. Its announcement remains the same wrapped reminder text on every provider and carries `tool_lifecycle` meta with the added and removed names. At request shaping, `shapeActiveHistory` narrows each announcement's `tool_lifecycle.removed` view to names still declared by earlier system tool-schema messages in that request, excluding top-level inline tools and names already unloaded, without rewriting persisted history or the reminder text. Kimi Chat Completions lowers each non-empty removed list to an immediately following system `unload_tools` message without `content` or `type`; names that only appeared in the loadable catalog or were already unloaded do not emit `unload_tools`. Loads remain system messages with `tools`. Before reselection, execution rejects the stale schema and directs the model to `select_tools`; after reselection, the current schema and executor run normally. A same-name modification of a purely inline tool keeps the active schema and executor pinned for the current running session and emits the existing reminder once per service instance. Models without dynamically loaded tools keep the provided top-level tools; `requestTools` only shapes the supplied list and never appends out-of-baseline tools from the live registry, so late-connected MCP servers and runtime additions never change the top-level tool list or invalidate the prompt cache prefix. The resolver removes `select_tools` and system tool schemas, converts lifecycle announcements to plain runtime reminders without lifecycle meta, and strips the `deferred` metadata; `legalize` retains the same deferred cleanup as a boundary safeguard for requests that bypass ToolSelect. Runtime additions are not copied into `tool[]`, and name changes remain content-bearing reminders. Model switches never rewrite the persisted snapshot, change ledger, or context history. Explicit tool overrides remain unchanged.

## Rejected Schemes (do not reintroduce)

- A `ModelRequester` wrapper, scoped `AgentLLMRequesterService` / `AgentContextProjectorService`, or a separate catalog/requester facade — `ProviderCatalogService` initializes requests, Loop owns the raw requester and execution context, and the human catalog owns only refresh state and metadata.
- Splitting the request actor into llmActor / llmStreamActor — one actor per request; non-streaming also accumulates over the stream.
- A dedicated llm state machine wrapping the request actor — the turn machine invokes the actor directly and owns retry/recovery.
- DDD domain-method wrapping (Generation Domain, etc.) — use the pipeline/protocol/provider layering instead.
- Per-request trait hook objects passed to requester factories — provider customization belongs in `protocol.with(patch)` composition.
- Binding customization into format closures — providers patch the protocol spec rather than wrapping the requester.
- A second `ProviderDefinition` / `Provider.createRequester()` route — built-in providers remain core requester preset data, and `ProviderCatalogService.createRequester` composes them in one place.
- A second requester or request adapter parallel to `llm/` — callers use core request, event, outcome, and error types directly.
- Hoisting system messages out of their position on egress — system messages stay in place in history and are converted in place.
- Loop rebuilding `AssistantMessage` attributes from a plain message plus `step.model`, or wrapping `Message` in a separate `HistoryEntry` envelope — llm owns `Message` + `MessageAttributes` and fills actual request attributes at settlement while dropping `attributes` at `NativeModule` conversion.
- A second Loop/turn message accumulator — settle owns the attempt-scoped accumulator and normalized stream; Loop only consumes its events and final outcome.
- Unlimited fallback for beta features — protocols are selected explicitly, and `betaApi` remains an options/model-driven opt-in.
