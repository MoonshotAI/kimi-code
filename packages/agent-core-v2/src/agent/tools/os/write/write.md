Create, append to, or replace a file entirely.

- Missing parent directories are created automatically (like `mkdir(parents=True, exist_ok=True)`).
- Mode defaults to overwrite; append adds content at EOF without adding a newline.
- Write is NOT ALLOWED for incremental changes to existing files, including trivial, one-line, quick, or cosmetic edits. Use Edit instead.
- Use Write only when the file does not exist, you intend a complete replacement, or the new contents have little continuity with the old contents.
- Do not create unsolicited documentation files (`*.md` write-ups, `README`s, summaries) just because a task finished — write one only when the user asks for it, or when a task or project instruction requires it (e.g. the plan-mode plan file, created with Write when plan mode directs you to, or a changeset the repo mandates).
- Read before overwriting an existing file.
- When overwriting an existing file, its byte order mark (BOM) and dominant line ending style are preserved: a UTF-8 BOM is written back, a valid UTF-16 BOM re-encodes the content as UTF-16 (malformed UTF-16, and any write bridged through an ACP client that receives text, is written as UTF-8 instead), and content line endings are converted to the file's dominant style (CRLF, LF, or CR). A file without a BOM stays BOM-less (one leading U+FEFF in the content is dropped). BOM-less UTF-16 whose bytes are also valid UTF-8 is indistinguishable from UTF-8 and is treated as UTF-8. Files that are not decodable text (binary or UTF-32) are overwritten literally as UTF-8.
- For new files — including files created by append — line endings and BOM follow repo conventions: `end_of_line` and `charset` (`utf-8-bom`, `utf-16le`, `utf-16be`) from the nearest `.editorconfig` (searching from the file's directory up to the workspace boundary, stopping at `root = true`) take precedence; otherwise the dominant style of same-extension sibling files in the same directory applies. A resolved BOM-less convention (for example `charset = utf-8` or BOM-less siblings) drops one leading U+FEFF from the supplied content. With no signal at all, new files are written exactly as supplied (no BOM).
- Write ignores the Read/Edit line-number view. NEVER include line prefixes.
- Appending to an existing file outputs supplied line endings literally: \n stays LF, \r\n stays CRLF.
- For new content too large for one call, overwrite the first chunk, then append subsequent chunks. Appended chunks are literal UTF-8 bytes, so a chunked write cannot build a UTF-16 file or enforce a line-ending convention — for such targets, assemble the content first (e.g. write chunks to a temp file and combine via Bash) instead of appending directly. Never chunk Write to modify an existing file.
