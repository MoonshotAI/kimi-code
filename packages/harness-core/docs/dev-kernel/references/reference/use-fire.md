# useFire

Reference：需要在 setup 中取得绑定当前节点的事件发送函数，并在后续业务回调里通知祖先时使用 `useFire`。

## 使用场景

- 从发生动作的节点向祖先报告事件，让路径上的订阅者同步处理。
- 不适合请求应答、等待异步监听器完成或向所有兄弟广播；兄弟协作见 [兄弟事件](../how-to-guides/sibling-events.md)。

## 调用契约

```ts
useFire(): (event: RuntimeEvent) => void
```

- 取得函数必须在同步 setup 中；返回的函数保存当前节点，之后调用不要求 setup 上下文。
- 事件必须包含字符串 `type`，其余字段由业务定义；发送函数返回 `void`。
- 每次发送取该节点当时的自身至根路径，不扫描其他分支。
- capture 阶段从根到发送节点，随后 bubble 阶段从发送节点到根；发送节点也参与两个阶段。
- 每个节点、每个阶段先运行具体类型的处理器，再运行 `'*'` 处理器；各组按登记顺序执行。
- 实际派发的是合并后的浅拷贝事件，不是原输入对象本身。

## 边界

- `EventContext` 从根到发送节点逐层合并；同节点按提供先后合并所有条目，后条目覆盖前条目，较深节点覆盖祖先，最后显式事件字段覆盖上下文。
- 这与 [inject](inject.md) 只取最近栈顶条目的规则不同；不要把事件上下文合并理解为一次注入。
- 祖先接收到事件并不意味着祖先的其他子节点也会接收；事件只沿本次发送路径传播。
- 派发是同步调用，没有队列、异常隔离或自动等待；处理器抛错会直接向发送者传播并中断后续派发。
- async 处理器返回的 Promise 不被等待；不要把发送成功当成异步处理成功，也不要让异步拒绝无人处理。
- 没有内建的停止传播、取消默认行为或返回值收集协议；事件上的同名字段也不会触发这些机制。
- 显式 `node.fire(event)` 使用相同派发逻辑，无需先调用本 hook；发送函数自身不登记资源，也没有撤销 API。
- 保存的函数不会因卸载自动失效，`fire()` 也没有统一的已卸载检查；业务回调应随所有者清理，避免卸载期间或之后继续发送。
- 处理器的生命周期由 [useOn](use-on.md) 或 `node.on()` 的取消函数管理，与发送函数分开。
