## Repository Shape

- `src/kernel/`: the Unit runtime on `@vue/reactivity` — `createUnit`/`mountRoot`, token tiers (`createToken`/`createFacadeToken`/`createCollection`), setup hooks (`provide`/`useInject`/`useExpose`/`useReady`/`useFire`/`useOn`/`useWait`/`useContribute`/`useCollection`/`useChildren`/`useMounted`/`useCleanup`), and the re-exported reactivity primitives (`ref`/`reactive`/`computed`/`watch`/`watchEffect`/`effectScope`). Event listeners accept `{ once: true }`, and `useWait`/`UnitNode.wait(type, { match, timeoutMs, signal })` awaits a single matching (enriched) event, rejecting on timeout, external abort or unit unmount.
- `src/llm/`: canonical contract (`request.ts`, `message.ts`, `response.ts`, `endpoint.ts`), `requester.ts`, `generate.ts`.
- `src/llm/policy/`: run loop, resolvers, recoveries, retry, settle.
- `src/llm/protocol/`: mechanism (`protocol.ts`, `pipeline.ts`, `pattern.ts`, `errors.ts`); `rules/` for rules the core applies to every protocol; `kit/` for opt-in protocol helpers.
- `src/llm/builtin/`: protocols, providers, built-in policies.
- `src/llm/builtin/policy/store-ref/`: resolver that turns `store` refs into wire sources; ports (`RefStore`, `UploadCache`), mechanism (`resolve.ts`, `materialize.ts`, `session.ts` with the in-process memo and budget) and `adapters/blob.ts` (`createBlobRefStore` maps a failed integrity check to unavailable, `createBlobUploadCache` validates entries and ignores cache errors).
- `src/loop/`: the public entry `createLoop` (`create-loop.ts`), a `Loop` instance with plain methods, a `subscribe` event channel and a plain `state` projection — with `wait(type, { match, timeoutMs, signal })` awaiting a single emitted event over that channel; XState stays behind it, and each method validates its arguments once (throwing `TypeError`) before the command reaches the machine. `loop.requester` (`requester.ts`) is a `LoopLlmRequester` facade for side requests: each `request`/`generate` re-reads the host's requester getter and fills it with the live history (`toRequestMessages` of the loop messages plus a `usedContextTokens` estimate) before applying the accumulated `.with()` parts, so terminal calls always run the host requester's own methods on the latest configuration and context. Input commands (`submit`/`notify`/`remind`/`steer`/`cancel`/`setContext`/`setSystemPrompt`/`setTools`) return the event the machine emitted synchronously for them, or `undefined` once the loop is closed. The loop's profile (system prompt and tool descriptions) is native state: `setSystemPrompt`/`setTools` settle it like `setContext` (accepted while idle and at a step's ending, rejected otherwise; a mid-turn change takes effect from the next step), the request actor adds it to every LLM request next to the history where it overrides any `profile` layered on the host's requester, and `loop.state.profile` exposes the current values. Two hook points sit inside the step lifecycle: `step.starting` fires once per LLM request before it (not per retry; a resumed turn's next step passes through it while `turn.starting` is skipped) with the current messages and profile, and may rewrite the history (chained through the hooks; an effective rewrite assigns `context.messages` and is settled as `context.settled`, so it stays durable) or block the step (`blocked at step.starting`, with `step.ended`/`turn.ended` still emitted); `tool.batch-starting` fires once after a done reply with tool calls and before the tool actors spawn, and a block applies to every call (each gets `tool.started`/`tool.ended` with the blocked outcome sharing one optional result, no per-call hooks or executors run, and the tool entries land in the history as usual). Per call, `tool.starting` hooks run first and `tool.permitting` hooks second: the phase order is fixed regardless of registration order, a rewrite chains through both phases so each hook sees the call as rewritten so far, and the first block settles the call with the blocked outcome without running later hooks or the executor — `tool.permitting` therefore always adjudicates the final rewritten call. The loop starts held: queued items from `input` do not run until `runTurn` (idle only, resolves with that turn's outcome; an abort of its optional `signal` aborts the turn and resolves as `aborted`), `continue`, `submit`, `notify` or a successful `steer` releases it. An aborted turn returns its prompt to the inbox and holds. `close()` aborts a running turn with no grace (unsettled tool calls get aborted results and `turn.ended` carries `CLOSED`), reports each detached tool as an aborted `tool.async_ended`, then reaches `closed` and stops the actor. `input.unfinished` (a turn a crashed process left without `turn.ended`) starts the loop in `interrupted`, held. There `continue` resumes the turn when it is resumable — it appended a message, no tool result of its last step stopped it, and with aborted results filled in for unanswered tool calls the history ends with a user or tool message — by closing the unfinished step as `continue` with `CRASHED`, emitting `turn.resumed` and running the next step under the same turn id; `abort`, `runTurn`, any release (`submit`/`notify`/`steer`) and a non-resumable `continue` first close it in one batch (aborted tool results, `step.ended` and `turn.ended` aborted with `CRASHED`) and then act as from idle; `remind`/`cancel` only touch the inbox, `setContext` and the profile setters are rejected, and `close` writes nothing, so the next open finds the same state. The loop holds no persistence. `record.ts` is its durable contract only: `LoopRecord` is the durable subset of emitted events (turn start, resume and end, step, message, context, system prompt and tools settlement, tool start, async tool end with its completion entry, hook failure, llm retry and notice; streaming deltas, hook config, prompt queue events and payload duplicates of `message.appended` are left out), `toLoopRecord` selects one and converts unknown errors to JSON, and `loopProjection` folds records back into the settled `profile`, `messages`, `nextTurnId` (past every recorded turn id, so ids are never reused), turn positions with their outcomes, the `unfinished` turn and `notify` (completion entries of detached tools not yet appended, an aborted `INTERRUPTED` one for a detached tool that never ended; tool entries mark `detached` and `stopTurn` in their meta), the shape `createLoop({ input })` takes.
  - `contract/`: commands, emitted events, hook points and decisions, inbox, turn/step/tool outcomes.
  - `guards.ts`: runtime type guards for values returned by hooks, executors and requesters.
  - `hook/`: registry, per-point runners with decision guards, failure reporting.
  - `tool/`: tool-call machine, tool outcomes and entries, waiting for detached tools.
  - `machine/`: the XState v5 loop machine with turn and step as nested states (`loop.ts`), context and pure reducers (`context.ts`), the LLM request actor that reads the host's requester getter once per step and adds the current profile plus the history content (`request-actor.ts`).
  - `builtin/`: hooks shipped with the loop but registered by the host, e.g. `createMaxStepsHook`.
- `src/history/`: history domain on top of `src/llm/message.ts` — entries with meta, steer merging, tool-result rendering, token estimation.
- `src/store/`: event-sourced logs with one writer and many readers. The top level is platform-free and re-exported by `index.ts`; backends are imported by path. `commit.ts` is shared by the writer, in-process readers and remote clients: `Commit` (`seq`/`time` plus `rewind` and/or `events`) and the line codec (`encodeCommit`/`decodeCommit`/`parseLog`). `replica.ts` has `createReplica` (effective entries, rewind truncation, per-reader `view(projection)`). `writer.ts` holds the `Journal` port and `openWriter` (lazy per-log load, serialized `commit`, `subscribe(from)` with catch-up then live lines, a monotonic clock across logs).
  - `backend/`: one `Journal` per platform: `memory.ts`, `node.ts` (jsonl file per log, torn-tail truncation, writer lock) and `durable-object.ts` (Durable Object SQLite tables with commits split into parts).
- `src/blob/`: object-store-like conversion between files and refs, with caching; platform-free top level re-exported by `index.ts`, backends imported by path. `backend.ts` is the `BlobBackend` port (`has`/`read`/`write` on keys; `read` returns `undefined` when missing). `store.ts` has `openBlobStore`: `put({ bytes, mimeType?, filename? })` encodes one record (length-prefixed JSON header plus bytes) under `data/<ref>` where `ref` is the record's sha256, `get` returns `undefined` for unknown refs and throws `BlobIntegrityError` on a hash mismatch. `cache.ts` has `openBlobCache(backend, namespace)`: JSON values under `cache/<namespace>/<sha256(key)>`, so one backend serves both. Consumers adapt it to their own ports (store-ref in `src/llm/`, the session takes a `BlobStore` directly from its `SessionSpace` container).
  - `backend/`: `memory.ts`, `node.ts` (one file per key, atomic rename) and `durable-object.ts` (SQLite rows split into parts).
- `src/session/`: the session domain, the single implementation of every session and agent operation. State rules: facts are events defined next to their projection (`LoopRecord` + `loopProjection` in `src/loop/record.ts`, `agent.registered` + `sessionProjection` in `model.ts`); runtime state (inbox, running turn, open agents, open source) lives only in live objects; composite state (`SessionStatus`) is computed from both; derived values are never committed back as events. A session always has a store; "no persistence" is the memory journal and blob backend.
  - `model.ts`: `SESSION_LOG`/`AGENT_LOG_PREFIX`, the roster event and `sessionProjection` (roster only, no meta).
  - `session.ts`: `createSession({ id, journal, blobs, source, lastTurn, onLastTurn, onClosed })` returns a plain `Session` whose `agents` is a reactive map of live `Agent`s. The session owns all persistence: an `Agent` binds one loop to its `agents/<id>` log — rehydrated from the `loopProjection` view (the settled profile, messages, `nextTurnId`, the unfinished turn and pending async tool notifications), recorded through `toLoopRecord` in per-microtask batches (`flush` commits the pending batch now), closed when a write fails — and exposes `loop`/`log`/`view`/`since`/`flush`/`close`. `open` registers the agent before its log is written and is idempotent for a live agent; `fork` copies the source's effective records into a new log; `undo` (idle live agents only) rewinds the agent log to a turn start, hands the rewound messages to `loop.setContext` and re-settles any profile value the rewind dropped; orphan agent logs are registered on open. The main agent's last finished turn is derived from its `loopProjection` view and reported through `onLastTurn`; `status()` combines it with the live loops.
  - `space.ts`: the `SessionSpace` port (catalog records with title, metadata, the `lastTurn` index and timestamps, plus a journal and blob container per session) and its memory implementation. The catalog is the only home of title and metadata; `lastTurn` there is a rebuildable index so status is available without loading the main agent log.
- `src/app/`: the outermost instance, usually one per process; the unit tree is an internal detail and no unit node is exposed.
  - `app.ts`: `createApp({ space, scope })` mounts the root unit and returns `App`: a reactive map of live sessions, `create` (startup, resume or fork against the space, deduplicated per id), `update`, `close(sessionId?)` (without an id it unmounts the tree and closes every session), `delete`, `on(type, handler, { once })` plus `wait(type, { match, timeoutMs, signal })` for every event bubbling to the root (`session.created`/`session.deleted`/`session.meta_updated`, forwarded log commits, feature events, each enriched with `sessionId`/`agentId`) and `features`. `on`/`wait` also take a feature as the first argument: `on(feature, type, handler)` narrows the handler to the feature's declared event union, and `'*'` prefix-matches `<name>.` (with `once` honored only on a matching event). There are no Session/Agent-level event handles by design: hosts use `app.on`/`app.wait` with the enriched `sessionId`/`agentId` (a `match` filters one session or agent), feature units use `useOn`/`useWait` on their level node, and loop-local events (e.g. `prompt.submitted`) are reached through `agent.loop.subscribe`/`loop.wait`. It keeps the space's `lastTurn` index current and waits for it on close.
  - `features.ts`: `createFeature(name, { app?, session?, agent? })` defines a feature from optional unit setups, one per level; `createFeature<E>(name, ...)` declares the feature's event contract as a phantom `events` type for the typed `on`/`wait` forms. `app.features.add(feature, { session?, agent?, props? })` registers it where the scope points — the app (no `session`), a live session or a live agent — and returns an async remover, with `delete` and `list` alongside. The scope decides the reach: from the app the app unit mounts once, the session unit in every session and the agent unit in every agent; from a session its session unit and the agent unit in every agent of it; from an agent only its agent unit; later sessions and agents are covered, units above the scope are skipped, and a feature without a unit at or below the scope is rejected. Each domain object has its own reactive set, created lazily and dropped with the object. Registration is host state, never persisted.
  - `units.ts`: `AppUnit`/`SessionUnit`/`AgentUnit` provide their domain object, contribute `EventContext`, forward log commits from `since` as unit events, fire `agent.opened`/`agent.closed`, pass registrations down as the `SessionFeatures`/`AgentFeatures` collections, and mirror both the live domain children (keyed by object identity, so a reopened agent remounts) and the feature units of their level (registrations folded root to node, then the instance's own; the nearest registration of a name wins, same feature updates props, a different feature remounts). Feature units are mounted attached (`UnitNode` `host`): their `useOn`, `provide` and `useContribute` register on the level node while their cleanup stays their own, so a session unit hears every event bubbling from the agents of that session and from its sibling feature units, and what it provides is visible to them. Mirroring mounts synchronously in the reactive trigger (`useMounted` covers the initial children), so a session or agent and its feature units are mounted before `app.create` or `session.open` resolves; unmounting is asynchronous and the feature removers wait for it. `useApp`/`useSession`/`useAgent` are sugar over the instance tokens: an agent unit sees all three, a session unit session and app. The loop hook helpers, one per hook point (`useTurnStarting`/`useMessageAppending`/`useStepStarting`/`useToolBatchStarting`/`useToolStarting`/`useToolPermitting`/`useToolEnding`/`useStepStopping`/`useStepContinuing`, each `(hook, { id?, onFailure? })`), add the hook to the agent's loop and remove it in `onScopeDispose`, which runs synchronously when the unit starts unmounting (feature removed, agent closed, session or app closed), so a remounted feature reusing the hook id never collides with the outgoing one. `useRequester()` is sugar for `useAgent().loop.requester`. `useToolHandler(definition)` or `useToolHandler(name, handler)` registers on `loop.executor` when that object is a tool registry and removes the registration in `onScopeDispose`. `src/utils/wait.ts` has the one `waitEvent(listen, { match, timeoutMs, signal })` used for both loop and unit events.
- `src/tool/`: tool contract and the host-held executor. `contract.ts` holds `ToolResult`, `ToolExecuteInput`, `ToolExecutor` (`execute` only — what the loop calls) and `ToolExecutorHost` (`register` / `invalidate` / `restore`). `executor.ts` is `createToolExecutor`: one slot per name, an in-flight call keeps the handler it resolved, and `execute` resolves the slot, returns an in-band error for an unknown or invalidated name, runs the handler, then truncates text to `policy.maxResultChars`. `define.ts` is `defineTool`, which parses arguments with a `ToolSchema` before the typed `execute`. `schema.ts` is `zodSchema`. `createLoop` stores the object it was given on `loop.executor`.
- `src/utils/abort.ts`: abort scopes shared by the machines.
- `src/utils/hash.ts`: `sha256Hex` on `crypto.subtle`, shared by `src/blob/` and the store-ref resolver.
- `src/utils/error.ts`: `errorCode` for errors with a `code`; `src/utils/durable-object.ts`: the `DurableObjectSql` storage shape shared by the store and blob backends.
- `src/node/`: Node-only host glue: env-based endpoints, a fetch with headers timeout and proxy.
- `src/image/`: Node-only image intake (compress, crop, dimensions), independent of `src/llm/`.
- `test/`, `example/generate.ts`, `example/loop.ts` (re-act loop demo with a fake requester), `example/session.ts` (session demo with a subagent tool, fake requester).

## Current Principles

- The caller guarantees the semantic invariants of the history; violations fail as syntax errors and are never repaired by the core.
- The llm layer adapts layout and representation differences between protocols and models.
- Tolerance for invalid input is opt-in and belongs in a `MessageResolver`, not in encode.
- Configuration parsing and environment variables stay with the host; the layer receives resolved values.
- `src/llm/` is platform-free: only web globals (`fetch`, `crypto.subtle`, `performance`, `atob`/`btoa`), no `node:*`, `Buffer`, `process` or `undici`; Node-specific code goes in `src/node/`.
- A protocol flag must be executed by the pipeline that declares it.
- Keep English and Chinese docs in sync when either changes.

## Agent Rules

- Preserve user changes. Do not revert unrelated dirty or untracked files.
- Write no code comments unless the user asks for them; comments are always in English.
