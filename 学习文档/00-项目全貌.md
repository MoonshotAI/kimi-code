# 00 · 项目全貌（架构深度解析）

> 时效基线：基于 commit `d4e0ad4b2`（2026-08）。行号会漂移，以路径为准。
> 本文以 **VS Code 插件为主入口**梳理整套架构：入口与启动序列（第一节）、模块依赖关系（第二节）、配置与数据加载（第三节）、模块关系总图（第四节）。插件 UI 层的代码细节见 `02`，引擎内部循环见 `04`，CLI/Web 宿主见 `05`。

## 〇、一分钟心智模型

Kimi Code 是"**一套引擎、多个宿主**"的系统：`packages/agent-core-v2` 是引擎，VS Code 插件 / 终端 CLI / 浏览器 Web 只是三种宿主外壳。VS Code 插件的特殊性在于：**引擎就跑在扩展宿主进程里**——没有子进程、没有本地服务器，插件激活的那一刻引擎就已经启动，之后的一切（配置、登录、会话）都是往这个进程内引擎里填数据。

理解本文的关键线索是三个"什么时候"：

1. **引擎什么时候启动** —— 插件 `activate()` 期间，同步、急切（eager）；
2. **配置/登录什么时候加载** —— 引擎启动即读盘（`config.toml`），登录是懒的（用户点登录才走 device code flow）；
3. **会话什么时候创建** —— 用户发出第一条消息时，才按 workDir 物化 workspace 与 session 两层作用域。

## 一、入口在哪里，启动后做了什么

入口不是一个函数，而是一条链：**用户点开侧边栏 → 扩展激活 → 引擎引导 → webview 初始化 → 首条消息时创建会话**。下面按时间顺序分六个阶段展开，每一阶段都可独立下断点观察（调试方法见 `03`）。

### 阶段 A：扩展激活（extension host 进程，同步执行）

插件的 `package.json` 里 `activationEvents: []`，激活靠 `contributes.views` 声明的 `kimi.webview` view 隐式触发（VS Code 自动生成 `onView:kimi.webview`）。所以**真正的入口事件是"用户第一次点开 Kimi 侧边栏"**。

`activate()`（`apps/vscode/src/extension.ts:19`）按顺序做：

1. 创建 "Kimi Code" 输出通道（`src/extension.ts:20`）；
2. `new KimiWebviewProvider(...)`（`src/extension.ts:24`）——其构造函数（`src/KimiWebviewProvider.ts:29`）立刻 `new BridgeHandler(...)`，而 `BridgeHandler` 构造函数（`src/bridge-handler.ts:42`）立刻 `new KimiRuntime(...)`。**引擎引导就发生在这一行**，不在任何 lazy 边界后面；
3. `KimiRuntime` 构造函数（`src/runtime/kimi-runtime.ts:61`）第 65 行做引擎选择：`options.useAgentCoreV1 ? createKimiHarness : createKimiHarnessV2`（默认 v2），66-76 行传入 `{ homeDir, identity: { productName: "kimi-code-vscode", ... }, uiMode: "vscode" }` 调用之；
4. 若引擎启动抛错，`src/bridge-handler.ts:51-61` 不做静默降级——直接抛出并附"可回退 v1"提示；
5. 回到 `activate()`：检查登录态（`src/extension.ts:34`）、注册 `kimi-baseline` 虚拟文档 provider（`src/extension.ts:39-53`）、注册设置变更广播与 view provider（`src/extension.ts:55-70`）、注册 10 个命令（`src/extension.ts:88-131`）、后台发现旧版 `~/.kimi` 数据（`src/extension.ts:133`）；
6. `activate()` 返回。**此刻引擎的 App 作用域已完整物化**，但还没有任何会话。

### 阶段 B：SDK 层引导（`SDKRpcClientV2` 构造函数）

`createKimiHarnessV2()`（`packages/node-sdk/src/sdk-rpc-client-v2.ts:2978`）= `new SDKRpcClientV2(options)` + `new KimiHarness(rpc, {...})`。前者是引擎引导主体，构造函数（`packages/node-sdk/src/sdk-rpc-client-v2.ts:467`）严格按以下顺序执行（表内 `:NNN` 均指 `sdk-rpc-client-v2.ts` 行号）：

| # | 步骤 | 位置 | 落盘效果 |
|---|---|---|---|

| 2 | 解析数据根 `resolveKimiHome`：`homeDir ?? KIMI_CODE_HOME ?? ~/.kimi-code` | `:471` → `packages/agent-core-v2/src/app/bootstrap/bootstrap.ts:160` | — |

| 5 | 创建 `KimiAuthFacade`（登录门面，包装 oauth 包的 `KimiOAuthToolkit`） | `:478`，实现在 `packages/node-sdk/src/auth.ts:110` | — |

### 阶段 C：引擎 App 作用域物化（`bootstrap()`）

`bootstrap()`（`packages/agent-core-v2/src/app/bootstrap/bootstrap.ts:135`）做两件事：

1. 组装 **seeds**（作用域种子）：`bootstrapSeed`（环境信息：cwd/platform/身份/请求头）、`storageSeed`（`IFileSystemStorageService`——一切持久化的单一底座，`persistence/backends/node-fs/fileStorageService.ts`，带 chokidar watch）、`skillSeed`（skill 发现）；
2. `createAppScope(...)` → `Scope.createApp`（`src/_base/di/scope.ts:209`）：从**模块加载时**通过 `registerScopedService(...)` 注册的全局登记表里，取出所有 App 级服务，以**一个 `provideAll` 事务**注册并 **eager 激活**——即"作用域一存在就构造"，每个服务构造函数里的副作用（初始文件加载、watch 注册）立即发生。任何 App 服务构造抛错 → 整个作用域销毁、`bootstrap()` 抛错 → 插件激活报错。**没有半启动状态**。

`BootstrapService`（`src/app/bootstrap/bootstrapService.ts:35-60`）同时定下磁盘布局：`<home>` 下 `sessions/`、`blobs/`、`store/`、`cache/`、`logs/`、`credentials/` 各司其职（完整表见 第三节）。

### 阶段 D：配置初载与模型就绪（激活期间后台执行）

- `ConfigService` 构造（`src/app/config/configService.ts:314`）：`ready = migrate → load('load')`（`:327-330`）读取并校验 `config.toml`（管线细节见 第三节）；随后 `documentStore.watch` 盯住该文件（`:331-335`），外部改动 150ms 防抖后自动热重载；
- `KosongConfigService.initialize`（`src/app/kosongConfig/kosongConfigService.ts:45-86`）：等 `config.ready`，然后 `providers.loadAll(config.get('providers'))` + `models.loadAll(config.get('models'))`——`modelReady` 至此 resolve。配置段与服务之间是**双向同步**：改配置段 → `loadAll` 重载；服务内变更 → 写回 config.toml。

### 阶段 E：webview 启动（用户点开侧边栏之后）

- 宿主侧：`KimiWebviewProvider.resolveWebviewView`（`src/KimiWebviewProvider.ts:51`）给 webview 发 ID（`sidebar_<uuid>`）、注入 HTML（CSP+nonce，`setupWebview`，`:97`），并把 `webview.onDidReceiveMessage` 接到 `BridgeHandler.handle`（`:106-109`）——这就是 postMessage RPC 的宿主端入口；
- webview 侧：React 应用启动后 `useAppInit`（`webview-ui/src/hooks/useAppInit.ts:54`）依次：`checkWorkspace` → 并行拉 `getExtensionConfig` / `getMCPServers` / `getSlashCommands`（`:91-95`）→ 并行 `checkLoginStatus` / `getModels`（`:104`）→ `resolveAppView`（`:28`）路由到 **登录页 / 状态页（无 workspace、无模型、出错）/ 主界面**；
- 注意：到此为止**还没有任何会话被创建**，引擎里只有 App 作用域。

### 阶段 F：第一条消息 → 会话创建链（真正的"懒加载"）

用户发送第一条消息时，`streamChat`（`src/handlers/chat.handler.ts:74`）先做前置（workDir 校验、可选 autosave、`getOrCreateSession`、按需 setModel/setThinking/setPlanMode，`:104-125`），然后进入会话创建链——**这是整个系统里最重要的一条路径**：

链上关键入口的完整路径（配合上图，断点就下在这些函数上）：

- 插件侧：`apps/vscode/src/runtime/kimi-runtime.ts` 的 `openSession` → `apps/vscode/src/handlers/chat.handler.ts:74` 的 `streamChat`
- SDK 侧：`packages/node-sdk/src/kimi-harness.ts:128` 的 `createSession` → `packages/node-sdk/src/sdk-rpc-client-v2.ts:1302` 的 `doCreateSession`
- 引擎侧：`packages/agent-core-v2/src/app/sessionManager/sessionManagerService.ts:62` 的 `SessionManager.create` → `packages/agent-core-v2/src/app/workspace/workspaceService.ts:54` 的 `createOrTouch`（workspace id 生成在 `packages/agent-core-v2/src/_base/utils/workdir-slug.ts:17`）→ `packages/agent-core-v2/src/workspace/sessionLifecycle/sessionLifecycleService.ts:184` 的 `create`

几个值得记住的细节：

- **workspace 层是按需物化的**：第一个会话创建时才为该 workDir 建 workspace handler（含 MCP 连接、skill 扫描、AGENTS.md 读取）；同一 workspace 的后续会话共享它；
- **preflight 兜底**：`materializeSession` 会等 `config.ready`、`models.ready`、`providers.ready`，所以即使激活时配置还在后台加载，会话创建也不会读到半初始化状态；
- **失败即回滚**：会话创建链任何一步失败都会清 DI 作用域、删磁盘目录，不留僵尸会话；
- 事件回流：引擎事件经 `wireSession` 接线 → SDK `Session.onEvent`（`packages/node-sdk/src/session.ts:122`）→ 插件 `SessionRuntime` 唯一订阅 → `event-adapter` 转 UI 事件 → webview 渲染（详见 `02` 的"一条消息的完整旅程"）。

### 补充：登录发生在什么时候

登录也是懒的：`useAppInit` 发现未登录 → 登录页 → `auth.handler.ts` 调 `harness.auth.login` → `KimiAuthFacade` 走 **device code flow**（`packages/oauth`），成功后把托管的 `[providers.kimi_code]` OAuth 引用与模型条目**写进 config.toml**，令牌存 `<home>/credentials/*.json`；模型列表因此非空，`no-models` 状态解除。此后每次模型请求经 `IOAuthService` 惰性取/刷新令牌（`ensureFresh`，跨进程锁防并发刷新）。

## 二、主要模块之间的依赖关系

### 2.1 依赖 = 进程内调用栈（自上而下五层）

VS Code 插件场景下，"模块依赖"可以直接从一条断点调用栈读出来。从 UI 到 LLM 共五层，**每层只能调用紧邻下一层**（有契约校验，无跨层捷径）：

```
L5 宿主 UI      apps/vscode（webview + extension host）
                职责：交互、渲染、把用户意图翻译成 SDK 调用
                    │ 唯一依赖：@moonshot-ai/kimi-code-sdk
                    ▼
L4 SDK 门面     packages/node-sdk（KimiHarness / Session / KimiAuthFacade）
                职责：稳定的宿主 API；v1/v2 引擎差异在这里抹平（src/v2/ 纯映射层）
                    │ 进程内调用
                    ▼
L3 契约层       packages/klient（facade + zod contract + memory transport）
                职责：global.* / session(id).* / agent(id).* 三段 facade；
                      每次调用过契约校验 + JSON 往返（与网络传输同一纪律）
                    │ memory transport
                    ▼
L2 引擎         packages/agent-core-v2（DI × Scope）
                职责：agent loop、工具、权限、上下文、会话生命周期、持久化
                    │ 内嵌（无独立包依赖）
                    ▼
L1 模型抽象     agent-core-v2/src/kosong/（内嵌版）
                职责：provider/protocol 适配 → Anthropic / OpenAI / Gemini / Kimi 的 HTTPS API
```

两个结构性细节：

- **`engineAccessor` 逃生舱**（`packages/node-sdk/src/sdk-rpc-client-v2.ts:600`）：klient facade 覆盖不到的面（显式 sessionId、resume/fork、workspace 技能列表等），node-sdk 通过 `app.accessor` 直接读 App 级服务。这是**受控的破例**：仅限 App 作用域、仅进程内、每次使用需注明替代了哪个 facade 方法；
- **v1 回退路径**：`kimi.useAgentCoreV1` 时 L3/L2 换成 `SDKRpcClient` 直接 `new KimiCore`（`packages/node-sdk/src/sdk-rpc-client.ts:78`）+ `packages/agent-core` + `packages/kosong` + `packages/kaos`。对外 API 形状不变（L4 保证）。

### 2.2 包级依赖表

```
L4 宿主    apps/vscode ──────────► node-sdk, migration-legacy
           apps/kimi-code (CLI) ──► node-sdk, kap-server, acp-server, acp-adapter,
                                    pi-tui, oauth, minidb, telemetry, …
           apps/kimi-inspect ─────► agent-core-v2, transcript
L3 门面    node-sdk ──► agent-core(v1), agent-core-v2, klient, kosong, oauth, kaos
           kap-server ─► agent-core-v2, oauth, minidb, transcript（REST+WS 替代 klient）
           klient ─────► agent-core-v2
           acp-server ─► agent-core-v2, klient, protocol
L2 引擎    agent-core-v2 ─► oauth, protocol, minidb, tree-sitter-bash（内嵌 kosong）
           agent-core (v1) ─► kosong, kaos, oauth, protocol
L1 叶子    kosong · kaos · transcript · protocol · minidb · oauth · telemetry
           pi-tui · tree-sitter-bash · migration-legacy
```

注意两点：`apps/kimi-code` 与 `node-sdk` 把引擎包声明为 devDependencies，因为构建时 tsdown 整体打进产物，代码层面是真实依赖；**agent-core-v2 不依赖 packages/kosong**（内嵌了自己的演化版）。

### 2.3 旁路模块（不在主调用栈上）

| 包 | 与主线的关系 |
|---|---|
| `packages/oauth` | 被 node-sdk（SDK 侧登录门面）与引擎（`IOAuthService`，请求时取令牌）**双端使用**，通过 `<home>/credentials/` 共享令牌文件 |
| `packages/migration-legacy` | 插件/CLI 启动后后台跑：旧 `~/.kimi` → `~/.kimi-code` 迁移 |
| `packages/agent-core` (v1) | 仅回退路径；其 `src/loop/` 仍是理解 agent loop 的最佳简读本 |
| `packages/transcript` | 不在插件路径上；kap-server/kimi-inspect 用它把 `wire.jsonl` 投影成 UI 数据层 |

### 2.4 三种宿主的对照（引擎接入方式是唯一差异）

| 宿主 | 引擎进程位置 | 契约层 | UI |
|---|---|---|---|
| VS Code 插件 | 扩展宿主进程内 | node-sdk → klient **memory** | React webview（postMessage） |
| CLI / TUI（`kimi`） | CLI 进程内 | 直接组装（`apps/kimi-code/src/cli/experimental-v2.ts`、`src/cli/v2/`） | pi-tui 终端 UI |
| Web（`kimi web`） | server 进程内 | **kap-server** REST+WS（替代 klient） | 预构建 `dist-web`（源码在外部 code-app 仓库） |
| ACP（`kimi acp --native`） | ACP 进程内 | acp-server → klient memory | 无（外部编辑器） |

## 三、配置和数据的加载流程

### 3.1 磁盘全景：`<home>`（默认 `~/.kimi-code`）目录树

```
~/.kimi-code/
├── config.toml                  ← 全部引擎配置（TOML，分节 schema）
├── workspaces.json              ← workspace 目录（id ↔ root 映射与时间戳）
├── session_index.jsonl          ← 追加式会话索引日志（create/delete 记录）
├── mcp.json                     ← 用户级 MCP 服务器（SDK 侧写，引擎只读）
├── credentials/                 ← OAuth 令牌（0700 目录 / 0600 文件）
│   ├── <name>.json              ← Kimi 登录令牌
│   └── mcp/<key>-*.json         ← 各 MCP 服务器的 OAuth 凭据
├── workspace-trust/<wdKey>      ← 每个 workspace 的信任标记 JSON
├── sessions/<wsId>/<sessionId>/ ← 每会话一目录
│   ├── state.json               ← 会话元数据（标题、agents、时间戳…）
│   ├── agents/<agentId>/wire.jsonl  ← 每 agent 追加式事件日志（重放/恢复源）
│   ├── agents/<agentId>/{tasks,cron}/  ← 子代理任务与定时状态
│   └── logs/kimi-code.log       ← 会话级日志
├── blobs/ · store/ · cache/query-store/   ← 大对象 / 杂项 / minidb 会话索引镜像
├── logs/kimi-code.log           ← 全局日志
└── server/instances/<id>.json   ← 运行中 kap-server 实例注册（kimi-inspect 发现用）
```

项目侧（不在 home 下）：`<git根>/.mcp.json`、`<cwd>/.kimi-code/mcp.json`（项目级 MCP，受 trust 门控）、`<项目>/.kimi-code/local.toml`（`workspace.additional_dir`）、各级 `AGENTS.md`。

### 3.2 config.toml 的一生

**创建（懒）**：`ensureKimiHome` 只建目录；config.toml 由宿主显式调 `harness.ensureConfigFile()` 时才创建——`open(path, 'wx', 0o600)` 写入一段纯注释模板（`packages/agent-core/src/config/toml.ts:56`），哲学是"空文件让内置默认值生效，登录再填托管段"。

**读取管线**（`ConfigService.load`，`src/app/config/configService.ts:525`）：

```
smol-toml 解析 → snake_case→camelCase 逐节变换 → 收集废弃键
→ 逐节 zod 校验（失败转 diagnostics，不炸进程）→ 填默认值
→ 应用环境变量绑定/覆盖（见下）
```

**热更新**：构造时 `documentStore.watch`（chokidar，150ms 防抖）盯住文件，外部编辑自动 `reload`。

**写入**：`set`/`replace`/`replaceSections` 走原子文档存储（重读 → rebase → 剥离环境变量派生值 → 原子写）。**污染阻断**：文件解析失败会把服务标记为 tainted，阻止任何写回（`assertPersistable`，`packages/agent-core-v2/src/app/config/configService.ts:406` 起的各写入口），防止把坏配置"修复"成空配置。

**已注册的节**（节选）：`providers` + `defaultProvider`、`models` + `defaultModel`、`thinking`、`modelCatalog`、`mcp`、`experimental`（flags）、`permission`、`defaultPermissionMode`、`tools`、`loopControl`、`hooks`、`cron`、`extraSkillDirs`、`extraAgentDirs`、`defaultPlanMode`、`image`、`subagent` + `secondaryModel`。

### 3.3 配置分层与优先级（谁覆盖谁）

```
环境变量绑定（最高，且持久化时被剥离，不落盘）
  └─ 全局 <home>/config.toml            ← IConfigService 管理
       （独立体系，不进 IConfigService：）
       ├─ 项目 <project>/.kimi-code/local.toml   ← 仅 workspace.additional_dir；
       │                                            WorkspaceDirsService 独立读取 + watch
       └─ MCP 三层合并（低→高）：
          <home>/mcp.json  <  <git根>/.mcp.json  <  <cwd>/.kimi-code/mcp.json
          （packages/agent-core-v2/src/workspace/workspaceMcpConfig/internal/config-loader.ts:41
            合并 {...user, ...projectRoot, ...project}；
            项目两层仅在 workspace 受信后参与——trust 标记在 <home>/workspace-trust/）
```

值得注意的环境变量绑定：`KIMI_MODEL_API_KEY`/`KIMI_MODEL_BASE_URL`/`KIMI_MODEL_PROVIDER_TYPE` 会合成一个伪 provider `__kimi_env__`；`KIMI_MCP_STARTUP_TIMEOUT_MS` 等映射到对应节。

### 3.4 模型与 provider 从哪来

**没有内置模型清单**——`IModelService` 只装 config.toml 里 `[models]` 的记录。来源三种：

1. **托管登录**：device code flow 成功后 oauth 包把 `kimi_code` provider + 模型条目写进 config.toml（普通用户的主路径）；
2. **models.dev 导入**：`IModelsDevImportService`（`packages/agent-core-v2/src/app/kosongConfig/modelsDevImportService.ts:44`）从上游目录 HTTP 拉取；
3. **手工编辑** config.toml。

config → 可运行模型的解析在 `ModelCatalog.buildModel`（`packages/agent-core-v2/src/kosong/model/catalogService.ts:255`）：provider 解析（含"从 baseUrl 合成 provider"的兜底）→ protocol 选择 → 鉴权构造 → 能力并集 → 每 protocol 的 providerOptions。请求经内嵌 kosong 的 provider 基座（`packages/agent-core-v2/src/kosong/provider/bases/`：anthropic / openai / google-genai + `providers/kimi`）发出。

### 3.5 鉴权链（一次模型请求怎么拿到令牌）

```
agent loop 发起请求
  → ModelCatalog.buildAuthProvider（catalogService.ts:493）
  → IModelOAuthTokens.getAccessToken（oauthTokenAdapter.ts:26）
    （完整路径：packages/agent-core-v2/src/kosong/model/catalogService.ts 与
      packages/agent-core-v2/src/app/kosongConfig/oauthTokenAdapter.ts）
  → IOAuthService.resolveTokenProvider → KimiOAuthToolkit（packages/oauth）
  → FileTokenStorage 读 <home>/credentials/<name>.json（0600）
  → OAuthManager.ensureFresh：过期阈值内直接用；过期则惰性刷新
    （in-flight 合并 + 跨进程文件锁防并发刷新；无后台循环）
  → 令牌为空 ⇒ AUTH_LOGIN_REQUIRED（UI 引导登录）
```

### 3.6 会话数据怎么被读回（resume 的逆过程）

`session_index.jsonl`（追加日志）记录每个会话的 `{sessionId, sessionDir, workDir}`；`ISessionIndex` 从中建索引，会话摘要读 `sessions/<ws>/<id>/state.json`（可选 minidb 读模型加速，flag `persistence_minidb_readmodel`）。resume 时按 `summary.workspaceId` 物化 workspace，再折叠 `agents/<id>/wire.jsonl`（首条是 `metadata` 记录）重建 agent 状态——fork 则按 turn 切片重写 wire 日志。

### 3.7 加载时机总表（把 第一节 和 第三节 串起来）

| 时机 | 发生的读写 |
|---|---|
| 插件激活（同步） | 建 `<home>`（0700）；App 作用域服务物化；`config.toml` 首读+watch 注册（config.toml **不存在也不报错**，空配置+默认值运行） |
| 激活后（后台 Promise） | 配置校验/默认值/env 绑定完成（`configReady`）；providers/models 装载（`modelReady`） |
| 打开侧边栏 | webview 拉取扩展配置、MCP 列表、斜杠命令、登录态、模型列表（纯读） |
| 用户点登录 | device code flow → 写 `config.toml` 托管段 + `credentials/*.json` |
| 第一条消息 | 建/读 `workspaces.json`；workspace 层物化（AGENTS.md、skills、MCP 三层合并、git、trust）；建 `sessions/<ws>/<id>/`；追加 `session_index.jsonl`；此后每 turn 追加 `wire.jsonl` |
| 关闭会话/插件 | 逐层 drain（追加日志退休、索引镜像、日志关闭）后销毁作用域——保证宿主随后删目录也不竞态 |
