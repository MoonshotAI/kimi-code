# 06 · 支撑包详解（深度版）

> 时效基线：基于 commit `d4e0ad4b2`（2026-08）。每包讲"真实机制 + 关键类 + 谁在用"，比口号深一层、比通读浅一层——读完能决定要不要深入，深入时知道从哪个文件进。v1 引擎（`packages/agent-core`）在文末。

## 1. packages/kosong — LLM 抽象层（v1 栈使用）

入口 `src/index.ts`：`generate()`、`ChatProvider`、能力系统、错误分类学、消息工具函数。**具体 provider 适配器故意不进根 barrel**（`packages/kosong/src/index.ts:88` 注释：它们的 SDK 类型图会污染下游声明文件），要从 `@moonshot-ai/kosong/providers/kimi` 等子路径导入。

- **`generate(provider, systemPrompt, tools, history, callbacks?, options?)`**（`packages/kosong/src/generate.ts:87`）不是简单透传，是**流式合并循环**：维护 `pendingPart` 与 `toolCallIndexMap`，把各家的流式索引（OpenAI 的 `index`、Responses 的 `item_id`）路由到 `message.toolCalls` 的正确位置；`onToolCall` 回调**故意推迟到流结束**才触发（`packages/kosong/src/generate.ts:56-63` 注释：并行工具调用的参数增量会交错，提前回调顺序是错的）；空响应与"只有 think 的响应"都抛 `APIEmptyResponseError`（`:219-247`）。
- **`Tool.deferred` 标记**（`packages/kosong/src/tool.ts:8`）是渐进披露的关键点：generate 会在调 provider 前把 deferred 工具从顶层 `tools[]` 剥掉（`packages/kosong/src/generate.ts:120-125`），消息级的工具声明不破坏 prompt 缓存——标记永不上线。
- **能力系统是纯静态表**：`getModelCapability`（`packages/kosong/src/providers/index.ts:54`）不实例化 provider；Kimi 返回 `UNKNOWN_CAPABILITY`（带 Symbol 标记，`packages/kosong/src/capability.ts:43`，能力来自宿主目录）。
- provider 家族（`ProviderConfig` 判别联合，`packages/kosong/src/providers/index.ts:15`）：`anthropic`（Messages API）、`openai`（legacy chat-completions）、`openai_responses`、`kimi`、`google-genai`、`vertexai`（复用 genai 适配器）。冷知识：**KimiChatProvider 用的是 OpenAI SDK 打 chat-completions 线协议**（`packages/kosong/src/providers/kimi.ts:408`）。
- v1 引擎的消费姿势见 `packages/agent-core/src/agent/turn/kosong-llm.ts:129`（每请求临时 clone 上限 tokens、四个 TTFT 埋点钩子）。v2 引擎不用它（内嵌 `agent-core-v2/src/kosong/`）。

## 2. packages/kaos — 执行环境抽象（v1 栈使用）

"Kimi Agent Operating System"：刻意镜像 Python 的 `os`/`pathlib`（连 `errors: 'strict'|'replace'|'ignore'`、`StatResult` 形状都对齐）。

- **`Kaos` 接口**（`packages/kaos/src/kaos.ts:12`）：路径/文件/目录/进程四组操作；`withCwd/withEnv` 返回叠加了环境的**新 Kaos**（env 在 spawn 时才读）；
- **`KaosProcess`**（`packages/kaos/src/process.ts:10`）刻意最小（stdin/stdout/stderr/pid/wait/kill/dispose）——注释明说"可由本地子进程、SSH 会话或容器运行时支撑"；
- **环境探测是纯函数**（`detectEnvironment(deps)`，`packages/kaos/src/environment.ts:75`，探针注入可测）：POSIX 依序探 `/bin/bash`→`/usr/bin/bash`→`/usr/local/bin/bash` 回退 `/bin/sh`；Windows 找 Git Bash（`KIMI_SHELL_PATH` 覆盖→PATH 上的 git.exe→`git --exec-path`），找不到抛带候选路径列表的 `KaosShellNotFoundError`；
- **两个实现**：`LocalKaos`（`packages/kaos/src/local.ts:188`）与 `SSHKaos`（`packages/kaos/src/ssh.ts:435`，ssh2 库：文件走 SFTP、进程走 exec 通道，SFTP 状态码映射成四类错误 `:77-101`）。
- 消费者：v1 引擎、acp-adapter（`AcpKaos` 每会话沙箱视图，`packages/acp-adapter/src/kaos-acp.ts:42`）、node-sdk。

## 3. packages/transcript — 同构 transcript 数据层（L1–L4）

自述："agent 粒度 L1 存储、幂等 L2 操作、`off/turn/block/delta` L3 订阅粒度、无框架 L4 视图注册、turn 游标分页；纯 TS 浏览器安全，transcript 契约类型的唯一所有者"（其 AGENTS.md）。**kap-server 的 transcript REST/WS 面和 kimi-inspect 都建在它上面**。

- **L1 存储**：`TranscriptStore`（`packages/transcript/src/store/transcriptStore.ts:16`，每会话一张 `AgentTranscript` + agent 花名册）；`AgentTranscript.apply(ops)`（`packages/transcript/src/store/agentTranscript.ts:49`）是**唯一收敛路径**——纯折叠、跳过 no-op、append 落不了位时记 `gap` 信号（下游据此触发重同步）；
- **L2 操作与 seq**：14 种 `TranscriptOperation`（`packages/transcript/src/ops/operation.ts:131`，upsert 全部按 id 内容寻址、天然幂等）；**seq 契约**（`packages/transcript/src/contract/schema.ts:451`）——seq 按**派发的 op 批**递增（不是按 op），`reset`/REST 响应上的 seq 是水位线，补发 = `seq > since_seq` 的批次（`GET .../transcript/ops?since_seq=N` 或订阅字段 `transcript_since`）；
- **L3 粒度**：`off < turn < block < delta`（`packages/transcript/src/granularity/grade.ts:3`）；**只有升级粒度才要求 reset**（降级把细操作流进粗存储不需重来，`needsResetOnTransition`，`:22`）；`filterOpsForGrade` 降档、`redactSnapshotForGrade` 脱敏快照；
- **L4 视图注册**：按工具名/turn 来源/marker 键三张表，`C` 由宿主指定（React 组件或别的什么）——框架无关；
- **分页**：游标是 **turn id**，整 turn 分段取（`packages/transcript/src/pagination/paginate.ts:15`）；
- **冷重建**：两级折叠 `wire.jsonl`（`src/history/groupTurns.ts` + `foldFacts.ts`）；已知限制：live 投影才有的细节（usage/finishReason/时延）不回填。

## 4. packages/minidb — 嵌入式文档库（kap-server 搜索与 v2 会话索引镜像的后端）

自述 "Redis meets SQLite"：纯 Node 零原生依赖；内存 O(1) KV + AOF 式 WAL（组提交、`always|everysec|no` 三档 fsync，`packages/minidb/src/wal.ts:30`）+ 快照/压缩；TTL；跳表二级/复合/时间索引；全文倒排；可选 RESP TCP；可选分片 Cluster。

- **`MiniDb`**（`packages/minidb/src/mini-db.ts:76`）：一个类由十余个 facet（write/read/wal-group/text-registry/generation/内存守卫/维护/备份/统计）驱动共享状态——"字段非私有（包内可见）"是有意设计；
- **比内存大**：`Store` 的 `ValueRef` 有 `memory|disk` 两态（`packages/minidb/src/store.ts:16`），disk 模式内存只留指针、同步定位读（`src/value-reader.ts`）；**全文索引**（`packages/minidb/src/text-index/index.ts:82`）只有字典+doc 长度+key↔docID 在内存，postings 在磁盘，写入只进内存 delta+tombstone（零盘 IO），读时合并打 TF-IDF，分词 = Latin 词 + CJK 一元/二元（无词典）；
- **写锁**（`packages/minidb/src/lockfile.ts:74`）：O_EXCL 创建独占；**"仅当属主 PID 已死才算 stale，绝不因为旧"**；接管走 bid/watch-file 协议（自适应停顿 60ms–2s）；抢不到锁的实例以只读打开并从 WAL 追赶；
- **索引世代**（`src/generation.ts`）：`generations/g-NNNNNN/` + `CURRENT`，构建写临时目录后**原子改名发布**；加载 = 读已发布世代 + WAL 增量重放（不重新解码/重分词）；损坏回退全量恢复，语料级全文重建放后台维护任务；
- **分片**（`packages/minidb/src/cluster/index.ts:69` `ClusterDb`）：哈希分片多目录多进程并发读写；跨片 2pc 显式预留未实现；**全文构建 worker**（`packages/minidb/src/worker/text-build.ts:148`，`--experimental-transform-types` 直跑 TS，有界聚合 + 外部归并排序；worker 缺失时同核心内联回退）。

## 5. packages/oauth — 登录与令牌

- **`KimiOAuthToolkit`**（`packages/oauth/src/toolkit.ts:110`）：按 OAuth key 管一组 `OAuthManager`；`login()`（`:159`）成功后顺带把托管 provider 配置写进 config.toml；`tokenProvider()`（`:271`）返回惰性 `getAccessToken({force})`——模型请求的取令牌入口；
- **device flow 状态机**（`packages/oauth/src/oauth-manager.ts:406` 的 `login()`）：15 分钟总预算；RFC 8628 的 `slow_down` 永久 +5s；`expired_token` 换新码重来；`denied` 抛错。HTTP 层是三个无状态 POST 端点（`packages/oauth/src/oauth.ts:1-11` 头注释）；
- **刷新**（`ensureFresh`，`:254`）：阈值 = `max(300s, 有效期×0.5)`；in-flight 合并（force 只搭 force 的车）；**跨进程文件锁**（`proper-lockfile`，重试 120×500ms-1s，**拿不到锁就失败而不是无锁刷新**）；锁内重读存储——**对端进程可能已轮换令牌**，拿对端的用；401 且对端没动过 → 写 revoked 墓碑防止新进程反复试死码；
- **`FileTokenStorage`**（`packages/oauth/src/storage.ts:41`）：目录 0700、文件 0600，tmp（带 pid+随机后缀）→ fsync → rename 原子写；`basename` 防路径穿越。

## 6. packages/protocol — 守护进程的线上 schema

单一 barrel：envelope（`{code, msg, data, request_id}`，`src/envelope.ts:3`）、**分段错误码**（`src/error-codes.ts` 头注释：0 成功 / 4xxxx 客户端 / 5xxxx 守护进程 / 6xxxx 工具运行时 / 7xxxx LLM 透传 / 8xxxx MCP 透传 / 9xxxx 预留）、分页（`before_id`/`after_id` 互斥校验，`packages/protocol/src/pagination.ts:4`）、**ws-control v2**（`packages/protocol/src/ws-control.ts:18`）：游标 = `{seq, epoch}`，seq 是**持久**的日志偏移（daemon 重启不回退）、volatile 事件不推进 seq、文本增量带 `offset` 字段做幂等对齐、`resync_required` 区分 epoch 变更。写对接 `kimi web` 的客户端，以它为准。

## 7. packages/pi-tui — 内嵌终端 UI 库（CLI 的 TUI 地基）

上游 pi-mono 0.80.2 基线的 vendored 副本，**不再走 pnpm patch，本地修改直接进源码**——其 AGENTS.md 列了 8 条必须随每次 re-vendor 保留的本地差异（CJK 换行栈溢出守卫、容器宽度钳位、超宽行截断不抛错、稳态帧 O(变更行) 复用、CJK 边界自动链接、内联斜杠补全等），每条都有测试守着。核心类：`Container`（`packages/pi-tui/src/tui.ts:211`）、`TuiMainScreen`/`TuiAltScreen`、`ProcessTerminal`。组件：`Editor`/`ScrollView`/`Markdown`/`SelectList`/`Image`（kitty graphics）…。CLI 有 153 处 import，集中在 `apps/kimi-code/src/tui/`。测试用 **node:test**（CI 单独 job）。

## 8. packages/tree-sitter-bash — 纯 TS bash 解析器

为 agent 侧的命令权限分析而生：节点类型与 tree-sitter-bash 0.25.0 一一对应，用**双解析差分测试**（官方语料全量比对）保证等价。

- **API 契约**（`packages/tree-sitter-bash/src/parse.ts:6-27`）：预算耗尽 → `{ok:false, reason:'aborted'}`（内部 `Aborted` 异常永不外逃）；语法异常 → `{ok:true, hasError:true}`（带 ERROR/部分节点）；解析器自身 bug 兜底降级为整段 ERROR 节点——**任何情况下不 throw**；
- **预算**（`src/budget.ts`）：默认 50ms / 50k 节点；长扫描循环（词串、heredoc 体）单独查截止时间；深度上限（替换 150 / 解析 500 / 扫描 1024）局部降级不爆栈；
- 唯一生产消费者：v2 引擎的 `src/app/bashParser/bashParserService.ts`。只做解析、不做安全判断。

## 9. packages/migration-legacy — 旧版 kimi-cli → kimi-code 迁移

五步流水（`packages/migration-legacy/src/run-migration.ts:34` `runMigration`）：config（冲突写兄弟文件不覆盖）→ mcp（新值优先，标出需重授权项）→ 用户历史 → skills → **sessions**（旧记录翻译成新 wire 格式 + 写 `session_index.jsonl`，单会话失败进追加式 `migration-errors.log` 跨运行记账）。入口三件套：`detectMigration`（只探测出 `MigrationPlan`）、`shouldSuppressMigration`（`.migrated-to-kimi-code`/`.skip-migration-from-kimi-cli` 标记）、`runMigration`（两段式提示：现在/以后/从不 × 仅配置/全会话）。消费者：CLI 的 `src/migration/`（TUI 启动流程）与插件 `src/migration/legacy-migration.manager.ts`。

## 10. packages/acp-adapter 与 acp-server — ACP 双代

两包 API 刻意兼容（`AcpServerOptions.slashCommands` 等同名同义），内部完全不同：

| | acp-adapter（v1） | acp-server（v2） |
|---|---|---|
| 包裹对象 | node-sdk 的 `KimiHarness`（`packages/acp-adapter/src/server.ts:221`，构造器收 harness） | agent-core-v2 引擎经 **klient memory facade**（`packages/acp-server/src/server.ts:1-14` 头注释） |
| 引导 | 宿主自己建 harness 传入 | `src/start.ts` 自己 `bootstrap()` 建 App scope + klient |
| 方法面 | initialize/session/new/cancel/prompt，其余拒绝 | 全生命周期（new/load/resume/list/close/delete/fork）+ 配置面 |
| 特色 | 每会话 `AcpKaos` 沙箱视图；懒建一个 `LocalKaos` 共享 | 客户端声明 `terminal` 能力时 Bash 反向 RPC 到客户端终端执行 |
| 调用方 | `kimi acp`（`apps/kimi-code/src/cli/sub/acp.ts:122`，harness 来自 `createKimiHarness`） | `kimi acp` 原生路径（`src/cli/sub/acp-native.ts:60` 动态 import） |

两者 stdio runner 都先"console 重定向到 stderr（stdout 是 JSON-RPC 信道）"；v2 的 `close()`（`src/start.ts:180-216`）遵循与 kap-server 相同的排空顺序（klient → 追加日志 → 元数据 → 索引镜像 → 注册表 → drain）。

## 11. packages/klient — 契约驱动客户端门面

三层：facade（`src/core/klient.ts:38` + `src/core/facade/{global,session,agent}.ts`）、contract（`src/contract/` zod）、transport（memory / ipc）。**ipc 是 unix domain socket，不是 spawn**：宿主侧 `serveKlientIpc({ scope, socketPath })`（`src/transports/ipc/host.ts:53`）接收一个**已引导的引擎 App scope**，socket 上的帧桥进与 memory transport 同一个进程内 dispatcher（"ipc 与内存行为构造性一致，只差序列化"）；客户端 `IpcChannel` 只连接现成 socket——**klient 从不自己启动引擎**。帧为 NDJSON + hello 令牌校验。消费者：node-sdk（memory）、acp-server（memory）。

## 附：v1 引擎（packages/agent-core）哪里还值得读

仅作 `KIMI_CODE_LEGACY_FLAG` 回退存在，但 `src/loop/` 是理解 agent loop 的**最简读本**：`run-turn.ts`（turn 收敛、abort/compaction 安全点、max steps）、`turn-step.ts`、`tool-call.ts`/`tool-scheduler.ts`（按资源冲突并行/串行——v2 `toolScheduler` 的原型）、刻意无状态不 import 宿主（其 `src/loop/README.md` 写明契约）。`src/tools/builtin/` 的"一工具一 `.ts` 一 `.md`"形式被 v2 延续。kosong/kaos 是它的专属依赖。

## 读包顺序建议

按学习路线（`README.md`）自然顺序即可：04（引擎）→ transcript（理解 UI 数据从哪来）→ oauth（登录链）→ minidb（搜索）→ 其余按需。每包先读其 `AGENTS.md`（若有）再进 `src/`。
