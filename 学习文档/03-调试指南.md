## 1. VS Code 插件：F5（最顺的一条路）

**前提**：已执行过根目录 `pnpm install`；需要让工作区包含 `apps/vscode`，但不一定要"另开窗口"。背后两个机制：

1. **配置发现机制**：F5 用的 `launch.json` 和它的 `preLaunchTask` 对应的 `tasks.json`，VS Code **只从"工作区文件夹的 `.vscode/`"里读**。这套文件只有 `apps/vscode/.vscode/` 里有，仓库根没有——所以你现在的根窗口按 F5，列表里**根本没有**这个调试配置。
2. **路径绑定**：`launch.json` 里所有路径都是 `${workspaceFolder}/...` 且带 `../../` 层级（比如 `${workspaceFolder}/../../.tmp/vscode-extension-dev/user-data`），`${workspaceFolder}` 必须解析为 `apps/vscode`，这些路径才指向正确位置。

当前就在仓库根窗口，怎么做？

| 方式 | 操作 | 适合 |
|---|---|---|
| **A. 另开窗口（最简单）** | 终端跑 `code apps/vscode`（或 File → Open Folder） | 最常用：根窗口留着干别的，新窗口专管插件调试 |
| **B. 不另开窗口** | 当前窗口 File → **Add Folder to Workspace...** 加入 `apps/vscode` → F5 | 就想要单窗口时 |

方式 B 的原理：多根工作区会把**每个文件夹自己的** `launch.json`/`tasks.json` 合并进调试列表，配置按所属文件夹解析——`${workspaceFolder}` 仍是 `apps/vscode`，preLaunchTask 也在那个文件夹的 tasks.json 里找，行为完全不变。想下次复用就 File → Save Workspace As… 存成 `.tmp/` 下的 `.code-workspace` 文件（别提交进仓库）。

**1. "工作区包含 apps/vscode"是什么意思？**

**工作区 = 当前这个 VS Code 窗口"打开"的那一组文件夹。**

- 普通 `code kimi-code` 打开一个文件夹 → 工作区就是这一个文件夹（kimi-code）；
- 你刚才 `Add Folder to Workspace` 加了 `apps/vscode` → 工作区变成**两个**文件夹。

`.vscode/launch.json` 只是磁盘上的一个文件，VS Code 只去读“属于当前工作区的文件夹”里的 .vscode/。文件虽然在磁盘上、但它的文件夹不在工作区里，那这份配置就等于不存在——这就是为什么之前在根窗口按 F5 看不到插件调试配置：配置在 `apps/vscode/.vscode/` 里，而 `apps/vscode` 不在工作区。

所以`File` → **`Add Folder to Workspace...`** 加入 `apps/vscode`的意思就是：**apps/vscode 必须是当前窗口打开的文件夹之一**。你现在加了，就已经做到了。验证方法：按 F5，下拉列表里应该出现 `"Kimi Code: Extension Development Host (isolated)"`（多根下可能带 "vscode:" 文件夹前缀）——看到它就成功了。

**2. 现在的状态：两个根 + 窗口重启了一下**

- 你观察到的全部是**多根工作区的正常现象**：

- **资源管理器出现两个顶级文件夹**（kimi-code 和 vscode）：因为你把 apps/vscode 单独加成了第二个根；
- **窗口"重启"了一下**：加入/移除工作区文件夹会触发窗口重载，正常，不是故障；
- **实际影响**：功能上没有坏影响，F5 目标已达成。唯一的小干扰——你加的 apps/vscode **本来就在 kimi-code 里面**，所以两边都能浏览到它，全局搜索 apps/vscode 下的文件会出**双份结果**（一条路径从 kimi-code 根下走、一条从 vscode 根下走）。Git/终端基本无感（同一个仓库）。

三个选择，按喜好定：

| 选择 | 操作 | 效果 |
|---|---|---|
| 保持现状 | 什么都不做 | 双根，搜索有重复，能接受就行 |
| 精简成单根 | 右键 kimi-code 根 → **Remove Folder from Workspace** | 窗口变成只开 apps/vscode——等于不开新窗口"切换"了过去，搜索不再重复；想看根目录其他内容再 Add 回来 |
| 保存复用 | File → **Save Workspace As…** 存到 `.tmp/xxx.code-workspace` | 这套双根布局存成文件，下次 `code .tmp/xxx.code-workspace` 一键恢复 |

**3. "无标题（工作区）"是什么意思？**

这是**未保存的多根工作区**的默认标题：

- 单文件夹窗口，标题栏显示文件夹名（比如 kimi-code）；
- 多根工作区如果还没保存，标题就是"无标题（工作区）"——意思是这套"文件夹组合"目前**只活在当前窗口里**，关掉窗口它就没了（下次 `code kimi-code` 又回到单文件夹状态）；
- 执行 Save Workspace As 存成 `.code-workspace` 文件后，标题变成你起的文件名，组合才算持久化。

对你没有任何功能影响，只是提示"这套组合是临时的"。

**步骤**：

1. 按 `F5`，选 **"Kimi Code: Extension Development Host (isolated)"**。
2. `preLaunchTask: vscode: dev`（`apps/vscode/.vscode/tasks.json`）会并行跑三件事：
   - `pnpm run dev:prepare`：在仓库根 `.tmp/vscode-extension-dev/` 下创建一次性沙箱——独立的 `user-data/`、`extensions/`、`kimi-home/`（作为 `KIMI_CODE_HOME`）、空 `workspace/` 文件夹；
   - `pnpm run dev:extension`：tsdown watch 构建 `dist/extension.js`，**带 sourcemap**（`scripts/watch-extension.mjs` 轮询触发，见下面"改哪些代码会生效"）；
   - `pnpm run dev:webview`：vite watch 构建 webview（`--sourcemap`）。
3. 弹出新的 "Extension Development Host" 窗口：干净的隔离配置、打开的是沙箱 workspace、插件数据完全隔离（不碰你真实的 `~/.kimi-code`）。首次要在里面重新登录。
4. 在**原窗口**的 `apps/vscode/src/**` 下断点，宿主窗口里操作即可命中（launch.json 已开 `sourceMaps` 并限定 `resolveSourceMapLocations` 到本目录）。

**改哪些代码会自动生效**（`scripts/watch-extension.mjs:9-22` 的轮询列表）：

- `apps/vscode/{src,shared}` + `packages/{agent-core,kaos,kosong,migration-legacy,node-sdk,oauth,protocol,telemetry}/src`——改动后自动重打包，然后在宿主窗口 **Developer: Reload Window** 重新加载扩展。
- **不在列表里**：`agent-core-v2`、`klient`、`transcript`、`minidb` 等。注意：它们**并不是从 dist 打进插件的**——所有 workspace 包的开发态 `exports` 都指向 `src`（机制详见 `01` 第二节），tsdown 解析这些包时同样落在源码上；`tsdown.config.ts:21-28` 的 alias 只是显式路径替换，不是 dist/dist 的区别。所以**改 v2 引擎源码不需要 `pnpm build:packages`**，真正的问题是 watch 轮询列表（v1 时代写的）没含这些目录，**不会自动触发重打包**：改完后 touch 任一被监听文件（或重跑 `pnpm dev`）触发重打包，再 Reload Window。
- 断点提示：watch 重打包带 sourcemap，理论上映射回 `packages/*/src`；但 launch.json 的 `resolveSourceMapLocations` 只允许 `workspaceFolder`（apps/vscode）内，`packages/**` 不在其中，**v2 源码断点可能绑不上**。调试引擎内部首选 第 3 节 的 CLI attach 方式（tsx 直跑源码，断点天然成立），或在 node-sdk facade 层下断点。

**webview 重载**：宿主代码改动用 Reload Window；webview 改动 watch 重建后，可用命令面板执行 **Kimi Code: Reset Kimi**（命令 id `kimi.resetKimi`，完整 title 见 `package.json:143`）或直接 Reload Window。

**日志：插件专属的"输出通道"（OutputChannel，术语见 `08` 术语表）**

**它是什么**：

- VS Code 底部的"输出"（Output）面板不是一整块，而是"右上角一个下拉框 + 一堆只读文本页签"：VS Code 自身、每个插件、每个语言服务器各占一个页签，滚动显示各自的运行日志；
- "输出通道"就是插件往**自己那个页签**写文字的官方 API：`vscode.window.createOutputChannel("Kimi Code")`（`src/extension.ts:20`）创建一个名叫 "Kimi Code" 的通道——这个名字就是输出面板下拉框里显示的页签名；
- 用途是给插件"记流水账"：激活版本、登录检查、旧版本迁移统计、各处报错都追加到同一个地方，平时不弹窗打扰你，出问题再打开看。

**什么内容会写进去**：

- 写入统一走 `log()`：每行格式 `[ISO 时间戳] 消息`（`outputChannel.appendLine`，`src/extension.ts:150-152`）；`logError()` 把异常名和消息拼好也走它（`src/extension.ts:154-157`）；
- 首行通常是激活日志：版本号 + 是否 remote 环境（`src/extension.ts:22`）；
- `SessionRuntime` 的错误也汇到这里。

**在 VS Code 里怎么看到（四种入口）**：

1. 命令面板 `Cmd+Shift+P` → 输入 **Kimi Code: Show Logs** 回车（命令 title 定义在 `package.json:137-139`，实现在 `src/extension.ts:120`，就是 `outputChannel?.show()`）；
2. 手动翻：`Cmd+Shift+U` 直接聚焦输出面板（或 `Cmd+J` 呼出底部面板 → 顶部页签选 **输出 / OUTPUT**）→ 面板右上角下拉框选 **Kimi Code**；
3. 报错弹窗的按钮：插件弹 error / warning 通知时自带 "Show Logs" 按钮（`src/extension.ts:249-253`、`src/handlers/session.handler.ts:165-169`），点了直达；
4. webview 里也能触发同一个动作（`shared/bridge.ts:61` → `src/handlers/config.handler.ts:105-106`）。

**两个注意点**：

- 输出面板 ≠ 调试控制台（Debug Console）：断点调试时 `console.log` 落在 Debug Console；插件的 `log()` 落在输出面板的 Kimi Code 页签；
- F5 之后"三样东西"的窗口归属各不相同，极易混淆：

| 东西 | 在哪个窗口 | 为什么 |
|---|---|---|
| 断点（编辑器里的红点） | **原窗口** | 调试会话在原窗口，断点是调试器的东西 |
| Debug Console（调试控制台） | **原窗口** | 被调试进程里的 `console.log` 会被送回调试会话的控制台 |
| 输出面板的 "Kimi Code" 页签 | **宿主窗口** | 输出通道是插件在自己跑的那个窗口的 UI 上建的页签 |

- 关键机制：输出通道是**窗口本地**的——插件跑在哪个窗口的扩展宿主（Extension Host）里，`createOutputChannel` 建的页签就出现在哪个窗口的输出面板，VS Code 不会把它转发给别的窗口。而开发版插件只通过 `--extensionDevelopmentPath` 加载进宿主窗口（`launch.json` 的启动参数），原窗口里根本没有这个开发版插件在跑，所以它的 "Kimi Code" 页签只可能在宿主窗口；
- 什么时候你会在原窗口也看到一个 "Kimi Code" 页签：如果你平时用的那个原窗口正式安装过市场版 Kimi Code 插件，那个实例会在原窗口建自己的**同名**通道——但那不是你 F5 的开发版。区分方法：看首行激活日志的版本号（`src/extension.ts:22` 打的 `Kimi Code <版本号> activating`），或直接在宿主窗口里做一次登录/会话操作，看哪个窗口的页签在滚动追加；
- 30 秒验证：F5 起来后，两个窗口各按 `Cmd+Shift+U` 对比下拉框；再在宿主窗口里随便触发一个插件动作，日志立刻追加——滚动的只有宿主窗口那份。

## 3. CLI / TUI 调试（attach 模式）

没有现成 launch.json，两种做法：

**做法 A（推荐）：JavaScript Debug Terminal**

1. VS Code（打开仓库根）命令面板 → **JavaScript Debug Terminal**，得到一个自动 attach 的终端（它会自动跟踪里面启动的 node 子进程）；
2. 在里面跑 `pnpm dev:cli`（dev.mjs 会起市场 dev server 并 spawn tsx 子进程，子进程会被调试终端自动跟踪）。若想绕过市场 server 直接起 CLI，用等价的裸命令并**必须带上 dev tsconfig**（不带会在 v1 引擎的参数装饰器处报错，机理见 `01` 的 2.2 节）：

   ```bash
   cd apps/kimi-code
   pnpm exec tsx --tsconfig ./tsconfig.dev.json \
     --import ../../build/register-raw-text-loader.mjs ./src/main.ts
   ```

   （注意：`apps/kimi-code` 的 `dev:cli-only` 脚本就是少了这个 `--tsconfig`，裸用会炸。）
3. 断点下在 `apps/kimi-code/src/**` 或任何 workspace 包**源码**里（tsx 直跑 TS，sourcemap 天然成立）——这正是调试 `agent-core-v2` 内部的最佳方式。

**做法 B：inspect 端口附加**

```bash
cd apps/kimi-code
NODE_OPTIONS=--inspect pnpm exec tsx --tsconfig ./tsconfig.dev.json \
  --import ../../build/register-raw-text-loader.mjs ./src/main.ts
# 或对已运行的进程：命令面板 → Debug: Attach to Node Process → 选 tsx 子进程
```

再配一个个人 `.vscode/launch.json`（放仓库根，`.vscode/` 未提交，属个人配置）：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Attach to kimi dev CLI",
      "type": "node",
      "request": "attach",
      "port": 9229,
      "restart": true,
      "resolveSourceMapLocations": null,
      "skipFiles": ["<node_internals>/**", "**/node_modules/**"]
    }
  ]
}
```

**TUI 注意**：断点挂起会冻结整个 TUI 渲染，属正常现象；resume 即恢复。TUI 与调试输出混在同一个终端会花屏，建议让被调试进程跑在普通终端、调试器只附加（做法 B），或调试非交互子命令（如 `web`）。

## 4. kap-server（`kimi web`）调试与观测

**启动**（仓库根）：

```bash
pnpm dev:server
```

实际命令：`KIMI_CODE_DEV_SERVER=1 tsx ... src/main.ts web --no-open --debug-endpoints`（定义在 `apps/kimi-code/package.json` 的 `dev:server`）。特点：

- 绑定**回环地址**并启用 bearer 鉴权（默认安全，不暴露局域网）；
- `--debug-endpoints` 挂载 `/api/v1/debug/*` 反射 RPC——整个 DI 注册表的自省面；
- 日志：`--log-level debug`（`apps/kimi-code/src/cli/sub/web/run.ts` 的子命令选项）或 `KIMI_LOG_LEVEL`；
- `KIMI_CODE_DEV_SERVER=1` 时容忍缺失的 `dist-web`（浏览器 UI 来自外部 code-app 仓库的预构建产物）。

**断点**：与 第 3 节 相同——JS Debug Terminal 里跑 `pnpm dev:server`，或在 web 子命令入口 `apps/kimi-code/src/cli/sub/web/run.ts` 与 `packages/kap-server/src/**` 下断点。

**观测（强烈推荐）**：另开终端跑

```bash
pnpm --filter @moonshot-ai/kimi-inspect dev
```

kimi-inspect 是网页版调试器（Vite 代理 `KIMI_SERVER_URL`，默认 `http://127.0.0.1:58627`），并**自动发现** `~/.kimi-code/server/instances/` 下的运行实例（每个实例一个 `<serverId>.json` 元数据，见 `packages/kap-server/src/instanceRegistry.ts:210`），从页头下拉切换。能看：workspace/session 浏览、逐会话 transcript 对话、跨会话搜索、Service 面板、DI 单元树/级联视图。

直接 curl 调试面：从实例 JSON 里取连接信息，`curl -H "Authorization: Bearer <token>" http://127.0.0.1:<port>/api/v1/debug/...`（只在回环可用）。

## 5. 单元测试调试

```bash
pnpm test                                  # 全量（根 vitest workspace）
pnpm --filter @moonshot-ai/agent-core-v2 test
pnpm -C packages/agent-core-v2 exec vitest run src/agent/loop     # 只跑某目录/文件
pnpm -C apps/vscode test                   # 插件 16 个套件
```

- 按用例名过滤：`vitest run -t "<name pattern>"`。
- **断点调试**：开一个 JavaScript Debug Terminal，在里面跑上面的 vitest 命令，断点直接命中（对 agent-core-v2 这种无注释区包尤其好用——测试就是最好的文档）。
- `apps/kimi-code` 的 `test`/`e2e` 脚本自带 `pnpm -w run build:packages` 前置——这不是解析需要（vitest 同样走 exports→src，见 `01` 第二节），而是发布门禁链的完整性设计；本地只想跑单文件可用 `pnpm -C apps/kimi-code exec vitest run test/<path>` 绕过。e2e 用 `pnpm e2e`（mock）与 `e2e:real`（真实 LLM，谨慎跑）。
- 例外：`packages/pi-tui` 用 **node:test**（`node --test test/*.test.ts`，CI 单独跑）；`apps/kimi-inspect` 的 vitest 不在根 projects 列表，要进它的目录跑。

## 6. 会话数据与回放：vis

```bash
pnpm vis
```

vis（`apps/vis`）可视化会话与回放：vis-server（API，默认 5174）+ vis web（默认 5173），由 `apps/vis/scripts/dev.mjs` 用 concurrently 同时拉起并协商空闲端口。学习 transcript / 事件流时，把一次真实对话放到 vis 里看事件时序，比读代码快。

## 7. 常用环境变量

| 变量 | 作用 |
|---|---|
| `KIMI_CODE_HOME` | 数据根（默认 `~/.kimi-code`）。调试时指向沙箱目录可完全隔离 |
| `KIMI_LOG_LEVEL` | 日志级别（`off`/`error`/`warn`/`info`/`debug`；测试里常见 `off`） |
| `KIMI_CODE_LEGACY_FLAG` | `=1` 强制 v1 引擎（CLI 的 `dev:cli:legacy`、插件引擎回退都会用到） |
| `KIMI_CODE_EXPERIMENTAL_FLAG` | 打开全部实验特性；单项用 `KIMI_CODE_EXPERIMENTAL_<NAME>`（清单见 `docs/en/configuration/env-vars.md` 与 `packages/agent-core-v2/docs/flag.md`） |
| `KIMI_CODE_DEV_SERVER` | dev 模式标记（容忍缺失 dist-web 等） |
| `KIMI_SERVER_URL` | kimi-inspect / code-app 的 web dev 指向哪个 server |

## 8. 已知坑

- `dev:server` / `dev:kap-server` / `dev:v2` 三个根脚本是**同一条命令**的历史别名，别纠结用哪个。
- `apps/kimi-inspect/README.md` 提到的 `dev:v1` 已不存在，等价物是 `dev:server`。
- 插件引擎切换（`kimi.useAgentCoreV1`）是启动时一次性解析的，改设置后必须 **Reload Window**。

- **断点全部变空心/不命中**：十有八九是 `dist/extension.js` 没有 sourcemap。注意 `build:extension`（`tsdown.config.ts` 里 `sourcemap: false` 且 `clean: true`）会**把 watch 构建生成的 `.map` 清掉**——跑过一次正式构建后 F5，如果 watch 进程是旧的（只盯源码变化、没变化就不重建），调试会话加载的就是无 map 产物。修法：按 watch 的同款命令重建一次 `pnpm -C apps/vscode exec tsdown --config tsdown.config.ts --sourcemap`，再重启调试会话。断点要下在**原窗口**的 `apps/vscode/src/**`（实心圆=绑定成功，空心圆=没绑上）。
- **拉新代码后 F5 激活报 `Cannot find package 'xxx'`（比如 `xstate`）**：是 `node_modules` 落后于 lockfile——新代码给某个包（`xstate` 来自 agent-core-v2 的 agent runtime 重构）新加了依赖，而本地没重新 `pnpm install`。坑点在于 tsdown 对**解析不到的裸导入不报错**，直接把它留成外部 `import` 写进产物（构建时只有一条 warning），于是激活时必然炸。修法：仓库根 `pnpm install`，重新构建（F5 的 preLaunchTask 会自动重建）。想验证产物干净不干净：扫 `dist/extension.js` 里**语句级**的 `import ... from '裸包名'`——只应出现 `vscode`、Node 内置、以及 apps/vscode 自己声明的依赖（如 `immer`）；注意区分注释里的示例代码（xstate 源码的 JSDoc `@example` 里就有一堆假 import，不算数）。
