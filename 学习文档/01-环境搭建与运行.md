# 01 · 环境搭建与运行

> 内容基于 commit `d4e0ad4b2`（2026 年 8 月）核对，后续代码变动可能使细节过时。本文回答三类问题：怎么装、**什么时候需要构建（以及为什么）**、怎么把三种运行形态（CLI、VS Code 插件、Web 服务器）跑起来。第二节「构建体系」的结论全部经代码与实测验证，包括"零 dist 也能开发"的实证。

## 一、环境要求与安装

| 依赖 | 版本 | 来源与强制机制 |
|---|---|---|
| Node.js | **≥ 24.15.0** | 根 `package.json` 的 `engines` 字段（声明"本包要求的 Node 版本"）；`.nvmrc` 固定 `24.15.0`（nvm/fnm/mise 是三个常用的 Node 版本管理器，都会读这个文件）。`.npmrc`（npm/pnpm 的配置文件）里 `engine-strict=true` 让版本不符时 `pnpm install` **直接失败** |
| pnpm | **10.33.0** | 根 `package.json` 的 `packageManager` 字段声明精确版本；corepack（Node 自带的包管理器版本管理工具）据此保证：用错版本会被 pnpm 自身拒绝 |

```bash
node -v && pnpm -v        # 先自检，报错先查这里再谈别的
git clone <repo> && cd kimi-code
pnpm install
```

`pnpm install` 装完依赖后还会自动执行两个收尾脚本（即 `package.json` `scripts` 里的 `postinstall` 钩子——npm/pnpm 约定的"装完自动跑一次"的脚本。**写在哪个包的 package.json 里，就在那个包装完后执行**；无需也不应手工重跑）：

- **挂在仓库根** `package.json` 的 `scripts/fix-node-pty-perms.mjs`：整个 monorepo 装完后在根目录跑一次，给 node-pty 自带的 `spawn-helper` 小程序补回"可执行"权限。来龙去脉：CLI 开终端跑 shell 靠 node-pty（由 `packages/agent-core-v2` 与 `apps/kimi-code` 声明依赖，实际装在根 `node_modules/.pnpm/` 共享存储），它自带一个预编译辅助程序（`prebuilds/<平台>/spawn-helper`），是个程序就得有 +x 权限才能被执行；而 pnpm 的包存储机制会把这个权限弄丢（装完是 0644，"能读写、不能执行"），真开终端时系统直接拒绝执行、报 `posix_spawnp failed`。此脚本在每次装完后自动 `chmod +x` 修回来。pnpm 开发环境特有（npm/yarn 与正式发布的包都正常）；可重复执行，失败也不影响安装；
- **挂在 `apps/kimi-code` 包** `package.json` 的 `scripts/postinstall.mjs`：`apps/kimi-code` 就是本仓库开发的 CLI/TUI 应用本体（发布名 `@moonshot-ai/kimi-code`），此脚本在该包装完后执行。它服务的是**最终用户的全局安装**场景：用户 `npm install -g @moonshot-ai/kimi-code` 装完，终端里才有 `kimi` 命令；而 kimi 旧版是 Python 写的、命令也叫 `kimi`，老用户电脑上可能残留旧命令并挡住新命令。脚本只在检测到"这是一次全局安装"时干活（把旧 Python 版 `kimi` 改名 `kimi-legacy`，给新命令让路）；开发者在仓库里 `pnpm install` 不是全局安装，脚本开头就直接 return，什么都不做（no-op）。

为什么在**根目录**跑一次 `pnpm install`，所有包的依赖就都装好了？——workspace 机制：`pnpm-workspace.yaml` 用 `packages/*`、`apps/*` 等 glob（通配符路径写法）圈定成员包；pnpm 在根目录 install 时按这份清单找出全部成员，把整个仓库当成**一个项目**对待——统一读所有成员的 `package.json`、解析出**一份**根级 `pnpm-lock.yaml`，外部依赖一次性装进根 `node_modules/.pnpm/` 共享存储，再在各成员的 `node_modules` 里放链接（兄弟包之间就是 2.1 节讲的软链接）。所以**永远只在根目录装一次**，不要进子包再跑 install。另：`catalog:`（pnpm 的统一版本清单，写在 pnpm-workspace.yaml 里，各包引用同一版本号）锁 zod 版本；**增删包要同步改 `flake.nix` 的两个手维护列表**（详见 `07`）。

## 二、构建体系：什么时候需要 build，为什么

这一节讲透一个初学最容易困惑的问题：**为什么 `pnpm install` 之后不用构建就能开发，但有些脚本又自动先构建？**

### 2.1 根基：开发时的模块解析（import 一个包名后去读哪个文件）根本不经过 dist

先补两个背景概念：

- **`exports` 字段 = 包的"入口地图"**。别人写 `import x from '@moonshot-ai/agent-core-v2'` 时，Node/打包器查这个字段决定"包名最终读哪个文件"。正常发布的库这里指向编译产物（`dist/*.mjs`）；而这个仓库全部 16 个 workspace 包的 `exports` **都指向源码**——直接指到 `.ts` 文件（`types` 是给类型检查器看的入口、`default` 是给运行时/打包器看的入口，这里两者指同一个文件），例如（`packages/agent-core-v2/package.json`）：

```json
"exports": {
  ".": { "types": "./src/index.ts", "default": "./src/index.ts" },
  "./*": { "types": "./src/*.ts", "default": "./src/*.ts" }
}
```

- **workspace 依赖 = 软链接，不是下载**。兄弟包之间的依赖写在各自 `package.json` 的 `dependencies` 里，但版本号用 `workspace:` 协议（如 `apps/kimi-code/package.json` 的 `"@moonshot-ai/agent-core-v2": "workspace:^"`），意思是"这个依赖不在 npm 上，就在本 monorepo 里"。pnpm 据此不做真正的下载安装，而是在引用它的那个包（"消费方"）的 `node_modules` 里建软链接：`apps/kimi-code/node_modules/@moonshot-ai/agent-core-v2 -> ../../../../packages/agent-core-v2`（`ls -la` 可验证）。

两条叠加，import 的完整链路是：**包名 → `node_modules` 里的软链接 → 穿透到 `packages/agent-core-v2/` → 读它的 `package.json` → `exports` 把入口指到 `src/index.ts`**——不管是 tsx（直接运行 TS 的工具）、tsc（TS 官方编译器，此处只做类型检查；其 tsconfig 选项 `moduleResolution: "bundler"` 允许按打包器风格解析 exports）、vitest（测试框架，自带 TS 转换）、tsdown/rolldown（打包工具）还是 vite（前端构建工具），全部如此。**dist 是否存在不影响任何开发态解析。**

那 dist 是给谁的？**发布**。可发布的两个包带 `publishConfig.exports` 指向 `dist/*.mjs` + `dist/*.d.mts`（如 `packages/node-sdk/package.json`）——`pnpm publish` 时用 publishConfig 覆盖 package.json，装到用户手上的才是 dist。也就是说：**dist 是发布产物，不是开发依赖**。实证：本学习文档写作时整个仓库工作区（checkout）**没有任何一个包构建过**（所有 `packages/*/dist` 不存在），照样完成了 typecheck 与 CLI 启动验证。

### 2.2 源码怎么被"运行"起来：三种机制与各自的坑

**① tsx（`dev:*` 开发脚本都用它）**：tsx 内部用 esbuild（一个极快的编译器）在运行前现场把 TS 转成 JS，不需要预先编译。关键坑：**tsx 只对匹配 tsconfig `include` 的文件应用 compilerOptions**。`apps/kimi-code/tsconfig.json` 的 include 只有 `src`/`test`，不含 `packages/*/src`，于是 v1 引擎里用到的参数装饰器（TS 的一种语法特性，需要编译选项 `experimentalDecorators` 打开才可用）不被启用、直接报 `Parameter decorators only work when experimental decorators are enabled`。解法就是 `apps/kimi-code/tsconfig.dev.json`——它的 include 额外覆盖 `../../packages/*/src/**`，`scripts/dev.mjs:53-57` 的注释写明了这一点，并显式传 `--tsconfig resolve(APP_ROOT, 'tsconfig.dev.json')`。

> 实测注意：`pnpm -C apps/kimi-code run dev:cli-only` 这个**裸命令没有带 `--tsconfig`**，在默认 v2 路径也会因为引到 v1 `agent-core` 的装饰器而炸。调试 CLI 请用 `pnpm dev:cli`（dev.mjs 已带正确 tsconfig）再附加调试器，或自己补上 `--tsconfig ./tsconfig.dev.json`。

**② worker 线程**（Node 的子线程，在后台跑重活、不阻塞主线程）：Node ≥22.7 加 `--experimental-transform-types` 参数可以直接跑 TS。kap-server 搜索 worker 的入口查找（`packages/kap-server/src/search/worker/host.ts:329-360`）按三级顺序回退（前一个找不到就用下一个）：打包配置指定的产物 → **同目录的源码文件**（`entry.ts` + 开发态钩子，在本仓库里跑测试/开发走这条）→ 预先打包好的 `search-worker.mjs`。所以 worker 也不强制 dist。

**③ vitest / tsc**：vitest 自带转换、tsc 走 2.1 节的 exports→src——两者天然消费源码。各包的 `test`/`typecheck` 脚本都是裸 `vitest run` / `tsc --noEmit`，没有任何构建前缀（"构建前缀"＝脚本命令开头用 `&&` 拼接的构建步骤，如根 typecheck 的 `pnpm run build:packages && …`；实测：零 dist 状态下 `pnpm --filter @moonshot-ai/klient run typecheck` 通过，而 klient 消费 agent-core-v2）。

### 2.3 结论：场景 × 是否需要构建

| 场景 | 需要 dist 吗 | 说明 |
|---|---|---|
| `pnpm dev:cli`（起 CLI）/ `pnpm dev:server`（起 Web 服务器）/ 插件 F5（VS Code 调试插件，后台 watch 任务持续打包） | **否** | 前两者由 tsx 直接跑源码、插件由 rolldown watch 打包；而 tsx/rolldown 解析 workspace 包都落在 `.ts` 源码（链路见 2.1/2.2 节），全程不碰 dist |
| `pnpm --filter <pkg> test` / `typecheck`（包级） | **否** | 各包自带的脚本本身就没有构建前缀（裸 `vitest run` / `tsc --noEmit`，见 2.2 节第③条） |
| 根 `pnpm typecheck` | 脚本会先自动 `build:packages` | 根脚本写的是 `pnpm run build:packages && …typecheck…`——typecheck 前面拼了一步构建（即"构建前缀"）。这步构建与"tsc 能否解析"无关（tsc 永远走 src，见 2.1 节），存在的原因是：根 typecheck 是**发布门禁链**的第一环——根 `publish` 脚本为 `typecheck → lint → sherif → test → build → lint:pkg → changeset publish` 的串联（sherif＝检查 monorepo 各包 package.json 一致性的工具；lint:pkg＝publint + attw，检查发布配置与类型声明是否规范；changeset publish＝按变更记录逐包发版），发布前要求全链从"已构建"状态做完整校验、任一环失败即中止。本地日常改完代码想快速验类型：`pnpm --filter <pkg> run typecheck`（"单包脚本"＝各包自己 `package.json` 里的 typecheck，内容就一条命令 `tsc --noEmit`——`--noEmit` 表示**只查类型、不产出任何编译文件**，天生不需要 dist；前面也没拼构建步骤，所以快） |
| `apps/kimi-code` 的 `test` / `e2e`（end-to-end 端到端测试） | 脚本自带 `pnpm -w run build:packages`（`-w`＝到仓库根执行） | 同上；本地只想跑单个测试文件可绕过：`pnpm -C apps/kimi-code exec vitest run test/<path>` |
| 打 VSIX（VS Code 插件安装包格式）、`pnpm build`、native 单文件、`lint:pkg` | **是** | 这些就是 dist 的消费者：`publish` 链（见上一行）、`vscode:prepublish`（VS Code 打插件包前自动跑的钩子脚本）、SEA 流水线（SEA＝Node 的 Single Executable Application，把应用打成不依赖 Node 安装的单个可执行文件） |
| `kimi web` 的浏览器 UI | 特例 | `dist-web` 是**预先构建好、直接提交进 git 的产物**（源码在外部 code-app 仓库，本仓库只有成品）；开发模式下 `KIMI_CODE_DEV_SERVER=1` 允许它不存在（此时只提供 API、没有页面） |

一句话：**"要不要构建"的分界线不是"开发 vs 测试"，而是"消费源码 vs 消费产物"**。tsx/tsc/vitest/tsdown 走前者，发布与打包链走后者。

### 2.4 构建命令族谱

| 命令 | 实际行为 |
|---|---|
| `pnpm build` | `pnpm -r run build`（`-r`＝递归对所有包执行）：所有包+应用。apps/kimi-code 的 build 还含跑两遍 tsdown 打包（主包一份、搜索 worker 一份）、`copy-native-assets`（拷贝原生资源）、`check-web-assets`（dist-web 缺失即失败，防止打出坏包） |
| `pnpm build:packages` | 只构建 `packages/*` |
| `pnpm --filter @moonshot-ai/agent-core-v2 build` | 单包构建（改引擎后想验证可构建性时用） |
| `pnpm clean` | 递归清各包 dist |

`pnpm dev:cli` 启动 CLI 之前，`dev.mjs` 先在本机临时起一个小 `HTTP` 服务器(`dev-plugin-marketplace-server.mjs`),它干的事：

1. 把本仓库的 `plugins/` 目录临时变成一个“市场”：动态生成 `marketplace.json`, `CLI` 要装某个插件时，它**现场把那个插件目录打包成 `zip`** 再发给 `CLI`——所以你本地改插件、马上就能在 `dev CLI` 里“安装”验证，不用发布到远程市场；

## 五、数据目录与隔离

数据根由 `KIMI_CODE_HOME` 决定（默认 `~/.kimi-code`）：`config.toml`、会话、OAuth 凭据、插件、搜索索引都在里面，**VS Code 插件与 CLI 共享同一个 home**（同一会话别在两个入口同时打开）。做实验时前缀 `KIMI_CODE_HOME=/path/to/sandbox` 即可完全隔离（插件 F5 的隔离配置就是这么做的）。完整目录语义见 `00` 第三节。

## 七、排错速查

| 症状 | 原因与解法 |
|---|---|
| `pnpm install` 直接失败 | Node/pnpm 版本不满足 engine-strict（见第一节）；用 nvm/fnm/mise 切到 `.nvmrc` |
| `Parameter decorators only work when experimental decorators is enabled` | tsx 没拿到覆盖 `packages/*/src` 的 tsconfig（2.2 节第①条）：用 `pnpm dev:cli`，或裸 tsx 命令补 `--tsconfig ./tsconfig.dev.json` |
| PTY/shell 启动报 `posix_spawnp failed` | node-pty spawn-helper 丢了 +x：重跑 `node scripts/fix-node-pty-perms.mjs` |
| 改了 `packages/agent-core-v2` 源码，插件里没生效 | 不是缺构建——是插件 watch 轮询列表没含 v2/klient 目录，不会自动重打包。touch 任一被监听文件触发重打包再 Reload Window（详见 `03-调试指南.md` 第 1 节） |
| 根 `pnpm typecheck` 慢 | 它先全量构建 packages（发布门禁链设计如此）；日常用 `pnpm --filter <pkg> run typecheck` |
| `kimi web` 打不开浏览器 UI | `dist-web` 缺失（源码在外部 code-app 仓库）；dev 下 `--no-open` + 只提供 API 是正常形态。要浏览器 UI：去 code-app 仓库跑 `KIMI_CODE_REPO=<本仓库路径> pnpm run sync:web` 把构建产物同步过来 |
