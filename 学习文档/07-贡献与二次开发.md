# 07 · 贡献与二次开发（深度版）

> 时效基线：基于 commit `d4e0ad4b2`（2026-08）。权威来源：`CONTRIBUTING.md`（中英镜像）、根 `AGENTS.md`、`.changeset/README.md`、`.github/` 下的实际配置——本文的事实全部来自这些文件本身。AI 辅助贡献按同一标准："你必须能解释你提交的每一行"。

## 一、CI 全景：每个 PR 实际跑什么（`.github/workflows/ci.yml`）

| Job | 内容 | 对开发的含义 |
|---|---|---|
| build + smoke | `pnpm install --frozen-lockfile` → `pnpm run build` → `pnpm -C apps/kimi-code run smoke` | 产物可构建、CLI bundle 可启动 |
| test（matrix 1–5/5） | `pnpm run test --shard=n/5` | 根 vitest workspace 五分片并行 |
| test-pi-tui | `pnpm --filter @moonshot-ai/pi-tui test` | pi-tui 用 node:test，单独 job |
| test-vscode | `pnpm run test -- --testTimeout=30000` | 插件套件（v2 引擎），超时放宽 |
| **test-vscode-legacy** | `pnpm --filter kimi-code test` + `KIMI_CODE_LEGACY_FLAG=1` | **插件在 v1 引擎上再跑一遍**——改插件时两个引擎都要过（注意 `kimi-code` 是 apps/vscode 的包名，别和 `@moonshot-ai/kimi-code` 混淆） |
| test-windows | 同套测试的 Windows 跑法 | 跨平台回归 |
| lint + sherif | `pnpm run lint`（oxlint --type-aware + 无注释检查）+ sherif | 风格与 monorepo 依赖一致性 |
| typecheck | 根 typecheck + 插件 + vis-server + vis-web 逐个 | 见 `01` 第二节：typecheck 自带 build:packages 前缀 |

其余 workflows：`pr-title-checker`（Conventional Commits 强制）、`release`、`pkg-pr-new`（PR 上直接发布试装包）、`docs-deploy`、`_native-build` / `manual-native-bundle` / `nix-build`。

## 二、贡献门槛与 PR 规范

- **门槛**（PR 模板开头的双语声明）：外部 PR 仅接受维护者 `/approve` 过的 issue 的 **bug 修复**；外部 feature PR 不收；约 100 行以上的重构/API 变更先开讨论；
- **PR 模板**（`.github/pull_request_template.md`）四段：Related Issue（外部 PR 必须链接已批准 issue，否则可能被关）/ Problem / What changed / Checklist（读过 CONTRIBUTING、链接 issue、加了测试、跑过 `gen-changesets` 技能或说明不需要、跑过 `gen-docs` 或说明不需要）；
- **提交与 PR 标题**：Conventional Commits（`feat/fix/docs/chore/refactor/test/ci/build/perf/style`），CI 强制；
- **用户可感知行为变化必须同步 `docs/`**（双语镜像，规则在 `docs/AGENTS.md`）。

## 三、changeset 深规则

配置事实（`.changeset/config.json`）：`baseBranch: main`、changelog 用 GitHub 版本、`updateInternalDependencies: patch`（内部依赖联动只 bump patch）、**ignore 列表** = vis / vis-server / vis-web / kimi-inspect（其余内部包本就 private，实际可发布的只有 `@moonshot-ai/kimi-code` 与 `@moonshot-ai/kimi-code-sdk`）。

写法规则（`.agents/skills/gen-changesets/SKILL.md`）：**一句话、只写用户可感知的变化**；影响发布产物的 PR 必须带，纯文档/测试/CI 免；`major` 不能自行决定——停下来说明并取得明确确认，默认 minor、保底 patch。快照配置 `{tag}-{commit}` 供 pkg-pr-new 试装。

## 四、写代码前必知的硬约定

1. **无注释区**：`packages/agent-core-v2`、`packages/kap-server`、`packages/transcript` 的 `src/test/scripts` 三目录禁行/块注释——`scripts/check-no-comments.mjs` 用 **TypeScript AST** 检查（非正则），**2026-09-01 起（#3226）连导出符号的 JSDoc 也禁**，唯一放行的是 lint 抑制指令（`oxlint-disable`/`eslint-disable`），跑在 `pnpm lint` 里；
2. **workspace 增删包双登记**：`pnpm-workspace.yaml`（glob 自动）+ `flake.nix` 的 `workspacePaths`/`workspaceNames`（纯手维护）。漏 path 会静默丢文件、漏 name 会坏 pnpmConfigHook；自动检查只覆盖 kimi-code 依赖闭包，**绿的检查不等于同步了**；
3. 风格细则：可选属性直接传 `undefined` 不做条件展开；可选属性类型不加 `| undefined`；单参内部方法不包 options 对象；非包入口 `index.ts` 用 `export *`；导入优先 `#/...`；
4. 测试：不新建零散测试文件，往对应模块现有文件加；测试因你的改动挂了先改测试（除非实现真有 bug）；
5. 提交信息与 PR 描述**不含 agent 署名**；提交前 `git status` + `git diff --staged --stat` 清掉草稿（学习笔记放 `.tmp/`，gitignored）。

## 五、二次开发切入点（深版）

### 5.1 给引擎加一个工具（最常见扩展）

完整闭环五件事：

1. **实现**：`packages/agent-core-v2/src/agent/tools/<域>/`——一个 `.ts` 定义（zod 输入 schema + `import desc from './x.md?raw'` 渲染描述模板）+ 同名 `.md` 描述文件，参照 `tools/os/read/readTool.ts`（含 runtime 租约与 generation 复查）或 `tools/edit/editTool.ts`（写路径 + display + approvalRule）；
2. **注册**：`registerAgentToolService(ITool, Tool, {name, domain, requiredRuntimeCapabilities})`——Agent 级 OnDemand 服务 + 贡献点记录（机制见 `04` 的 4.4-4.5 小节）；
3. **权限归类**：只读工具应进 `DefaultToolApprove` 放行名单（`src/agent/permissionPolicy/policies/default-tool-approve.ts`），否则默认落 `FallbackAsk`（每次问用户）；
4. **结果构造**：用 `src/tool/result-builder.ts`（50k 字符/2000 行自动截断）；
5. **测试**：加进 tools 相关的现有测试文件；本地 `pnpm --filter @moonshot-ai/agent-core-v2 test`（无构建前缀，见 `01` 第二节）。

### 5.2 给 VS Code 插件加功能

"三处联动"固定动作：`apps/vscode/shared/bridge.ts` 加 `Methods`/`Events` 常量 → `apps/vscode/src/handlers/` 加处理器（经 `HandlerContext` 能力面，别直接摸 runtime）→ `apps/vscode/webview-ui/src/` 的 `services/bridge.ts` 加调用 + store/组件消费。需要引擎配合再往下走 node-sdk → klient 契约。**注意 CI 的 test-vscode-legacy：改动要两代引擎都过**。

### 5.3 把引擎嵌进自己的宿主

用 `@moonshot-ai/kimi-code-sdk` 的 `createKimiHarnessV2`，完整范例就是 `apps/vscode/src/runtime/kimi-runtime.ts`（约百行跑起 harness）。headless 场景参照 `apps/kimi-code/src/cli/v2/run-v2-print.ts`（不经 SDK 直连原生服务的极简版）。跨进程换 klient 的 ipc 传输（unix socket，宿主自己 `serveKlientIpc`，见 `06` 第 11 节），或直接部署 kap-server 走 REST/WS。

### 5.4 给服务器加接口 / 加特性

- kap-server：`src/routes/` 加路由（信封/分页用 `packages/protocol`；会话触达走 `ISessionIndex → getLiveSessionById → handle.accessor` 模式，见 `05` 第五节）；OpenAPI 面同步；
- 引擎特性：`src/features/` 写成自组装 Feature（`contributeService/contributeTool/contributeConfig/contributeCommand`，参照 `features/plan/`）——比改内核域更受鼓励，可整体撤销。

## 六、发布链与打包

- `pnpm publish`（根脚本）逐级门禁：typecheck → lint → sherif → test → build → `lint:pkg`（publint + attw，消费 dist 产物）→ `changeset publish`；
- 插件 VSIX：`apps/vscode` 的 `package:platform` 用 pinned vsce 打 **6 平台**包（darwin/linux/win × 架构），`package:verify` 审计 manifest 与敏感文件；发布脚本与构建分离；
- native 单文件：`build:native:*` + SEA 流水线（`scripts/native/`），`__update_download` 自装下载器与 staged 换入配合（见 `05` 第一、九节）；
- 测试装包：pkg-pr-new 在 PR 上发快照（`{tag}-{commit}` 版本号）。

## 七、实战练习清单（分级）

**入门**：给插件加自定义设置项（package.json contributes → `config/vscode-settings.ts` → webview 显示，注意过 legacy CI）；给 CLI 加一个小命令（参照 `src/cli/sub/doctor.ts`）。

**进阶**：走通插件三处联动；给引擎加一个玩具工具（如 `currentTime`，无权限要求），CLI 与插件都调通；用 node-sdk 写 headless 脚本（起 harness → 建会话 → prompt → 打印事件流）。

**实战**：挑一个 maintainer `/approve` 过的 issue 走全流程：分支 → 修复 → 测试（两引擎）→ changeset（一句话）→ Conventional Commit → PR 模板四段填全 → 双语文档（如需）。
