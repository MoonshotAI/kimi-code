## npm / pnpm 生态

| 术语 | 人话 |
|---|---|
| 钩子（hook） | 某个固定时机自动执行的挂载点，如 `postinstall`（装完自动跑）、`vscode:prepublish`（打插件包前自动跑） |
| `postinstall` | `package.json` `scripts` 里的钩子：装完依赖自动跑一次；**写在哪个包的 package.json 里，就在那个包装完后执行** |
| `workspace:` 协议 | 依赖版本写法（如 `"@moonshot-ai/x": "workspace:^"`），意思是"这个依赖不在 npm 上，就在本 monorepo 里"；pnpm 据此建软链接而非下载 |
| `exports` 字段 | 包的"入口地图"：别人 `import '包名'` 时，Node/打包器查它决定读哪个文件；`types` 给类型检查器看、`default` 给运行时/打包器看 |
| `engines` | `package.json` 里声明"本包要求的 Node 版本"的字段 |
| `packageManager` | `package.json` 里声明精确包管理器版本的字段，corepack 据此强制 |
| `engine-strict` | `.npmrc` 配置项：版本不满足 `engines` 时让 `pnpm install` 直接失败 |
| `catalog:` | pnpm 的统一版本清单（写在 pnpm-workspace.yaml），各包引用同一版本号 |
| glob | 通配符路径写法，如 `packages/*` 匹配 packages 下所有目录 |
| 软链接（symlink） | 指向另一个路径的特殊文件，访问它等于访问目标；workspace 依赖靠它"装"进各包 `node_modules` |
| 共享存储（`node_modules/.pnpm/`） | pnpm 把所有外部包集中存在根目录的这一层，各包 `node_modules` 里只放链接指过去；同一个包全仓库只存一份 |
| `-w` / `-r` | pnpm flag：`-w`＝到仓库根执行；`-r`＝递归对所有包执行 |
| `--noEmit` | tsc 参数：只做类型检查、不产出任何编译文件 |
| 裸脚本 / 裸命令 | 脚本内容就一条命令、前后没拼别的步骤（对比"带构建前缀"） |
| 构建前缀 | 脚本命令开头用 `&&` 拼接的构建步骤，如根 typecheck 的 `pnpm run build:packages && …` |
| 全局安装 | 用户侧 `npm install -g <包>`，装完终端里出现对应命令 |
| shim | 命令转发用的小脚本；旧 Python 版 `kimi` 就是一个 shim，全局装新版时被改名 `kimi-legacy` |

## VS Code 插件 / 协议

| 术语 | 人话 |
|---|---|
| 扩展宿主（Extension Host） | VS Code 专门跑所有插件的独立 Node.js 进程（防止插件卡死编辑器主进程）；插件全部代码跑在这里 |
| 工作区（workspace） | 当前 VS Code 窗口打开的那组文件夹；窗口只读**工作区内**文件夹的 `.vscode/` 配置——文件夹不在工作区里，它的 launch.json/tasks.json 就等于不存在 |
| 多根工作区（multi-root workspace） | 窗口同时打开多个文件夹（Add Folder to Workspace）；各文件夹自己的 launch.json/tasks.json 合并进列表、按所属文件夹解析；未保存时标题为"无标题（工作区）"，Save Workspace As 存成 `.code-workspace` 文件后持久化 |
| 输出通道（OutputChannel） | VS Code"输出"面板里插件专属的只读日志页签：插件代码用 `createOutputChannel("名字")` 申请一个，之后往里逐行追加运行日志；"名字"就是输出面板右上角下拉框里的页签名 |
| Disposable | VS Code 的资源释放协议：占资源的对象实现 `dispose()`，push 进 `context.subscriptions` 后由 VS Code 在插件停用时统一调用——"怎么释放"对象自己写，"何时释放"生命周期管 |
| disposable-like | VS Code 官方词（`Disposable.from` 的 JSDoc）：不是 `Disposable` 实例、但身上有 `dispose()` 方法的对象——subscriptions 收的就是这种"按形状合格"的东西，不要求出身 |
| 结构类型（structural typing） | TypeScript 的类型匹配方式：只看对象**身上有没有**要求的成员（形状），不看它声明过 `implements` 谁（出身）——所以有 `dispose()` 方法就能进 subscriptions，不用写 `implements Disposable` |
| webview | 插件内嵌的网页（本质是浏览器标签页）：只有浏览器 API、不能读文件/起进程，只负责渲染界面 |
| 视图（view） | **一个 webview 聊天页面实例**：侧边栏一个（id 前缀 `sidebar_`）或"Open in Tab"面板若干个（`panel_`），同一窗口可并存多个；每个视图独立绑会话、独立有自己的工作目录（`源码详解/02-BridgeHandler方法详解.md` 第三节开头有定义与代码） |
| 会话（session） | **你和 AI 的一次完整对话**：从第一句提问开始，包含之后所有来回消息和 AI 执行过的操作；每个会话有唯一 id 和自己的工作目录，引擎把它存进 homeDir，关掉后可恢复接着聊。同一概念在三层各有一个对应物：磁盘上的记录 / 内存中引擎侧的 SDK Session / 插件侧包装它的 SessionRuntime |
| postMessage | webview ↔ 扩展宿主之间唯一的数据通道（浏览器标准的跨上下文消息 API） |
| RPC | Remote Procedure Call，远程过程调用：把"调用另一个进程里的函数"包装得像调本地函数——发一条 `{id, method, params}` 消息过去，那边执行完回 `{id, result}` 或 `{id, error}`，靠 id 配对请求和回答（同一时刻多个请求在飞也各归各）。本插件里"远程"＝一墙之隔的两个进程：webview（网页）↔ 扩展宿主（Node）——网页不能 import 宿主的函数，只能 postMessage 传 JSON，RPC 就是在这根管道上定出来的调用格式。**计数单位**：机制本身叫 RPC；一次调用＝"一条 RPC 请求 / 一次 RPC 调用"；通道上服务的一个操作＝"一个 RPC 方法"（JSON-RPC 规范就叫 method，区别于类里的普通方法）——"加一个 RPC"是病句，加的是 RPC 方法 |
| JSON-RPC | 用 JSON 表达"调哪个方法、传什么参数、返回什么/报什么错"的协议格式 |
| ACP | Agent Client Protocol：外部编辑器（如 Zed）接入 agent 的标准协议；本仓库 `packages/acp-server` 是其服务端实现 |
| MCP | Model Context Protocol：外接工具服务器的标准协议，引擎靠它连外部工具 |
| 门面（facade） | 设计模式：把内部一大堆能力收拢成少数几个干净入口（SDK 就是引擎的门面） |
| 依赖注入（DI） | 需要某能力的对象不自己创建/寻找它，而是由调用方从外面递进来（典型是构造函数参数）——BridgeHandler 的 broadcast/writeLog 等六项能力全是构造时递进来的，测试时塞假函数即可替换 |
| DI 容器 | 依赖注入的"总管家"对象：程序启动时把内部几十个服务集中创建、互相接线，销毁时一起收掉——引擎的 DI 容器就是 harness.close() 里 `this.app.dispose()` 销的那个（agent-core-v2 里按 App/Workspace/Session/Agent 四层 Scope 组织） |
| 控制反转（IoC） | "什么时候调用"的主动权从需要方倒转给提供方：KimiRuntime 需要保存基线快照但不认识 BaselineManager，由 BridgeHandler 的构造函数把 captureBaseline 回调递进去，KimiRuntime 只在约定时机调用 |
| 引用计数（refcount） | 记录"现在有几方在用我"的清理策略：每多一个使用者＋1、少一个－1，**清零才真正释放**——多个 webview 同看一个会话时，关掉一个不会误关会话 |
| 幂等（idempotent） | 同一个操作做一次和做多次效果相同——如 dispose 的 closed 守卫让重复触发直接返回；重复调用不留副作用 |
| 内容寻址存储（content-addressed） | 用内容的哈希当存储文件名（基线快照 `<sha256>`）：同内容天然只存一份、读取时可自校验、清理时"清单没提到就能删" |
| 原子写（atomic write） | 先写临时文件再 rename 成正式名——rename 在同一文件系统上是原子操作，读者永远不会看到写了一半的文件 |
| 状态机 | 把对象建模成"一组状态 + 状态间迁移规则"（如会话：空闲/等用户/等审批/流式输出中） |
| 不变量（invariant） | 改代码时永远必须成立的规则，违反即架构被破坏 |
| CSP（Content-Security-Policy） | 网页"能加载/执行什么资源"的白名单，写在 HTML meta 里；插件 webview 用 `default-src 'none'` 起手再逐条放行，防止注入的代码乱跑 |
| 源 / 同源策略（origin / same-origin） | 源 = 协议+域名+端口，页面只在自己源内可标识；浏览器规定**只有同源页面才能互相读取**（DOM/localStorage），不同源互相隔绝；协议或子域不同即不同源——VS Code 给每个 webview 发一个 `vscode-webview://<随机串>` 的独立源（资源则映射到 `*.vscode-cdn.net` 域），就是借同源策略做 webview 间的互相隔离 |
| nonce（一次性随机数） | 每次生成页面新造的随机串；CSP 规定只有带本次 nonce 的 `<script>` 才许执行，注入的脚本拿不到它就跑不起来 |
| 威胁模型（threat model） | 安全设计先回答的"**防谁**"清单：明确攻击者是谁、有什么能力、不防谁——比如 CSP 防内容注入，不防坐在浏览器前开 DevTools 的机器主人 |
| 逆流 RPC（reverse RPC） | 方向倒过来的调用：引擎→宿主→webview 里的用户（典型是审批/提问），实现是"宿主把 Promise 的 resolve 存进 Map，等用户点按钮的 RPC 回来再放行" |
| 投影（projection） | 把一种事件流用纯函数逐条转换成另一种（本仓库里：引擎事件 → UI 事件），不产生副作用；引擎协议改版不波及 UI 的防腐层 |
| 基线快照（baseline） | 工具改文件**前**抢先存下的一份原内容（按内容哈希存盘）；会话的 File Changes 面板、单文件回滚、diff 视图全靠它。动词**"保存快照"**＝把这份原内容读出来存盘这个动作（代码里叫 `capture`；旧文档里的"拍基线/拍快照""捕获基线"是同一件事，均已弃用） |
| 宿主假回合（host action） | 不进引擎、由插件宿主自己执行的斜杠命令（/init、/compact、/yolo 等），但 UI 上要装得像一轮对话：`beginHostAction` 手工发 TurnBegin/StepBegin 开场、`emitHostText` 发正文、`completeHostAction` 发 stream_complete 收场；靠自增的 actionId 对账，取消/被取代的旧号迟到调用一律作废 |
| 每会话串行队列（serialize） | BaselineManager 的写并发控制：每个会话 id 挂一个"最后一次写"的 Promise，新写操作排在它后面（`Promise.all(前序).then(干活)`），读者只等队尾不排队——清单永远不被并发写撕开，不同会话之间又不互相阻塞 |

## 登录 / OAuth（Kimi 账号）

| 术语 | 人话 |
|---|---|
| 设备码流（Device Code Flow / RFC 8628） | 为"没有回调地址的设备"设计的 OAuth 授权方式：程序向授权服务器申请一个设备码，把**带用户码的网址**交给用户在浏览器里打开确认，程序自己在原地每隔几秒轮询"用户点头了吗"直到拿到 token——电视、CLI、VS Code 插件这类开不了 `localhost/callback` 的场景全靠它 |
| 用户码 / 设备码（user_code / device_code） | 设备码流的一对凭证：用户码给人看（浏览器页面上核对的那串 `XXXX-XXXX`，通常拼在 `verification_uri_complete` 直链里），设备码给程序用（轮询时带上它问"这个码授权了没"） |
| 供给（provision） | 登录拿到 token 后的"把账号能力铺成配置"动作：宿主拿 token 去 `GET /models`，把模型清单、provider、默认模型、内置服务写进 config.toml——登录的产品化成果是配置文件，不是 token 本身（`源码详解/06-登录链路详解.md` 第四章） |
| 墓碑（tombstone） | refresh_token 被服务端拒绝（401/403）后写进 token 文件的一块"空记录"（access_token 置空、其余字段保留）：让别的进程读到时知道"登录过、现在需要重登"，而不是误判成"从未登录" |
| Bearer token | HTTP 认证的"出示即通行"格式：请求头带 `Authorization: Bearer <token>`，服务器只认 token 不问来源；`/models` 等托管端点全用它 |
| `managed:kimi-code` | config.toml 里托管 provider 的固定名字（`KIMI_CODE_PROVIDER_NAME`）：type 为 `kimi`、apiKey 刻意留空、凭据走 OAuth 的 provider；webview 判断"默认模型是否需要登录"就看它的 provider 是不是这个名字 |
