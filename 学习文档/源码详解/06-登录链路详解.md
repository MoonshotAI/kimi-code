## 〇、全局认知

1. **登录 = webview 里一次 RPC 往返 + 宿主内一条 OAuth 流水线**。webview（内嵌网页，只有浏览器 API）从头到尾没碰过网络、没见过 token；它只发一条 `login` RPC 然后等回包，真正干活的全在扩展宿主（Node.js 进程）里。

2. **用的是"设备码流"，不是"跳转回调"**。浏览器 OAuth 常见做法是把用户重定向到 `localhost:xxx/callback` 拿授权码——但 VS Code 插件的 webview 拿不到固定回调地址。所以这里走 RFC 8628（设备授权授予，术语见 `学习文档/08-术语表.md`"设备码流"）：插件向 `auth.kimi.com` 申请一个"设备码"，把**带用户码的网址**交给浏览器打开，然后自己在原地每隔几秒问一次"用户点头了吗"，直到拿到 token、被拒绝或 15 分钟超时。

3. **access_token 不进 webview、不进 VS Code 状态，只落磁盘**。它写在 `~/.kimi-code/credentials/kimi-code.json`（权限 0600），后续所有模型请求由宿主按需读取。webview 唯一拿到的是"登录成功了吗"这个布尔值。

4. **登录的"产品化成果"不是 token，而是 config.toml**。拿到 token 只是中间步骤：宿主立刻拿它去 `GET /models` 拉模型清单，把结果写成 `~/.kimi-code/config.toml` 里的 `providers` / `models` / `defaultModel` / `services` 四块配置。配置文件才是引擎和 UI 共同的事实源。

5. **webview 的模型列表永远是 config.toml 的投影，UI 更新靠"重拉"而不是"推送"**。登录 RPC 回包后，前端把初始化流程整个重跑一遍（重新 `checkLoginStatus` + `getModels`），视图路由器按新状态切换界面。没有一条"新模型来了"的专门广播。

## 一、点击瞬间：登录界面为什么会先出现，按钮按下后去了哪

### 1.1 前置：登录界面本身是初始化流程的产物

登录界面不是插件写死的第一屏，而是初始化流程**算出来的结论**。webview 挂载时 `useAppInit`（`apps/vscode/webview-ui/src/hooks/useAppInit.ts:54-150`）跑一遍 `init()`，其中关键一步是并行发两条 RPC（`useAppInit.ts:104`）：

```ts
const [loginStatus, kimiConfig] = await Promise.all([bridge.checkLoginStatus(), bridge.getModels()]);
```

- `checkLoginStatus`（宿主侧 `apps/vscode/src/handlers/auth.handler.ts:12-14`）问的是"磁盘上有没有可用 token"：`harness.auth.status()` 一路走到 `OAuthManager.hasToken()`（`packages/oauth/src/oauth-manager.ts:237-239`），后者把磁盘文件读出来交给三态分类（`packages/oauth/src/token-state.ts:28-34`）：

```ts
export function classifyToken(token: TokenInfo | undefined): TokenState {
  if (token === undefined) return { kind: 'missing' };
  if (token.accessToken.length === 0) {
    return { kind: 'revoked', scope: token.scope, tokenType: token.tokenType };
  }
  return { kind: 'valid', token: token };
}
```

  `missing`（没文件）和 `revoked`（文件在但 token 被清空——"登录过但被拒"，见 3.5 小节）都算未登录，只有 `valid` 算登录。

- `getModels` 读的是 config.toml 里的模型清单（5.3 小节详述）。

全新用户两条都是空的：`modelsCount === 0 && !loggedIn` → 状态置为 `not-logged-in`（`useAppInit.ts:116-118`）→ 视图路由器 `resolveAppView`（`useAppInit.ts:28-45`）返回 `{view: "login"}` → `App.tsx:111-118` 渲染 `LoginScreen`。这就是你看到"Sign in with Kimi Account"按钮的原因。

### 1.2 `handleLogin`：一次点击变成一条 RPC

按钮在 `apps/vscode/webview-ui/src/components/LoginScreen.tsx:148-155`，点击进 `handleLogin`（`LoginScreen.tsx:42-70`）：

```ts
const handleLogin = async () => {
  setState("pending");
  setUrl(null);
  setError(null);
  try {
    const result = await bridge.login();
    if (result.success) {
      onLoginSuccess();
    } else {
      const errorMessage = result.error || "Login failed";
      if (isPaymentRequiredError(errorMessage)) {
        setShowSubscribeDialog(true);   // 402：弹订阅引导，见 6.1
        setState("idle");
      } else {
        setState("error");
        setError(errorMessage);
      }
    }
  } catch (err) { /* 同上，走 catch 分支 */ }
};
```

`bridge.login()`（`apps/vscode/webview-ui/src/services/bridge.ts:129-131`）就是普通的一次 RPC 调用（RPC 机制——`{id, method, params}` 请求 + pending Map 等回包——见 `01` 第 4.2 小节）：

```ts
login() {
  return this.call<LoginResult>(Methods.Login, undefined, OAUTH_REQUEST_TIMEOUT_MS);
}
```

一个值得停留的数字：`OAUTH_REQUEST_TIMEOUT_MS = 16 * 60 * 1000`（16 分钟，`bridge.ts:28`），刻意长于普通请求默认的 10 分钟。因为这条 RPC 在宿主侧要等**整场设备码流**跑完才回包，而设备码流本身有 15 分钟总预算（3.3 小节）——前端超时必须比后端最坏情况再长一档，否则宿主还在认真等用户，前端已经宣告失败。

`state === "pending"` 时界面切成"Waiting for authentication…"（`LoginScreen.tsx:89-125`），并预留了 URL 展示位——它在等一条广播（2.3 小节）。

### 1.3 宿主侧的分发：查表到 `authHandlers.Login`

RPC 请求过 `postMessage` 进宿主，`BridgeHandler` 按 `method` 查表分发（`apps/vscode/src/bridge-handler.ts:142-143`）；表是各 handler 文件聚合出来的（`apps/vscode/src/handlers/index.ts:20-28`），`Methods.Login` 对应 `authHandlers` 里的实现（`apps/vscode/src/handlers/auth.handler.ts:16-38`）：

```ts
[Methods.Login]: async (_, ctx): Promise<LoginResult> => {
  try {
    await ctx.harness.auth.login(undefined, {
      onDeviceCode: async (authorization) => {
        const url = authorization.verificationUriComplete || authorization.verificationUri;
        ctx.broadcast(Events.LoginUrl, { url }, ctx.webviewId);
        await vscode.env.openExternal(vscode.Uri.parse(url));
      },
    });
    await updateLoginContext(ctx.harness);
    return { success: true };
  } catch (error) { /* 见 6.1 / 6.2 */ }
},
```

注意两件事：第一，`harness.auth.login` 是一个**会长时间挂起的 Promise**——从发出到 resolve，中间隔着用户在浏览器里的全部操作；第二，调用方塞进去了一个 `onDeviceCode` 回调，它是宿主与浏览器之间的唯一交汇点，下一章全讲它。

## 二、打开浏览器：设备码第一跳与"一箭双雕"的回调

### 2.1 分层：从 handler 到 OAuth 工具箱

`ctx.harness.auth` 是 `KimiAuthFacade`（`packages/node-sdk/src/kimi-harness.ts` 经 SDK 暴露；VS Code 插件在 `apps/vscode/src/runtime/kimi-runtime.ts:66-77` 用 `createKimiHarnessV2` 创建 harness，身份标识 `productName: "kimi-code-vscode"`）。Facade 的 `login`（`packages/node-sdk/src/auth.ts:136-168`）自己不碰 HTTP，干三件协调的事：

```ts
const auth = this.resolveManagedAuth(providerName);      // 从 config.toml 读已存的 baseUrl / oauth 引用
const loginAuth = resolveKimiCodeLoginAuth({             // 决定这次登录用哪对主机
  configuredBaseUrl: auth.baseUrl,
  configuredOAuthRef: auth.oauthRef,
  requestedBaseUrl: loginOptions.baseUrl ?? regionHosts?.baseUrl,
  requestedOAuthHost: loginOptions.oauthHost ?? regionHosts?.oauthHost,
});
const result = await this.toolkit.login(providerName, {
  ...loginOptions,
  baseUrl: loginAuth.baseUrl,
  oauthHost: loginAuth.oauthHost,
  oauthRef: loginOptions.oauthRef ?? loginAuth.oauthRef,
  provisionConfig: true,                                  // ← 关键：登录顺带供给模型配置
});
if (result.provision === undefined) {
  throw new Error('Kimi auth login did not provision model config.');
}
```

- **主机解析**（`resolveKimiCodeLoginAuth`，`packages/oauth/src/managed-kimi-code.ts:382-415`）：优先级是"本次显式请求 > 环境变量（`KIMI_CODE_BASE_URL` / `KIMI_CODE_OAUTH_HOST`）> config.toml 里已存的值"。默认主机是 `oauthHost = https://auth.kimi.com`（`packages/oauth/src/constants.ts:3`）、`baseUrl = https://api.kimi.com/coding/v1`（`packages/oauth/src/managed-usage.ts:29`）；海外区（`global`）对应 `auth.kimi.ai` / `api.kimi.ai`（`packages/oauth/src/region.ts:44-56` 的区域档案表）。
- **`provisionConfig: true`**：要求登录成功后必须完成"拉模型 + 写配置"（第四章），没完成就当登录失败抛错。
- **登录成功后**`readConfigFile` 重读 config.toml 并触发 `onConfigUpdated` 回调（`auth.ts:159-160`）——VS Code 这条链没传这个回调，配置回流走的是另一条路（5.3 小节）。

### 2.2 `toolkit.login` 的分流：老用户走捷径，新用户走全程

`KimiOAuthToolkit.login`（`packages/oauth/src/toolkit.ts:159-230`）先查磁盘上有没有旧 token（`toolkit.ts:167`），据此分流（`toolkit.ts:169-188`）：

```ts
const hadToken = await manager.hasToken();
let usedDeviceLogin = false;
const loginWithDevice = async (): Promise<string> => {
  usedDeviceLogin = true;
  return (await manager.login({ signal: options.signal, onDeviceCode: options.onDeviceCode })).accessToken;
};
let accessToken: string;
if (hadToken) {
  try {
    accessToken = await manager.ensureFresh();      // 旧 token 还活着：静默刷新，不弹浏览器
  } catch (error) {
    if (!(error instanceof OAuthUnauthorizedError)) throw error;
    accessToken = await loginWithDevice();          // refresh_token 被吊销：降级走设备码
  }
} else {
  accessToken = await loginWithDevice();            // 新用户：直接设备码
}
```

也就是说：**已经登录过的用户再点登录，通常不会看到浏览器**——宿主用旧 refresh_token 换新 access_token 就完事；只有服务端明确拒绝（401/403，`OAuthUnauthorizedError` 一族）才重新走浏览器授权。

### 2.3 `onDeviceCode`：一箭双雕的回调

设备码申请下来后（2.4 小节），`OAuthManager.login` 会调用一次 `onDeviceCode`（`packages/oauth/src/oauth-manager.ts:412`）。VS Code 侧在这个回调里做两件事（`auth.handler.ts:19-23`）：

```ts
onDeviceCode: async (authorization) => {
  const url = authorization.verificationUriComplete || authorization.verificationUri;
  ctx.broadcast(Events.LoginUrl, { url }, ctx.webviewId);   // ① 定向广播给发起登录的那个 webview
  await vscode.env.openExternal(vscode.Uri.parse(url));     // ② 用系统默认浏览器打开
},
```

① 把授权 URL 广播回 webview——第三个参数 `ctx.webviewId` 让这条广播**只发给发起登录的那个视图**（广播机制见 `dive-chain-broadcast链条详解.md`）。webview 侧 `LoginScreen.tsx:36-40` 订阅了它：

```ts
useEffect(() => {
  return bridge.on<{ url: string }>(Events.LoginUrl, ({ url }) => {
    setUrl(url);
  });
}, []);
```

`url` 一到，pending 界面就多出"浏览器没打开？手动访问这个链接"的兜底块，带复制按钮和"Open in browser"链接（`LoginScreen.tsx:101-122`）——自动开浏览器失败时用户仍有出路。

② `vscode.env.openExternal` 是 VS Code 官方的"用系统默认浏览器打开 URL"，跑在宿主进程。

### 2.4 设备码第一跳：`POST /api/oauth/device_authorization`

回调口中的 `authorization` 来自 `requestDeviceAuthorization`（`packages/oauth/src/oauth.ts:119-158`）：

```ts
const url = `${config.oauthHost.replace(/\/$/, '')}/api/oauth/device_authorization`;
const { status, data } = await postForm(url, { client_id: config.clientId }, options.deviceHeaders);
// ...status !== 200 抛 OAuthError；user_code / device_code / verification_uri_complete 三字段缺失即抛错

  userCode,
  deviceCode,
  verificationUri: ...,
  verificationUriComplete,      // 带用户码的直链，形如 https://auth.kimi.com/device?code=XXXX-XXXX
  expiresIn: ...,

```

请求体只有 `client_id`（`packages/oauth/src/constants.ts:14-21`，Kimi Code 的固定客户端 ID）——设备码流的特点是**发起端不需要任何密钥**，身份认定发生在用户在浏览器里登录账号的那一刻。HTTP 层统一走 `postForm`（`oauth.ts:59-99`）：30 秒单请求超时（`DEFAULT_HTTP_TIMEOUT_MS`，`oauth.ts:57`）、表单编码、失败时把 undici 藏在 `cause` 链里的真实原因（DNS / 拒连 / TLS）挖出来拼进报错（`oauth.ts:106-115`）。

## 三、授权轮询：宿主在原地等浏览器那边点头

### 3.1 双层循环：外层换码，内层轮询

用户在浏览器里看到 Kimi 的授权页（登录账号 → 确认那串用户码）的同时，宿主里 `OAuthManager.login`（`packages/oauth/src/oauth-manager.ts:406-457`）已经在转了。骨架是一个双层循环：

```ts
async login(options: LoginOptions = {}): Promise<TokenInfo> {
  const startedAt = this.now();
  const deadlineAt = startedAt + Math.ceil(this.deviceCodeTimeoutMs / 1000);   // 15 分钟总闸
  while (true) {                                  // 外层：申请设备码（过期就换一个重来）
    const auth = await this.requestImpl(this.config);
    await options.onDeviceCode?.(auth);           // ← 上一章那个回调在这触发
    let currentInterval = Math.max(auth.interval, 1);
    let deviceExpired = false;
    while (true) {                                // 内层：按 interval 轮询
      this.throwIfAborted(options.signal);
      if (this.now() >= deadlineAt) {
        throw new DeviceCodeTimeoutError(...);    // 总闸到点
      }
      const result = await this.pollImpl(this.config, auth.deviceCode);
      if (result.kind === 'success') {
        await this.storage.save(this.config.name, result.token);   // ← token 落盘
        return result.token;
      }
      if (result.kind === 'denied') { throw new OAuthAccessDeniedError(...); }
      if (result.kind === 'expired') { deviceExpired = true; break; }   // 回外层换码
      if (result.errorCode === 'slow_down') { currentInterval += 5; }   // RFC 8628：永久 +5s
      await this.sleep(currentInterval * 1000);
    }
    if (!deviceExpired) break;
    if (this.now() >= deadlineAt) { throw new DeviceCodeTimeoutError('Device authorization timed out'); }
  }
  throw new OAuthError('Device flow ended unexpectedly');   // 不可达，兜底
}
```

三个设计点：

- **15 分钟总闸**（`DEFAULT_DEVICE_CODE_TIMEOUT_MS = 15 * 60 * 1000`，`oauth-manager.ts:29`）：不管内层外层转到哪，墙钟过线就抛 `DeviceCodeTimeoutError`——永不挂死的保证。这也是 1.2 小节里前端 RPC 超时定为 16 分钟的依据。
- **`expired_token` 换码重来**：设备码本身有寿命（服务端的 `expires_in`），过期不是错误而是"再申一个"——外层循环存在的意义。
- **`slow_down` 永久生效**：RFC 8628 要求收到 `slow_down` 后本轮剩余轮询间隔至少加 5 秒，这里直接 `currentInterval += 5` 且不回落。

### 3.2 轮询的五种结果

内层每转一圈发一次 `pollDeviceToken`（`packages/oauth/src/oauth.ts:168-211`）：`POST /api/oauth/token`，表单里带 `grant_type=urn:ietf:params:oauth:grant-type:device_code` 和 `device_code`。结果分五种：

| 服务端回应 | `pollDeviceToken` 返回 | `login` 内层的反应 |
|---|---|---|
| 200 + `access_token` | `{kind: 'success', token}` | 存盘、返回，登录完成 |
| `authorization_pending` | `{kind: 'pending', errorCode}` | 睡 `interval` 秒继续问 |
| `slow_down` | `{kind: 'pending', errorCode}` | 间隔永久 +5s 后继续问 |
| `expired_token` | `{kind: 'expired'}` | 跳出内层，外层申请新设备码 |
| `access_denied` | `{kind: 'denied'}` | 抛 `OAuthAccessDeniedError`（用户点了"拒绝"） |
| 5xx | 直接抛 `OAuthError` | 冒泡给调用方 |

（另外支持 `options.signal` 中途打断——`throwIfAborted`，`oauth-manager.ts:420`。）

### 3.3 token 落盘：一次小心翼翊的写文件

`storage.save` 的目标是 `FileTokenStorage`（`packages/oauth/src/storage.ts:41`）。路径由三段拼出：根目录 `~/.kimi-code`（`KIMI_CODE_HOME` 可覆盖）→ 子目录 `credentials`（`toolkit.ts:128`）→ 文件名由 provider 与 oauth key 归一成 `kimi-code.json`（`resolveKimiTokenStorageName`，`toolkit.ts:472-486`；`storage.ts:59-70` 的 `pathFor` 用 `basename` 防路径穿越）。写入是教科书式的原子写（`storage.ts:90-109`）：

```ts
const tmp = `${target}.tmp.${process.pid}.${randomBytes(4).toString('hex')}`;  // 带 pid+随机后缀的临时文件
const fd = openSync(tmp, 'w', 0o600);            // 建文件即 0600（只有属主可读写）
// ...writeSync 全量写入 + fsyncSync 落盘
chmodSync(tmp, 0o600);                           // 防 umask 剥权限，再补一次
renameSync(tmp, target);                         // 原子改名替换
```

目录本身 `chmod 0700`（`storage.ts:48-57`）。先写临时文件再 `rename`，保证任何时刻磁盘上的 `kimi-code.json` 要么是完整的旧内容、要么是完整的新内容——进程写一半被杀也不会留下半个 JSON。

token 内容由 `tokenFromResponse`（`oauth.ts:29-56`）从授权响应构造，`access_token` / `refresh_token` / `expires_in` 三字段缺一即抛错（拒绝持久化"看着能存、之后莫名失败"的残缺响应），并当场算好绝对过期时间 `expiresAt`。

### 3.4 老 token 的降级梯子（provision 阶段的 401 重试）

2.2 小节是"取 token"阶段的分流；取到 token 后还有"供给配置"阶段（第四章），那里也有一架降级梯子（`toolkit.ts:205-226`）：用旧 token 直接 `ensureFresh` 成功、但拉 `/models` 时被拒（401）——说明 token 表面有效实则被吊销。梯子是：**强制刷新**（`ensureFresh({force: true})`）→ 还被拒就**重新设备码登录** → 再拉一次。只有"已经用过设备码登录还被拒"才彻底放弃——避免无限循环弹浏览器。

### 3.5 墓碑与跨进程锁：一句话带过

这套存储是**多进程共享**的（CLI、VS Code、server 可能同时活着），所以刷新令牌的临界区用 `proper-lockfile` 加了跨进程文件锁（`oauth-manager.ts:175-187` 的锁目标解析：非 Windows、未设 `KIMI_DISABLE_OAUTH_LOCK` 时锁 `~/.kimi-code/oauth/kimi-code`）；refresh_token 被 401 拒绝时会写一块"墓碑"——`access_token` 置空的记录（`token-state.ts:36-45` 的 `revokedTombstone`），让其他进程看到"登录过、现在需要重登"而不是"从未登录"。完整机制（锁重试参数、竞态恢复、in-flight 合并）在 `oauth-manager.ts` 里有成段注释，本文不展开。

## 四、获取并供给模型：从 access_token 到 config.toml 的四块配置

### 4.1 provision 四步曲

token 到手后，`toolkit.login` 立刻进入供给阶段（`toolkit.ts:190-206`）：调 `provisionManagedKimiCodeConfig`（`packages/oauth/src/managed-kimi-code.ts:840-860`）——一个只有四步的函数：

```ts
export async function provisionManagedKimiCodeConfig<TConfig>(options): Promise<...> {
  const models = await fetchManagedKimiCodeModels(options);   // ① 拉模型清单
  const config = await options.adapter.read();                // ② 读现有 config.toml（严格模式）
  const applied = options.adapter.apply(config, {...});       // ③ 内存中合并出新配置
  await options.adapter.write(config);                        // ④ 写回 config.toml
  return { providerName: KIMI_CODE_PROVIDER_NAME, defaultModel: applied.defaultModel,
           defaultThinking: applied.defaultThinking, models, configPath: options.adapter.configPath };
}
```

`adapter` 是 `KimiAuthFacade` 构造时注入的（`packages/node-sdk/src/auth.ts:118-128`）：`read` 用 `readConfigFileForUpdate`（严格——基础文件已损坏就直接报错，避免把用户"坏但可修"的配置段落悄悄写丢），`write` 用 `writeConfigFile`，`apply` 就是下一小节的 `applyManagedKimiCodeConfig`。

### 4.2 拉模型：`GET /models`

`fetchManagedKimiCodeModels`（`managed-kimi-code.ts:489-524`）带 Bearer token 请求 `${baseUrl}/models`（默认 `https://api.kimi.com/coding/v1/models`），响应按 OpenAI 风格的 `{data: [...]}` 解析，逐项过 `toModelInfo`（`managed-kimi-code.ts:417` 起：`id` 必须非空字符串、`context_length` 必须正整数）。**身份类错误单独成类**：

```ts
if (response.status === 401 || response.status === 402 || response.status === 403) {
  throw new ManagedKimiCodeModelsAuthError({
    status: response.status, baseUrl, message, credentialKind: options.credentialKind,
  });
}
```

`ManagedKimiCodeModelsAuthError`（`managed-kimi-code.ts:111-130`）继承 `OAuthUnauthorizedError`——这个继承关系是 3.4 小节降级梯子和 6.1 小节 402 弹窗能够工作的前提：`toolkit.login` 的 catch 只放行 `OAuthUnauthorizedError` 家族走重试梯子（`toolkit.ts:208`）。

### 4.3 写哪四块：`applyManagedKimiCodeConfig` 全景

`applyManagedKimiCodeConfig`（`managed-kimi-code.ts:565-644`）把模型清单翻译成 config.toml 的四个角落：

| config.toml 位置 | 写入内容 | 作用 |
|---|---|---|
| `providers["managed:kimi-code"]` | `{type: "kimi", baseUrl, apiKey: "", oauth: {key, oauthHost}}` | 声明"托管 provider"：走 OAuth 而非 API key（`apiKey` 刻意留空） |
| `models["kimi-code/<模型id>"]` 等 | 每个模型一条别名记录（字段映射见下） | 模型清单本体 |
| `defaultModel` + `thinking` | 选中的默认模型 + 默认思考开关 | 新会话的初始模型 |
| `services.moonshotSearch` / `services.moonshotFetch` | `{baseUrl: "<base>/search|/fetch", apiKey: "", oauth}` | 搜索/抓取两个内置服务也挂上同一个 OAuth 凭据 |

模型别名的字段映射在 `toManagedModelAlias`（`managed-kimi-code.ts:532-563`）：

- `id` → `model`（真实模型 ID）、`context_length` → `maxContextSize`、`display_name` → `displayName`；
- `capabilities` 数组原样保留（`thinking` / `always_thinking` 等）；
- `think_efforts` 解析成 `supportEfforts` / `defaultEffort`（`managed-kimi-code.ts:462` 起）；
- **协议特判**：`protocol === 'anthropic'` 的模型额外标 `betaApi: true`（Kimi 的 Anthropic 兼容端点在 `/v1/messages?beta=true`）和 `adaptiveThinking: true`（该端点只接受自适应思考）——这两条直接决定引擎侧怎么发请求。

合并策略是"上游所有权"（`managed-kimi-code.ts:599-622`）：上游（服务端 `/models`）声明的字段**覆盖**本地；用户手工加的字段**保留**；上游不再列出的托管模型**删除**。这样每次重新登录都等于一次模型目录同步，又不会抹掉用户的私货。

### 4.4 默认模型怎么选：`selectDefaultModel`

`selectDefaultModel`（`managed-kimi-code.ts:736-772`）只有两条路：二次登录（`preserveExisting`，即 2.2 小节的 `hadToken`）且旧默认仍有效 → 保持不动；否则取服务端列表的**第一个**模型。思考开关由 `forcedThinking`（`managed-kimi-code.ts:727-734`）按服务端三态声明纠偏：`only`（永远思考）强制开、`no`（不支持）强制关，其余尊重本地已有值。

## 五、加载与 UI 更新：让界面认识这批新模型

### 5.1 回程：一句 `{success: true}` 触发的连锁

设备码流完成、配置写盘后，`auth.handler.ts:25-26` 补一个 `updateLoginContext`（见 5.6）然后回包 `{success: true}`。webview 侧 `handleLogin` 收到 → `onLoginSuccess()`（`LoginScreen.tsx:48-49`）→ `App.tsx:86-90`：

```ts
const handleLoginSuccess = useCallback(() => {
  setShowLogin(false);     // 不再强制登录视图
  setSkippedLogin(false);
  refresh();               // 重跑整个初始化
}, [refresh]);
```

### 5.2 `refresh` 的实现：一个自增的 `initKey`

`refresh`（`useAppInit.ts:63-66`）只有两行：把状态重置回 `loading`，然后 `setInitKey((k) => k + 1)`。`initKey` 是 `init()` 那个 `useEffect` 的依赖项（`useAppInit.ts:147`）——数字一变，effect 重跑，1.1 小节描述的整个初始化流程（checkWorkspace → 三个配置 RPC → checkLoginStatus + getModels 并行）原样再来一遍。这是 React 里"把初始化当成可重放过程"的标准做法：不写"登录后要刷新 A、B、C"的散装补丁，而是让路由器基于新事实重新算一遍该显示什么。

### 5.3 `getModels`：强迫宿主重读 config.toml

`getModels` 的宿主侧（`apps/vscode/src/handlers/config.handler.ts:87-90`）：

```ts
const getModels: Handler<void, WebviewKimiConfig> = async (_, ctx) => {
  const config = await ctx.harness.getConfig({ reload: true });
  return toWebviewConfig(config);
};
```

`{reload: true}` 是关键词。harness（v2 引擎）的实现（`packages/node-sdk/src/sdk-rpc-client-v2.ts:662-668`）：

```ts
override async getConfig(options?: GetConfigOptions): Promise<KimiConfig> {
  await this.configReady;
  if (options?.reload) {
    await this.klient.global.config.reload();     // 丢弃内存缓存，重读 config.toml + env 覆盖
  }
  return resolvedConfigToKimiConfig(await this.klient.global.config.getAll());
}
```

因为第四章的供给是**直接写文件**（绕过了宿主内存里的配置缓存），不 `reload` 的话引擎还拿着登录前的旧快照——这是"配置文件是事实源、内存只是缓存"的直接体现。回包前再过一道 `toWebviewConfig`（`config.handler.ts:133-149`）：`models` 排序、补 `defaultModel`/`defaultThinking`/`defaultThinkingEffort`，裁成 webview 需要的形状。

### 5.4 三态判定与视图路由

`init()` 拿到新数据后的判定顺序（`useAppInit.ts:114-131`）：

| 条件 | 结果状态 | 界面 |
|---|---|---|
| `modelsCount === 0 && !loggedIn` | `not-logged-in` | 回登录页 |
| `modelsCount === 0`（但已登录） | `no-models` | 状态页（陷阱，见 6.4） |
| 默认模型是 `managed:kimi-code` 但未登录（`requiresManagedProviderLogin`，`settings.store.ts:80-87`） | `not-logged-in` | 回登录页 |
| 其余 | `ready` | 主界面 |

正常登录后走最后一行。视图切换由纯函数 `resolveAppView`（`useAppInit.ts:28-45`）完成——`App.tsx:108` 拿它的结论整棵换渲染树：登录屏消失，`ChatArea` + `InputArea` 上场。这个路由器的每条分支都有测试盯着（`apps/vscode/test/app-init.test.ts:35-81`，8 个用例）。

### 5.5 模型进 zustand，选择器重渲染

`init()` 里两条 RPC 之后立刻（`useAppInit.ts:111-112`）：

```ts
setIsLoggedIn(loginStatus.loggedIn);
initModels(kimiConfig.models, kimiConfig.defaultModel, kimiConfig.defaultThinking, kimiConfig.defaultThinkingEffort);
```

`initModels`（`apps/vscode/webview-ui/src/stores/settings.store.ts:321-338`）把模型数组、默认模型、思考档位一次性 `set` 进 zustand store（术语见 `学习文档/08-术语表.md`"zustand"）：算出 `initialModel`（默认模型或第一个）、`thinkingEffort`（按模型能力推默认档），标记 `modelsLoaded: true`。所有订阅这个 store 的组件随之重渲染，最直接的就是输入区的模型选择器（`apps/vscode/webview-ui/src/components/inputarea/InputArea.tsx`）：

- 按钮文案显示当前模型名（`InputArea.tsx:427`：`{currentModelConfig?.name ?? "No models available"}`）；
- 下拉按 provider 分组列出全部模型（`InputArea.tsx:441-455`），点选走 `updateModel(model.id)`（`InputArea.tsx:447`）→ `saveConfig` RPC 持久化回 config.toml——**用户在 UI 上选模型，写的正是第四章供给出来的那块 `defaultModel`**，闭环回到文件。

### 5.6 宿主侧的 UI 更新：`kimi.isLoggedIn` 上下文

webview 之外，宿主自己还有一排 UI 要同步。`updateLoginContext`（`apps/vscode/src/utils/context.ts:4-9`，登录成功/失败/登出后都会调）：

```ts
export async function updateLoginContext(harness: KimiHarness): Promise<boolean> {
  const status = await harness.auth.status();
  const loggedIn = status.providers.some((provider) => provider.hasToken);
  await vscode.commands.executeCommand("setContext", "kimi.isLoggedIn", loggedIn);
  return loggedIn;
}
```

`setContext` 设置的 `kimi.isLoggedIn` 是 VS Code 的**命令菜单显隐开关**：`apps/vscode/package.json:235` 里 logout 菜单项带着 `"when": "kimi.isLoggedIn"`——登录前它根本不出现。webview 侧的对应物是 store 里的 `isLoggedIn`（`setIsLoggedIn` 存入），驱动右上角操作菜单的 Sign in / Sign out 切换（`apps/vscode/webview-ui/src/components/ActionMenu.tsx:140-143`）。

一次成功登录最终更新的 UI 清单：

| 位置 | 变化 | 驱动数据 |
|---|---|---|
| webview 整体视图 | 登录屏 → 主界面（聊天区 + 输入区） | `resolveAppView` 判 `ready` |
| 输入区模型按钮/下拉 | "No models available" → 真实模型列表 | store `models` / `currentModel` |
| 输入区思考档位 | 出现该模型支持的档位 | store `thinkingEffort` |
| webview 操作菜单 | Sign in → Sign out | store `isLoggedIn` |
| VS Code 命令菜单 | 出现 Kimi logout 项 | `kimi.isLoggedIn` 上下文 |

## 六、异常分支：每个"不顺利"都有自己的下落

### 6.1 402：没订阅——登录其实成功了

服务端对没订阅 Kimi Code 的账号在 `/models` 上回 402。链路：`fetchManagedKimiCodeModels` 抛 `ManagedKimiCodeModelsAuthError`（4.2 小节）→ `toolkit.login` 的梯子判断"首次登录（`!hadToken`）不走重试"直接上抛（`toolkit.ts:208-209`）→ `auth.handler.ts:27-36` catch 住，返回 `{success: false, error: message}` → webview `handleLogin` 用 `isPaymentRequiredError`（`LoginScreen.tsx:24-27`）检查错误文本：

```ts
function isPaymentRequiredError(error: string | null): boolean {
  if (!error) return false;
  return error.includes("402") || error.toLowerCase().includes("payment required");
}
```

命中则不显示红色错误，而是弹"Subscription Required"对话框（`LoginScreen.tsx:170-183`），Subscribe 按钮打开 `https://www.kimi.com/code`（`LoginScreen.tsx:78`；海外区站点区分是已知 TODO，见该处注释）。注意此时 **token 已经落盘**（第三章先于第四章），所以"没订阅"的用户下次打开插件不会再看到登录页——他们落在 6.4 的 `no-models` 状态页。

### 6.2 用户拒绝授权：`access_denied`

浏览器授权页上点"拒绝" → 轮询拿到 `access_denied` → 抛 `OAuthAccessDeniedError`（`oauth-manager.ts:432-435`）→ `auth.handler.ts:35` 给错误消息加前缀返回：

```ts
error: error instanceof OAuthAccessDeniedError ? `Login cancelled: ${message}` : message,
```

webview 显示为普通错误 + 回到 idle 可重点。

### 6.3 三层超时的嵌套关系

| 层 | 时长 | 位置 | 超时后果 |
|---|---|---|---|
| 单次 HTTP 请求 | 30 秒 | `oauth.ts:57` `DEFAULT_HTTP_TIMEOUT_MS` | 抛 `OAuthConnectionError`（可重试层面在刷新流里） |
| 整场设备码流 | 15 分钟 | `oauth-manager.ts:29` + `:421-425` | 抛 `DeviceCodeTimeoutError` |
| webview RPC 等待 | 16 分钟 | `bridge.ts:28` `OAUTH_REQUEST_TIMEOUT_MS` | 前端 reject，显示错误 |

内层必须短于外层：设备码最坏 15 分钟结束，RPC 留 1 分钟余量——保证**宿主的结论永远先于前端的耐心到达**。

### 6.4 `no-models` 陷阱：token 在、模型不在

如果设备码流成功、token 落了盘，但供给阶段断网/服务端故障（第四章没写成 config.toml），用户下次打开插件：`checkLoginStatus` 说已登录、`getModels` 说零模型 → 5.4 表第二行 `no-models`。这个状态页**必须保留"回到登录"的入口**——因为"Reload"改变不了磁盘状态，唯一能重触发供给的动作就是再走一遍登录。这是一条写成注释的硬需求（`useAppInit.ts:20-27`），并且有专门测试用例盯着（`app-init.test.ts:54`"keeps a sign-in path in the no-models trap"）。
