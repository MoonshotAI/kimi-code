# Kimi Code 审批模式 — 渐进式教学

---

## 第一层：直觉 — 它是什么？

想象你让一个实习生（AI 助手）帮你改代码。有些实习生你非常信任，可以放手让他干；有些你不太放心，每次改文件前都想先看一眼他要改什么；还有一些介于两者之间。

**审批模式就是控制这个"放手程度"的开关。**

这个项目（Kimi Code CLI）提供了三种模式：**yolo（大胆放权）、manual（逐个审批）、auto（全自动）**。它在 `config.toml` 里配置，也支持在对话中用命令 `/yolo`、`/manual`、`/auto` 随时切换。

---

## 第二层：动手 — 具体怎么运作？

打开 `~/.config/kimi-code/config.toml`（或项目根目录下的 `.kimi/config.toml`），你可以看到类似这样的配置：

```toml
# 方案 A：旧式布尔开关
yolo = false

# 方案 B：新式枚举
defaultPermissionMode = "manual"

# 自定义规则
[permission]
rules = [
  { pattern = "Read",  decision = "allow" },
  { pattern = "Write(**/test/**)", decision = "allow", reason = "test files are safe" },
  { pattern = "Bash(rm *)", decision = "deny" },
]
```

每次 AI 要调用一个工具（比如 `Write` 写文件、`Bash` 跑命令、`Read` 读文件），都会经过一个**审批流水线**（`createPermissionDecisionPolicies`，在 `packages/agent-core/src/agent/permission/policies/index.ts`）。这个流水线上有 20 多个"政策"（policy），按顺序执行，**第一个命中的说了算**。

流水线的核心逻辑大概长这样：

```
PreToolCallHook → AgentSwarm独占 → Auto+AskUserQuestion拦截
→ PlanMode保护 → 用户配置的deny规则 → Auto模式直接批准
→ 历史会话批准规则 → 用户配置的ask规则 → 用户配置的allow规则
→ ExitPlanMode审查 → Goal启动审查 → PlanMode工具批准
→ 敏感文件(如.env)询问 → .git目录询问 → Yolo模式批准
→ Swarm模式批准 → 默认安全工具(只读)批准 → Git工作目录写批准
→ 以上都没命中 → 询问用户
```

## 第三层：为什么 — 解决了什么问题？

### 根本矛盾：效率 vs 安全

AI 编程助手面临一个核心的**信任-效率权衡**：

- 如果每次调用都要等用户点"确认"，效率极低，对话节奏被打断
- 如果完全放权，AI 可能误删文件、跑危险命令、泄露密钥

### 三种模式的解决思路

| 模式 | 怎么用 | 适合场景 |
|------|--------|----------|
| **manual** | 规则驱动：你写规则定义什么操作 allow/deny/ask，没规则匹配的默认 ask | 普通开发、对安全性敏感、想了解 AI 每一步在做什么 |
| **yolo** | 只有 deny 规则能拦截，其他全部放行 | 高度信任的场景、已知项目结构、重复性任务 |
| **auto** | deny 规则仍生效，但不再询问用户，所有非 deny 的调用自动批准 | 子 agent 自动化、CI/批处理、长时间无人值守任务 |

### 规则的三层作用

规则 `{ pattern, decision, scope }`：

- **allow** — 这类操作直接放行，不问
- **deny** — 这类操作直接禁止
- **ask** — 这类操作弹窗问你

scope 控制"这次批准了，以后同类操作还用不用再问"：
- `turn-override` — 仅本次有效
- `session-runtime` — "本次会话内都批准"（用户点了"批准本次会话"后自动产生）
- `project` / `user` — 来自项目或用户配置

## 第四层：细节 — 工程实现

代码主要在 `packages/agent-core/src/agent/permission/` 下。

### 核心类型（`types.ts`）

```typescript
type PermissionMode = 'manual' | 'yolo' | 'auto';
type PermissionRuleDecision = 'allow' | 'deny' | 'ask';
type PermissionRuleScope = 'turn-override' | 'session-runtime' | 'project' | 'user';

interface PermissionRule {
  decision: PermissionRuleDecision;
  scope: PermissionRuleScope;
  pattern: string;     // 如 "Read(/etc/**)", "Bash(rm *)"
  reason?: string;
}
```

### Policy 架构（策略模式）

每个 policy 实现 `PermissionPolicy` 接口：

```typescript
interface PermissionPolicy {
  readonly name: string;
  evaluate(context: PermissionPolicyContext): 
    PermissionPolicyResult | undefined;
}

type PermissionPolicyResult = 
  | { kind: 'approve'; reason?: ... }
  | { kind: 'deny';   reason?: ...; message?: string }
  | { kind: 'ask';    resolveApproval?: ...; resolveError?: ... };
```

20 多个 policy 被排成有序数组，逐一执行（`evaluatePolicies`），第一个返回非 `undefined` 的就作为最终决定。这种设计保证了**可组合性**：新增一个审批策略只需要写一个新 policy 类，插到流水线的合适位置即可。

### 配置加载流程

```
config.toml → schema.ts (zod 校验) → toml.ts (TOML ↔ 内部格式转换)
→ configService → PermissionManager → 流水线执行
```

### 模式切换

```
/auto / /manual / /yolo → PermissionManager.setMode()
→ logRecord (写入 records) + replayBuilder.push (写入回放)
→ emitStatusUpdated (通知 UI/TUI 更新状态栏)
→ DynamicInjector 注入上下文提示语到 agent 的 system prompt
```

`PermissionModeInjector` 会在模式切换时向 AI 的上下文中注入提醒。切到 auto 时会告诉 AI "你现在是 auto 模式，不要调用 AskUserQuestion，自己做决定"；离开 auto 时也会注入退出提示。

### 用户配置规则匹配

`matches-rule.ts` 里的 `matchesPattern` 函数处理模式字符串的匹配逻辑。支持 DSL 风格的语法如 `Read(/etc/**)`、`Bash(rm *)`，也支持裸工具名如 `Write`。

## 第五层：关联 — 更广阔的地图

### 与 plan mode 的关系

审批模式和 `planMode` 是正交的两个维度。plan mode 是"先写计划再执行"的工作流，而审批模式控制的是执行阶段的权限。两者可以叠加使用：

- `manual + planMode` → 写计划要审批，执行工具调用也要审批（最保守）
- `yolo + planMode` → 写计划通过后就放手执行（适合快速迭代）
- `auto + planMode` → 全自动计划->执行（agent 自治）

### 与 goal mode 的关系

`CreateGoal` 工具调用时，`GoalStartReviewAskPermissionPolicy` 会拦截并询问用户：**goal 以什么审批模式运行？** 这允许用户设定"这个自动化目标在 auto 模式下运行，不需要中间确认"。

### 行业对比

- **Claude Code** — 类似的三级权限：`yolo` / `auto` / `manual`，但 policy 系统更像硬编码逻辑，没有可组合的流水线架构
- **Cursor** — 权限配置更粗粒度，只有"每次操作问"/"自动允许"两级
- **Copilot** — 几乎没有审批机制，靠用户手动 review

Kimi Code 的审批架构优势在于**策略模式 + 流水线编排**：新增策略不改现有逻辑，每个 policy 职责单一，测试覆盖容易。
