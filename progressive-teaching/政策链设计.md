# Kimi Code 审批政策链设计 — 渐进式教学

---

## 第一层：直觉 — 政策链长什么样？

想象一个安检通道。入口处站了 20 个保安，排成一列。每个人只负责一件事：

- **保安 A**：检查你是不是 VIP（auto 模式），如果是直接放行
- **保安 B**：检查你是不是危险分子（deny 规则），如果是直接拦住
- **保安 C**：检查你是不是要去敏感区域（写 `.env` 文件），如果是就叫主管来问你
- ...以此类推

**谁先表态听谁的。** 如果保安 A 放行了，后面的保安就不再管了。如果保安 A 没表态，保安 B 上。

这就是政策链的核心设计：**一个有序的策略列表，第一个返回非 `undefined` 结果的就是最终决定。**

源代码就在 `packages/agent-core/src/agent/permission/policies/index.ts` 里——20 个 policy 排成一列：

```typescript
export function createPermissionDecisionPolicies(agent: Agent): PermissionPolicy[] {
  return [
    new PreToolCallHookPermissionPolicy(agent),
    new AgentSwarmExclusiveDenyPermissionPolicy(),
    // ……中间 16 个……
    new FallbackAskPermissionPolicy(),    // 谁都没表态？那就问用户
  ];
}
```

**思考题：** 如果两个 policy 一个想 `approve`、一个想 `deny`，放在不同顺序会产生完全不同的结果。你觉得应该把 deny 类的 policy 放在前面，还是 approve 类的放在前面？

## 第二层：动手 — 逐个走一遍流程

假设目前是 `manual` 模式，AI 调用 `Write(/root/projects/my-app/src/app.ts)`。

政策链会这样走：

| 步骤 | Policy | 判断 | 结果 |
|------|--------|------|------|
| 1 | `PreToolCallHook` | 检查 pre-tool hook 是否有拦截 | 无 → 跳过 |
| 2 | `AgentSwarmExclusiveDeny` | 不是 AgentSwarm 调用 | 跳过 |
| 3 | `AutoModeAskUserQuestionDeny` | 模式 != auto | 跳过 |
| 4 | `PlanModeGuardDeny` | plan mode 未激活 | 跳过 |
| 5 | **`UserConfiguredDeny`** | 遍历用户规则，匹配第一个 `deny` | 可能命中 → **deny**（到此为止） |
| 6 | `AutoModeApprove` | 模式 != auto | 跳过 |
| 7 | `SessionApprovalHistory` | 之前有没有"批准本次会话"的记录？ | 有则 **approve** |
| 8 | `UserConfiguredAsk` | 用户配了 `Write` 为 ask？ | 有则 **ask** |
| 9 | `UserConfiguredAllow` | 用户配了 `Write` 为 allow？ | 有则 **approve** |
| 10 | `ExitPlanModeReviewAsk` | 不涉及 ExitPlanMode | 跳过 |
| 11 | `GoalStartReviewAsk` | 不涉及 CreateGoal | 跳过 |
| 12 | `PlanModeToolApprove` | plan mode 未激活 | 跳过 |
| 13 | `SensitiveFileAccessAsk` | 不是 `.env`/SSH 密钥 | 跳过 |
| 14 | `GitControlPathAccessAsk` | 不是 `.git` 目录 | 跳过 |
| 15 | `YoloModeApprove` | 模式 != yolo | 跳过 |
| 16 | `SwarmModeAgentSwarmApprove` | 不是 swarm 场景 | 跳过 |
| 17 | `DefaultToolApprove` | Write 不在默认批准列表里 | 跳过 |
| 18 | `GitCwdWriteApprove` | 在 cwd 内 + 在 git 工作树内？ | 是 → **approve** |
| 19 | `FallbackAsk` | 前面的全跳过 | **ask**（兜底） |

最终结果要么在第 5 步被 deny 规则拦住，要么在第 18 步因为"在 git 工作目录内写文件"而被批准，要么在第 19 步直接问用户。

**动手练：** 如果换成 `yolo` 模式，流程会怎么变？

答案提示：忽略手动配置的 ask 规则、无视 FallbackAsk，到第 15 步 `YoloModeApprove` 就全部放行了。

## 第三层：为什么 — 这种设计解决了什么问题？

### 问题 1：审批逻辑的"大泥球"

如果不用政策链，你可能会写出这样的代码：

```typescript
function checkPermission(tool, context) {
  if (mode === 'yolo') return approve;
  if (mode === 'auto' && tool !== 'AskUserQuestion') return approve;
  if (planModeActive && tool === 'Write' && path !== planFile) return deny;
  for (const rule of rules) {
    if (match(rule)) return rule.decision;
  }
  // ... 更多逻辑
  return ask;
}
```

随着规则增多，这个函数会膨胀成**几百行的 if-else 迷宫**。新加一个规则要读懂整个函数，改一个地方可能影响其他逻辑。

### 问题 2：组合爆炸

审批决策有多个正交维度：

- 模式（yolo / manual / auto）
- 用户规则（allow / deny / ask）
- plan mode（激活 / 未激活）
- goal mode（激活 / 未激活）
- 工具类型（写文件 / 读文件 / 跑命令）
- 路径（git 工作目录 / .env 文件 / .git 目录）
- 历史记录（之前批准过当前会话吗？）

如果用 if-else 覆盖所有组合，复杂度是乘积级的。

### 政策链怎么解决

**每个 policy 只关心一件事。**

```
PreToolCallHook          → 只检查 hook 是否有拦截
PlanModeGuardDeny         → 只检查 plan mode 下是否违规写文件
SensitiveFileAccessAsk    → 只检查是否写 .env
GitCwdWriteApprove        → 只检查是否在 git 工作目录内写文件
SessionApprovalHistory    → 只检查之前有没有"批准本次会话"
```

每个 policy 的实现只有 10-30 行，一眼就能看明白它在干什么。

**组合靠顺序，而不是靠条件判断。** 想要"deny 优先于 allow"？把 deny policy 放在 allow policy 前面就行了。想要"auto 模式先拦截 AskUserQuestion 再放行其他"？放两个 policy：一个 deny（AskUserQuestion）、一个 approve（其他一切）。

### 一个关键的取舍

**政策链的"先命中先得"意味着顺序就是策略。** 这既是优点也是约束：

- 优点：顺序明确，一目了然
- 约束：不能在一个 policy 里说"我决定不了，让后面的看着办"——要么返回结果，要么返回 `undefined` 表示弃权

## 第四层：细节 — 工程实现剖析

### 接口契约

```typescript
// types.ts
interface PermissionPolicy {
  readonly name: string;                               // 用于日志和 telemetry
  evaluate(context: PermissionPolicyContext): 
    PermissionPolicyResult | undefined;                // undefined = 弃权
}

type PermissionPolicyResult = 
  | { kind: 'approve'; reason?: Record<string, ...> }  // 放行
  | { kind: 'deny';    reason?: ...; message?: string } // 拒绝
  | { kind: 'ask';     resolveApproval?: ... }          // 问用户
```

返回值语义：

- **`approve`** — 工具调用被批准
- **`deny`** — 工具调用被禁止，附带给 AI 的拒绝消息
- **`ask`** — 需要用户决策，通过 `requestToolApproval` 走审批 UI 流程
- **`undefined`** — 不关我事，下一个

### evaluate 的执行

在 `PermissionManager` 中：

```typescript
private async evaluatePolicies(context): Promise<PolicyEvaluation | undefined> {
  for (const policy of this.policies) {
    const result = await policy.evaluate(context);
    if (result !== undefined) {
      return { policyName: policy.name, result };
    }
  }
  return undefined;  // 这实际上不会发生，因为 FallbackAsk 永远返回非 undefined
}
```

### 几个值得关注的 policy 设计

#### `AutoModeAskUserQuestionDeny` — 优先于 `AutoModeApprove`

```typescript
// auto 模式下，先拒绝 AskUserQuestion，再放行其他
// 顺序很重要：如果 AutoModeApprove 在前面，AskUserQuestion 也会被放行
new AutoModeAskUserQuestionDenyPermissionPolicy(agent),  // 先拦截
new AutoModeApprovePermissionPolicy(agent),              // 后放行
```

#### `SessionApprovalHistory` — 放在 user ask 规则前

```typescript
// 用户点了"本次会话都批准"后，生成的 session-runtime 规则在这里生效
// 放在 UserConfiguredAsk 之前，使得会话级别的批准能覆盖 ask 规则
new SessionApprovalHistoryPermissionPolicy(agent),  // 先检查会话历史
new UserConfiguredAskPermissionPolicy(agent),       // 再检查 ask 规则
```

评论区写着：*"Runs before user-configured ask rules so an in-session grant beats a still-matching ask rule on later calls."*

#### `ExitPlanModeReviewAsk` — 也放在 session history 后

```typescript
// 即使之前批准了某个会话，新的 plan 内容仍然需要审查
new ExitPlanModeReviewAskPermissionPolicy(agent),  // 审查 plan
```

评论区写着：*"Runs before session history so a stale session approval can't bypass review of a new plan body."*

#### `FallbackAsk` — 兜底策略

最简单也最重要。只有 10 行：

```typescript
class FallbackAskPermissionPolicy implements PermissionPolicy {
  readonly name = 'fallback-ask';
  evaluate(_context): PermissionPolicyResult {
    return { kind: 'ask' };
  }
}
```

**它永远放在最后。** 这意味着"所有 policy 都不表态时，默认问用户"，而不是"默认放行"或"默认拒绝"。这是一个安全优先的设计决策。

### 数据流全景

```
ToolCall 准备执行
    │
    ▼
PermissionManager.beforeToolCall(context)
    │
    ▼
evaluatePolicies(context)
    │  for each policy:
    │    policy.evaluate(context)
    │      └── 可能读 mode、规则、路径、历史……
    │    if result !== undefined → 返回 PolicyEvaluation
    │
    ▼
处理结果 ─── kind === 'approve' ──→ 放行工具调用
            kind === 'deny'    ──→ 返回 block=true，附拒绝消息
            kind === 'ask'     ──→ requestToolApproval()
                                     ├── 有 rpc.requestApproval → 走审批 UI
                                     └── 无 rpc → 默认 approved
```

## 第五层：关联 — 政策链的演进与对比

### 类似设计模式

政策链本质是 **Chain of Responsibility（职责链模式）**+ **Strategy（策略模式）** 的混合体：

- 链式遍历：`for policy of policies`，类似 Express/Koa 的中间件
- 策略独立：每个 policy 可单独测试、单独部署

### 跟其他常见链式设计的对比

| 设计 | 遍历方式 | 终止条件 | 典型用途 |
|------|----------|----------|----------|
| **Kimi 政策链** | 线性，each-policy-once | 第一个非 undefined | 审批决策 |
| **Express 中间件** | 线性，顺序执行 | 不调用 `next()` | HTTP 请求处理 |
| **Koa 中间件** | 洋葱模型，双向 | 不调用 `await next()` | HTTP 请求处理 |
| **Linux VFS 钩子** | 堆叠，按优先级 | 返回非零 | 文件系统操作 |

Kimi 选择了最简单的线性模型，因为审批场景不需要"回到起点"（不像 Koa 的响应处理），也不需要优先级排序（顺序硬编码就够了）。

### 如何新增一个 policy

假设你想加一个"周五下午 5 点后拒绝所有非只读操作"的 policy（防止下班前乱改代码）：

1. 新建 `packages/agent-core/src/agent/permission/policies/friday-afternoon-deny.ts`
2. 实现 `PermissionPolicy` 接口
3. 在 `policies/index.ts` 里 import 并插入到合适位置

```typescript
// friday-afternoon-deny.ts
export class FridayAfternoonDenyPermissionPolicy implements PermissionPolicy {
  readonly name = 'friday-afternoon-deny';
  evaluate(context: PermissionPolicyContext): PermissionPolicyResult | undefined {
    const now = new Date();
    if (now.getDay() !== 5) return;          // 不是周五，弃权
    if (now.getHours() < 17) return;         // 还没到 5 点，弃权
    const tool = context.toolCall.name;
    if (DEFAULT_APPROVE_TOOLS.has(tool)) return; // 只读工具，弃权
    return {
      kind: 'deny',
      message: '周五下午 5 点后不允许执行修改操作，周一再改吧。',
    };
  }
}
```

然后在 `policies/index.ts` 中，你想把它放在哪？我的建议是放在 `UserConfiguredDeny` 之后、`AutoModeApprove` 之前——这样即使用户配了 allow 规则，周五晚上也不会放行破坏性操作：

```typescript
new UserConfiguredDenyPermissionPolicy(agent),
new FridayAfternoonDenyPermissionPolicy(agent),   // ← 加在这里
new AutoModeApprovePermissionPolicy(agent),
```

## 总结

政策链设计的三个核心要点：

1. **单一职责** — 每个 policy 只做一件事，10-30 行代码
2. **顺序即策略** — 排列顺序决定了 deny/approve/ask 的优先级
3. **兜底安全** — `FallbackAsk` 确保任何未明确匹配的调用都会问用户，而不是默认放行

*核心代码路径：*

- `packages/agent-core/src/agent/permission/policies/index.ts` — 政策链编排
- `packages/agent-core/src/agent/permission/policies/*.ts` — 各 policy 实现
- `packages/agent-core/src/agent/permission/types.ts` — Policy 接口定义
- `packages/agent-core/src/agent/permission/index.ts` — PermissionManager 执行引擎
