# 生成双语 Release Notes

桌面端更新弹窗会展示该版本的中英双语更新说明，按内容分小节呈现。数据源是 `apps/desktop/CHANGELOG.md`（changesets 从 `.changeset/*.md` 汇总生成，条目为中文）；本 skill 负责把指定版本的小节抽出来、清洗、**分类分节**、翻译成英文，产出两个 markdown 文件。

数据流：`apps/desktop/CHANGELOG.md` → 本 skill → `release-notes/<version>/changelog.{zh,en}.md`（git 存档，发布人 review）→ `publish-desktop-cdn.sh <version>` 上传到 CDN `desktop/<version>/` → 桌面端更新弹窗按系统语言展示。

## 输入

- 一个版本号（如 `0.2.0`）。用户没给时，取 `apps/desktop/CHANGELOG.md` 里最新（最靠上）的版本号，并向用户确认。
- 前提是该版本已进 CHANGELOG.md（版本 PR 已合入）。找不到对应 `## <version>` 小节时**报错停下**，提示先合入版本 PR——不要拿别的版本顶替，更不要编造。

## 产物

写到仓根 `release-notes/<version>/` 下两个文件（目录不存在则创建）：

- `changelog.zh.md`：中文，小节 + 无序列表。
- `changelog.en.md`：英文翻译，**小节集合、顺序、条目数与中文 1:1 镜像**。

格式（小节之间空行；无版本标题、无日期、无正文以外内容）：

```markdown
### 新功能

- 支持在后台自动下载新版本，下载完成后重启即可更新；可在设置 → 高级中开启。

### 修复

- 修复窗口全屏时点击关闭按钮变成全黑屏幕的问题。
```

小节固定顺序与英文映射：

| 中文 | 英文 | 含义 |
|---|---|---|
| `### 新功能` | `### Features` | 用户以前做不到的新能力（新功能、新开关、新模式） |
| `### 优化` | `### Polish` | 已有功能的用户可感知改进：体验/视觉/性能调整、默认行为变化 |
| `### 修复` | `### Bug Fixes` | 修复坏掉的行为 |
| `### 其他` | `### Other` | 以上都不沾边的兜底 |

顺序：新功能 → 优化 → 修复 → 其他。**空小节省略**（条目少的版本可能只有一两个小节，正常）。desktop 的 changeset 只写用户可感知的变化，不设「重构」小节。

## 长度约束（硬要求）

更新弹窗只有 440px 宽，是 glance 场景，不是文档。**长度超标是最常见的 review 打回原因**：

- **每条一行一句话：中文 ≤ 40 字，英文 ≤ 15 词。** 这不是建议——超标必须压缩到达标为止。
- **一条只说一个效果。** 不允许多效果并列（"修复甲，同时修复乙，另外还优化了丙"直接判不合格）。唯一例外是可以带一个很短的使用指引从句（如"可在设置 → 高级中开启"）。
- **原文过长必须概括，不是照抄。** CHANGELOG 里的长句（多效果、机制解释、实现原理）只保留用户最关心的一个效果，其余果断丢弃——细节丢了不可惜，用户在弹窗里扫一眼就要关掉。压缩必须忠实事实，不编造原文没有的效果。
- **总量 ≤ 10 条。** 超出时先用合并规则收敛（步骤 3）；仍超则砍读者价值最低的条目（「其他」类、边角小修优先砍）。版本再大都只展示最重要的 10 条。

## 步骤

1. 读 `apps/desktop/CHANGELOG.md`，定位 `## <version>` 到下一个 `## ` 之间的小节。
2. 抽取条目：changesets 生成的每条形如 `- [#74](...) [\`3adc4c5\`](...) Thanks [@user](...)! - 真正的文案`，只取 `! - ` 之后的文案原文，剥掉 PR 链接、commit 链接、作者致谢前缀。同一 PR 多条属正常（一个 PR 多个 changeset），全部进入下一步。
3. **合并与去重**（照抄 kimi-code `sync-changelog` 的规则）：
   - 同一表面（同一功能/页面/组件）的多条小调整合并成一条高层条目，用最具体的公共祖先命名（如「设置页」「会话卡片」「工作区选择器」）。
   - 同一区域或同类问题的修复达到 **3 条以上**时合并成一条（如「修复深色模式下多处图标与标记几乎不可见的问题」）。
   - **不过度合并**：影响面广、价值高或真正不同的修复保持独立。合并是为了避免一屏近似条目，不是为了凑少。
4. **分类**：先按文案判断；拿不准时用剥下来的 commit hash `git show <hash>` 或 `gh pr view <N>` 看改动；仍不清放「其他」，**不要猜着塞进「新功能」**。
   - 判别问句：用户以前能做到这件事吗？**不能**→这是新能力，归「新功能」；**能**→只是变得更好用，归「优化」。「支持/新增」开头不一定算新功能（给已有页面加个小元素通常是优化）；默认行为变化通常归优化。
5. **节内排序**：按读者价值排，不按上游顺序——影响大、显而易见、高频的在前，边角小修在后。只重排，不改写、不夸大。
6. 写 `changelog.zh.md`：短条目文案逐字照抄；**长条目按「长度约束」压缩成一句话**（合并条目同样适用——概括忠实于原文事实，不编细节）。
7. 逐条翻译，写 `changelog.en.md`：小节标题按上表映射，条目逐条对译（翻译规范见下节），同样遵守 ≤ 15 词的上限。
8. 自检：
   - **每条中文 ≤ 40 字、英文 ≤ 15 词；每条只说一个效果；总条目 ≤ 10 条**——逐条数一遍，不许放过；
   - zh 每条都能在 CHANGELOG 小节里找到出处（压缩/合并条目能找到对应的原文）；
   - 两个文件的小节集合、顺序、每节条目数完全一致；无空小节；
   - 无 PR 号、commit hash、作者名残留；
   - 分类无硬凑（「其他」不为零不等于失败，但每条「新功能」都经得起判别问句）。
9. 把两个文件的完整内容展示给用户，**停下来等 review**：用户可能直接改文案或调整分类。review 通过后再按用户指示 commit（commit message 用 `chore: add release notes for v<version>` 之类的 conventional commit）。**不要未经 review 就提交。**

## 翻译规范

- 逐条对译，不增不删，不补充中文原文没有的信息（原文含糊就保持含糊，交给 review）。
- 用户面向的短句，一条一句、每条 ≤ 15 词；同一小节内句式节奏保持一致（如同为 `Fixed ...` 起手）。中文已是压缩后的一句话，英文不得再拉长。
- 修复类 `Fixed ...`；新功能类直接说用户得到什么（`Updates can now download in the background.`）。不出现文件名、内部包名、PR 号。
- 产品术语对齐现有英译：翻译前先查 `packages/app-i18n/src/locales/en/` 里相应说法（如 会话→session、工作区→workspace、思考→thinking、设置→Settings），保持一致。
- 拿不准如何翻译的产品名/功能名保留英文原词（如 Plan mode、Thinking）。

## 红旗

- CHANGELOG 里没有该版本，却用其他版本或自行编造条目。
- **任何一条超过长度上限（中文 40 字 / 英文 15 词）、或一条里塞多个效果；总条目超过 10 条。**
- 产物里残留 PR 号、commit hash、作者名。
- 翻译时自由发挥、补充原文没有的内容或"修复原理"。
- zh 与 en 的小节集合、顺序或条目数不一致；出现空小节。
- 分类靠猜（没看 commit 就把拿不准的条目塞进「新功能」）；把多条真正独立的高价值修复揉成一条。
- 未经用户 review 就 commit 产物。
