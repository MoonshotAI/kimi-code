# Review PR

这个仓库过去的回归，大多是改动对它自己的意图来说没错，却悄悄改掉了某个现有人群依赖的行为。下面的规则主要防这一类问题。依赖现有行为的人群和触发线索见 `.agents/skills/review-pr/surfaces.md`。

## Code Review Rules

### 评审范围与输出

- 只评审 PR 相对于 base 的 diff。base 上原本就有的问题只作为非阻塞备注，除非 PR 直接触发或放大了它。
- 每个问题写明违反的规则（写标题，并链接到规则原文）、`file:line`、等级和安全的改法；同一类问题一次列出所有位置。
- 等级按各条规则写明的报。不对应任何规则的问题，会让功能出错的报 P1，其余报 P2。整个 PR 的结论按最高等级给：有 P0 建议阻塞，有 P1 需要修改，否则可以合并。
- 不报纯风格问题，也不报 lint、类型检查和测试能拦住的问题。
- 复审只看上次评审之后的改动。已解决的讨论，核实当前代码确实修好了就不再提。

### 行为变化

改动前能正常工作的输入（配置项、环境变量、CLI 参数、模型服务返回的结构、旧版本写入的会话、客户端请求、hook 载荷），改动后必须表现一致。删除或收窄分支、条件、默认值时，问原来谁会走到这里；新增条件时，问哪些现有输入会先命中它。例如 #3492：数组字段存在时不再读字符串字段，而 OpenRouter 形态的网关两个字段同时发。常见的几种情况：

- 翻转默认值或删除功能：所有用旧默认值的人都受影响。PR 已声明的界面精简和视觉调整不在此列。
- 移植和重构：旧路径做过的每件事（支持的环境变量、回退逻辑、接受的输入）都要在新路径里有着落。
- 提示词文本：修改或删除 `packages/agent-core-v2/src/**/*.md` 里的句子，会改变收到这段文本的所有会话的 agent 行为；没有测试引用这句话，不代表没有影响。

安全做法：保留旧行为；确实要改，写进 PR 的行为变化表，并点名受影响的人群。翻转默认值或删除功能时，changeset 写明用户失去了什么，提供配置、环境变量或开关作为逃生口（或者有维护者在 PR 里明确签字），并加一个测试固定仍用旧行为的人群的行为。移植时列出旧路径的功能清单。删掉提示词里的一句约束时，指出接替它的句子、代码或测试。

等级：没有声明的行为变化、悄悄丢掉一项功能、删掉约束却没有接替，P1；翻转默认值既没有逃生口也没有维护者签字，P1；只缺说明、功能清单、changeset 或测试，P2。

### 契约文件的兼容性

以下文件是跨组件或对外的契约：`packages/agent-core-v2/docs/` 下的清单文件（`config-manifest.toml`、`wire-manifest.d.ts`、`state-manifest.d.ts`）、`packages/kap-server/schema/contract.txt`、`packages/kap-server/docs/kap.md`、`packages/node-sdk/src/index.ts`、`packages/agent-core-v2/src/features/externalHooks/`、`packages/acp-server/` 和 `apps/kimi-code/src/cli/`。上一个版本写入的数据、上一个版本发布的客户端，必须继续正常工作。使用方包括本仓库的桌面端和 Web 端、通过 KAP 驱动会话的外部 agent 和机器人、VS Code 扩展、Zed 等 ACP 客户端、SDK 用户、hook 脚本，以及解析无界面输出的程序。

安全做法：保留旧的字段、名字和事件，新行为用新增的可选字段或新事件承载；确实要破坏时，PR 写明每个使用方怎样迁移。

等级：破坏契约且没有兼容路径，P0；有兼容路径但没写迁移说明，P2。

### 静默失败

产品不能在没有任何信号的情况下丢数据、放宽批准或安全检查、忽略用户给的配置或输入：用户收不到信号，就无从报告。

安全做法：报错或给出用户看得见的警告，说明哪项没有生效、为什么。

等级：静默丢数据或放宽批准、安全检查，P0；静默忽略配置或输入，P1。

### 流程和规范项

缺 changeset、缺文档同步、缺测试、文件或常量放错位置，都是流程和规范问题，不会让功能出错。changeset、注释和 PR 文字分别按 `gen-changesets` 技能、根 `AGENTS.md` 的「通用编码规则」和 `write-pr` 技能判断，先读原文再报。changeset 最常见的误报：不为 `packages/app-*` 要 changeset；共享 UI 默认只写 `kimi-code-app`，专门针对 `kimi web` 的改动才加 `@moonshot-ai/kimi-code`。

测试按风险要求：改动涉及状态机、异步时序、数据或协议契约、默认值时，才要求修复前会失败的测试；只改样式、文案或静态常量、出错一眼就能看到的改动，不要求为它搭重型 mock 测试。

等级：最高 P2。

### 机械发版 PR

从 release 分支回同步到 main、同步 changelog、添加发版说明的 PR，内容是已经评审合入的改动或照着它们写的说明。

安全做法：只核对同步的内容本身是否完整、准确，不重审其中累积的改动。发版说明先于 tag 合入是正常顺序，不报「tag 或上游 CHANGELOG 还不存在」。

等级：同步时漏掉或改错了代码，P1；说明文字有缺漏或写错，P2。

## 完整评审

用户要求 review 一个 PR 时，在上面的规则之外再做这几件事：

1. 用 `gh pr view <number>` 和 `gh pr diff <number>` 读 PR，再读足够的周边代码：只看 diff，看不出改动前谁会走到某个分支。
2. 独立列出行为变化清单。尽量交给一个子 agent，只给它 PR 号和 `surfaces.md` 的路径，不给它作者对影响范围的结论；自己做时也要先列清单，再读作者的表。
   - 列出 diff 改变的每一个可观测行为，包括作者说「不变」或认为是「内部」的。每一行写行为、变化前、变化后、受影响人群和证据。
   - 证据是改动前后各一处 `file:line`。人群从 `surfaces.md` 里取，并写出它存在的依据。缺一样就不算问题，放进「待作者确认」，最多 5 条。
   - diff 命中 `surfaces.md` 的触发线索，或者测试把旧断言改成了新行为，清单里就必须有对应的行。
   - 问一遍：旧版本写入的数据、上一版发布的客户端，改动后是否仍然可用；回滚到上一版是否安全。
3. 拿清单逐行对比 PR 描述里的行为变化表：作者漏列的行为是问题；作者写了但找不到证据的，放进「待作者确认」。
4. 按下面的格式输出：

```markdown
## 结论
可以合并 / 需要修改 / 建议阻塞。

## 问题
按等级从高到低；没有就写「无」。

## 行为变化
| 行为 | 变化前 | 变化后 | 受影响人群 | 证据 |
|---|---|---|---|---|

待作者确认（最多 5 条）：
1. …
```
