# Review PR

这个仓库过去出的问题，大多不是代码写错了，而是改动本身没错，却悄悄改掉了一部分用户依赖的行为。下面的规则主要防这一类问题。哪些用户依赖现有行为、改到哪些地方要特别查，见 `.agents/skills/review-pr/users.md`。

## Code Review Rules

### 评审范围与输出

- 只评审 PR 相对于 base 的 diff。base 上原本就有的问题只作为非阻塞备注，除非 PR 直接触发或放大了它。
- 每个问题写明违反的规则（写标题，并链接到规则原文）、`file:line`、等级和安全的改法；同一类问题一次列出所有位置。
- 等级按各条规则写明的报。不对应任何规则的问题，会让功能出错的报 P1，其余报 P2。整个 PR 的结论按最高等级给：有 P0 建议阻塞，有 P1 需要修改，否则可以合并。
- 不报纯风格问题，也不报 lint、类型检查和测试能拦住的问题。
- 复审只看上次评审之后的改动。已解决的讨论，核实当前代码确实修好了就不再提。

### 行为变化

改动前能正常工作的输入，改动后必须表现一致。这些输入包括：配置项、环境变量、命令行参数、模型服务返回的数据、旧版本保存的会话、客户端请求、hook 收到的数据。删掉一个分支、条件或默认值，或者缩小它的适用范围时，问原来谁会走到这里；新增条件时，问哪些现有输入会先命中它。例如 #3492：返回里有数组字段时就不再读字符串字段，而 OpenRouter 这类网关两个字段都会发。常见的几种情况：

- 翻转默认值或删除功能：所有用旧默认值的用户都会受影响。PR 里已经说明的界面精简和视觉调整不在此列。
- 移植和重构：旧代码做过的每件事（支持的环境变量、出错时的回退、接受的输入），新代码里都要有。
- 提示词文本：修改或删除 `packages/agent-core-v2/src/**/*.md` 里的句子，会改变所有收到这段文本的会话里 agent 的行为；没有测试引用这句话，不代表没有影响。

安全做法：保留旧行为；确实要改，写进 PR 的行为变化表，并写明影响到哪些用户。翻转默认值或删除功能时，changeset 写明用户失去了什么，提供能恢复旧行为的配置、环境变量或开关（或者有维护者在 PR 里明确同意），并加一个测试把还在用旧行为的情况固定住。移植时列出旧代码做过的事。删掉提示词里的一句要求时，指出现在由哪句话、哪段代码或哪个测试来保证。

等级：没有说明的行为变化、悄悄丢掉一项功能、删掉提示词里的要求却没有替代，P1；翻转默认值，既没有恢复旧行为的办法也没有维护者同意，P1；只是缺说明、缺清单、缺 changeset 或缺测试，P2。

### 契约文件的兼容性

以下文件定义了跨组件或对外的接口约定：`packages/agent-core-v2/docs/` 下的清单文件（`config-manifest.toml`、`wire-manifest.d.ts`、`state-manifest.d.ts`）、`packages/kap-server/schema/contract.txt`、`packages/kap-server/docs/kap.md`、`packages/node-sdk/src/index.ts`、`packages/agent-core-v2/src/features/externalHooks/`、`packages/acp-server/` 和 `apps/kimi-code/src/cli/`。上一个版本保存的数据、上一个版本发布的客户端，必须继续正常工作。依赖这些约定的有：本仓库的桌面端和 Web 端、通过 KAP 操作会话的外部 agent 和机器人、VS Code 扩展、Zed 等 ACP 客户端、SDK 用户、hook 脚本，以及解析无界面模式输出的程序。

安全做法：保留旧的字段、名字和事件，新行为用新增的可选字段或新事件来提供；确实要破坏兼容时，PR 写明每个使用方怎样迁移。

等级：破坏兼容且没有过渡办法，P0；有过渡办法但没写迁移说明，P2。

### 静默失败

产品不能在没有任何提示的情况下丢数据、放宽审批或安全检查、忽略用户给的配置或输入：用户什么都看不到，也就无从报告。

安全做法：报错，或者给出用户看得见的警告，说明哪一项没有生效、为什么。

等级：悄悄丢数据，或者悄悄放宽审批、安全检查，P0；悄悄忽略配置或输入，P1。

### 流程和规范项

缺 changeset、缺文档同步、缺测试、文件或常量放错位置，都属于流程和规范问题，不会让功能出错。changeset、注释和 PR 文字分别按 `gen-changesets` 技能、根 `AGENTS.md` 的「通用编码规则」和 `write-pr` 技能判断，先读原文再报。changeset 最常见的误报：不要为 `packages/app-*` 要求 changeset；共享 UI 默认只写 `kimi-code-app`，专门针对 `kimi web` 的改动才加 `@moonshot-ai/kimi-code`。

测试按风险要求：改动涉及状态机、异步时序、数据或接口约定、默认值时，才要求修复前会失败的测试；只改样式、文案或固定的常量、出错一眼就能看到的改动，不要求为它写大量 mock 的测试。

等级：最高 P2。

### 发版同步 PR

从 release 分支回同步到 main、同步 changelog、添加发版说明的 PR，内容都是已经评审合入的改动，或者照着这些改动写的说明。

安全做法：只核对同步的内容本身是否完整、准确，不重审其中累积的改动。发版说明先于 tag 合入是正常顺序，不要报「tag 或上游 CHANGELOG 还不存在」。

等级：同步时漏掉或改错了代码，P1；说明文字有缺漏或写错，P2。

## 完整评审

用户要求 review 一个 PR 时，在上面的规则之外再做这几件事：

1. 用 `gh pr view <number>` 和 `gh pr diff <number>` 读 PR，再读足够的周边代码：只看 diff，看不出改动前谁会走到某个分支。
2. 独立列出行为变化清单。尽量交给一个子 agent，只给它 PR 号和 `users.md` 的路径，不告诉它作者对影响范围的判断；自己做时也要先列清单，再读作者的表。
   - 列出 diff 改变的每一个外部看得到的行为，包括作者说「没变」或认为是「内部」的。每一行写行为、变化前、变化后、影响到谁、证据。
   - 证据是改动前后各一处 `file:line`。影响到谁要从 `users.md` 里找，并给出确实有人这样用的依据（文档、issue、配置示例）。缺一样就不算问题，放进「待作者确认」，最多 5 条。
   - diff 改到了 `users.md`「改到这些地方要查」里列的位置，或者测试把旧断言改成了新行为，清单里就必须有对应的行。
   - 问一遍：旧版本保存的数据、上一版发布的客户端，改动后是否还能用；回滚到上一版是否安全。
3. 拿清单逐行对比 PR 描述里的行为变化表：作者漏写的行为是问题；作者写了但找不到证据的，放进「待作者确认」。
4. 按下面的格式输出：

```markdown
## 结论
可以合并 / 需要修改 / 建议阻塞。

## 问题
按等级从高到低；没有就写「无」。

## 行为变化
| 行为 | 变化前 | 变化后 | 影响到谁 | 证据 |
|---|---|---|---|---|

待作者确认（最多 5 条）：
1. …
```
