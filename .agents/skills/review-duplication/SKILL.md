# 检查重复实现

单独使用时，从用户指定的能力或代码入手。用于 PR 评审时，以相对 base 的代码 diff 为入口，复审从上次评审后的代码改动入手。检查对象是源码中的实现，文档正文和其中的代码示例不计入重复。可以跨包取证，意见应落在本次改动引入、触发或放大的问题上。

## 1. 提取核心逻辑

用调用方的语言说清新代码负责什么，接受哪些输入，承诺什么结果。把业务名换成可搜索的线索，例如协议路径、字段名、底层 API、数据结构或组件交互。即使 `jscpd` 没有命中，也可以通过这些线索找到写法不同的平行实现。

## 2. 定位职责，追踪依赖

先判断这项能力最可能由谁维护，再从定义追到实际调用方。以根 `AGENTS.md` 的项目地图和相关包的公开导出为起点。例如：

- 会话与协议先区分服务端实现、客户端操作和测试驱动。测试驱动查 `packages/testkit`，KAP 服务端查 `packages/kap-server`，桌面与 Web 的会话逻辑查 `packages/app-core`。
- 组件先区分终端和图形界面。TUI 查 `apps/kimi-code/src/tui` 和 `packages/pi-tui`；桌面与 Web 的产品组件查 `packages/app-components`，基础组件查 `packages/app-ui`。
- 配置、服务或通用算法从消费方的 import 追到所属领域，核对谁解释配置、谁维护状态、谁提供接口。

遇到新增的第三方 import，搜索仓库里同一依赖的其他用法，判断项目是否已有封装。遇到手写算法，检查目标包的 `package.json`、导出和运行环境，确认现有依赖或标准库的 API 是否覆盖所需行为。依赖仅出现在其他工作区或 lockfile 里，还需核实目标包能否直接使用它。

## 3. 搜索并对读候选实现

线索明确时，直接用 `rg` 查符号、API 或字段名。扩大搜索时，依次尝试同义命名、同一底层调用，以及测试名称和断言中描述的行为。按 KC 的约定，契约词汇可从最近的 `AGENTS.md` 指向的设计或协议文档中补充，结论回到代码和调用方核实。

跨包调查时，优先将定位候选实现的工作交给可用的只读子 agent。交代改动位置、要查的职责、搜索线索和包边界，请它返回候选符号、文件位置和实际调用方。若多个候选需要逐条比较，可再委派只读对照，给出同一组输入，请它说明行为差异和可以复用的部分。当前环境无法委派时，直接完成同样的搜索和对读。

## 4. 验证复用是否合适

对照相同输入下的结果，以及调用方依赖的边界行为，例如分页、取消、异常上报和资源释放。再核对适用的局部约定：错误是否走同一上报路径，状态是否已有 store 或服务负责，UI 是否使用所在端的主题和组件。指出这些差异对调用方的具体影响。

检查依赖方向和公开入口，判断可以直接复用、需要扩展已有接口，还是两处各有独立契约。例如 testkit 需要启动产品代码时，应由调用方注入入口。两处恰好调用相同的底层 API，也可能需要不同的生命周期。

## 5. 向用户报告，等用户决定

发现重复时，先只读核实，在当前对话中把同一原因的调用点合并汇报。无论来自代码对读还是 jscpd 命中，都说明：

- 两端的仓库相对路径、行号和符号，以及它们共同承担的职责。
- 两处行为是否一致。若有差异，给出触发条件、受影响的调用方和后果；尚未核实的地方明确标出。
- 建议怎么处理、理由和主要代价。例如直接复用已有接口、扩展接口，或因调用方契约不同而保留两处实现。指出推荐哪一种，并请用户决定。

收到用户明确选择后才执行相应改动。等待期间不自行重构、提交修复或调整检测规则来放行。

例如，若冷恢复测试用一次 GET 读取完整历史，可以这样反馈：“历史超过一页时，这个断言只验证了当前页。现有 `packages/testkit/src/kap/harness.ts` 的 `KapHarness.turns()` 会沿 `before_ordinal` 取完各页。让子进程驱动也能调用这段分页逻辑，并用跨两页的历史验证恢复结果。” 正式评审时补上该次 diff 的调用点和行号。

实现前单独调用时，列出候选接口、覆盖的需求和仍需新增的部分即可。
